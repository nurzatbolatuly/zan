# Zan Frontend — стандарты разработки

Обязательны для всех троих фронтендов в команде. Это не пожелания — это критерии ревью: PR, который их нарушает, не мержится, пока не поправлен.

Смежные документы:

- `PLAN.md` — что и в каком порядке строим
- `DESIGN_SYSTEM.md` — фиксированные токены (цвет/типографика/spacing/z-index) — единственный источник значений для стилей
- `instructions.md` — журнал изменений, обновляется вместе с этим файлом при любом отходе от стандарта

---

## 1. Архитектурные слои и правила зависимостей

```
app/        → знает про всех
features/   → знает только про shared, НЕ знает про другие features
shared/     → не знает ни про app, ни про features
routes/     → тонкие обёртки, только компоновка + lazy import
```

Жёсткие правила:

- `shared/*` никогда не импортирует из `features/*` или `app/*`. Если общий код тянет что-то фичевое — это сигнал, что код не общий, и его нужно оставить в фиче или обобщить по-настоящему (убрать фичевую зависимость).
- `features/a` никогда не импортирует напрямую из `features/b`. Общий кусок функциональности — переезжает в `shared/`, а не тянется кросс-импортом.
- Компонент страницы (`ChatPage.tsx`, `HistoryPage.tsx`...) — точка входа фичи. Он собирает более мелкие компоненты и хуки, сам почти не содержит логики.
- Разделение "логика / рендер": вся нетривиальная логика (запросы, вычисления, обработчики) — в хуках (`useThread`, `useBundlePricing`), компонент получает готовые значения и функции и только рендерит. Это не про "10 файлов на одну кнопку" — если логика в 3 строки, хук не нужен; правило про то, что рендер-JSX не должен вperемешку содержать `fetch`, расчёты цены и условную бизнес-логику.

## 2. Состояние — что где хранить

| Тип состояния                             | Где                                 | Пример                                             |
| ----------------------------------------- | ----------------------------------- | -------------------------------------------------- |
| Локальное, живёт только внутри компонента | `useState`/`useReducer`             | открыт ли `<details>`, значение поля до сабмита    |
| Кросс-компонентное в рамках приложения    | Zustand-стор в `shared/stores`      | тема, язык, сессия/баланс, состояние общих модалок |
| Серверные данные (что лежит в БД на бэке) | TanStack Query                      | треды, тарифы, промпты, аналитика                  |
| Форма с валидацией                        | React Hook Form (+ Zod-схема рядом) | редактор тарифа, промпты, свой набор               |

Никогда не дублировать серверные данные в Zustand/useState "для удобства" — один источник истины на сущность. Если экрану нужны производные данные (отфильтрованный список, посчитанная сумма) — это `useMemo` от серверных данных, а не отдельное поле стейта, которое обновляется вручную (в прототипе `bundleOverrides`/`deletedBundleIds` — пример того, чего избегаем: состояние-патч поверх статичных моков, Zan.dc.html:989-995).

## 3. Правило "чистая замена, а не наслоение"

Это ключевое правило команды, применяется при **любом** изменении подхода: смене паттерна, рефакторинге, замене библиотеки, переписывании компонента.

**Обязательно:**

- Если меняется способ, которым что-то делается (например: был `useState` для формы → переходим на React Hook Form) — в этом же PR переписываются **все** места в затронутой фиче, использующие старый способ. Не "новое — по-новому, старое как было".
- Старая реализация удаляется полностью: функции, типы, стили, тесты, неиспользуемые импорты, feature-флаги, которые были нужны только для старого пути. Ничего не остаётся "на всякий случай" или закомментированным.
- Если что-то похожее на старый код нужно оставить — переносится в git-историю (там уже есть), не в закомментированный блок в рабочем файле.
- `TODO` в коде разрешён только с привязкой к issue/тикету и не переживает больше одного PR-цикла без решения — голый `// TODO: fix later` без контекста удаляется на ревью.
- Временное сосуществование двух подходов (например, миграция экрана частями) допустимо **только** если это явно объявлено в PR-описании, ограничено по времени и зафиксировано в `instructions.md` как временное — иначе ревьюер обязан потребовать полной замены.

**Проверка на ревью:** если дифф добавляет новый код и оставляет нетронутым старый код с тем же назначением — PR возвращается автору, пока старое не убрано.

## 4. Логирование

Цель: по логам можно восстановить, что произошло и где именно сломалось, не переспрашивая пользователя и не гадая по коду.

### 4.1 Единая точка

Весь фронтенд логирует только через `shared/lib/logger.ts`. Сырой `console.log`/`console.error` в коде фичи — запрещён (кроме самого `logger.ts`, где это реализация).

```ts
// shared/lib/logger.ts — контракт (реализуется в Stage 0)
type LogLevel = "debug" | "info" | "warn" | "error";

interface LogPayload {
  scope: string;              // "chat.composer", "tariffs.payment", "history.delete"
  event: string;               // "message_send_started", "payment_failed", "thread_deleted"
  data?: Record<string, unknown>;
  traceId?: string;            // тот же id, что уходит в X-Trace-Id к бэку
}

logger.debug(payload: LogPayload): void;   // только dev, в проде no-op
logger.info(payload: LogPayload): void;    // dev: консоль; prod: не отправляется, но остаётся в буфере на случай warn/error рядом
logger.warn(payload: LogPayload): void;    // dev: консоль; prod: отправляется в /logs/client
logger.error(payload: LogPayload & { error: unknown }): void; // dev: консоль; prod: отправляется в /logs/client всегда
```

### 4.2 Что логируется автоматически (не руками в каждом месте)

HTTP-клиент (`shared/lib/api.ts`) сам логирует **каждый** запрос: старт, успех, ошибку — с `scope: "api"`, `event: "request_started"/"request_succeeded"/"request_failed"`, длительностью и `traceId`. Разработчик фичи **не должен** руками логировать факт похода в сеть — это уже покрыто на уровне клиента. Руками логируются только доменные события (см. 4.3).

### 4.3 Что логируется руками, по месту

- Значимые действия пользователя, особенно необратимые или платные: отправка сообщения в новый тред, покупка тарифа, оплата, удаление треда/тарифа, сохранение промпта.
- Переходы состояний, которые не тривиальны: смена статуса треда (`queued→processing→done/error`), включение/выключение режима "подготовить документ".
- Открытие/закрытие платёжной и confirm-модалок (это точки, где чаще всего нужно будет разбираться "нажал ли пользователь купить").
- Все `catch`-блоки: **ни одного пустого `catch`**. Минимум — `logger.error` с исходной ошибкой. Проглатывать ошибку молча — нельзя никогда, даже если UI и так покажет тост.
- Границы `ErrorBoundary` — логируют `error` с полным stack на уровне `error` при каждом падении поддерева.

### 4.4 trace id

`traceId` генерируется на фронте один раз на пользовательское действие (например, на отправку сообщения) и передаётся сквозь весь запрос — тот же id уходит в заголовок `X-Trace-Id` к бэку (обязателен по контракту, backend-roadmap.md:44). Это значит: по одному id можно найти всю цепочку событий и на фронте, и в логах Go/Python. Не создавать новый id на каждый внутренний вызов одной операции.

### 4.5 Что никогда не логировать

- Полный текст пользовательских сообщений/документов в прод-логи (только в dev-консоли, и то по необходимости).
- Данные оплаты (даже мок).
- PII сверх того, что уже есть в `session_id`.

## 5. Naming conventions

- Компоненты: `PascalCase.tsx`, один компонент — один файл, имя файла = имя компонента.
- Хуки: `useXxx.ts`, всегда возвращают либо объект с именованными полями (если > 2 значений), либо кортеж как встроенные хуки (если ровно пара `[value, setter]`-семантики).
- Типы/интерфейсы: `PascalCase`, лежат в `types.ts` рядом с фичей либо в `shared/types`, если используются более чем в одной фиче.
- Булевы переменные/пропсы: префикс `is`/`has`/`can`/`should` (`isLoading`, `hasDiscount`, `canDelete`).
- Обработчики-пропсы: `onXxx` (`onSubmit`), внутренние обработчики-функции: `handleXxx`.
- Константы уровня модуля: `UPPER_SNAKE_CASE` только для реальных констант (лимиты, ключи), не для обычных переменных.
- Файлы моков: `*.mocks.ts`, не путать с реальными типами API — импортировать типы из `types.ts`, а не дублировать inline.

## 6. TypeScript

- `strict: true` на уровне `tsconfig`, без исключений на фичу.
- `any` запрещён без комментария в строку выше, объясняющего, почему по-другому нельзя (например, сторонняя нетипизированная библиотека).
- Публичные сигнатуры хуков и функций-утилит — с явными типами возврата. Локальные переменные — вывод типов, руками не дублировать.
- Состояния загрузки — через discriminated union, а не набор булевых флагов:

```ts
// плохо: isLoading, isError, data — три независимых поля, которые могут противоречить друг другу
// хорошо:
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: unknown };
```

(TanStack Query это уже даёт из коробки через `status` — руками переизобретать не нужно, пункт актуален там, где состояние всё же пишется вручную.)

## 7. Стили

- Все значения — из `DESIGN_SYSTEM.md` / `shared/styles/tokens.css` через Tailwind-классы, замаппленные на CSS-переменные. Сырой hex, `px`-значение "на глаз" или инлайновый `style={{ color: ... }}` в JSX фичи — запрещены (см. DESIGN_SYSTEM.md).
- Кастомный CSS (не Tailwind-утилиты) — только для того, что утилитами не выразить (кастомные анимации, сложные псевдоселекторы). Живёт рядом с компонентом как `Component.module.css`, не в глобальном файле.
- Тёмная тема — не отдельная ветка стилей, а те же классы поверх других значений CSS-переменных (`[data-theme="dark"]`), как уже сделано в токенах прототипа. Компонент не должен знать, светлая тема сейчас или тёмная.

## 8. Обработка ошибок

- Сетевые ошибки — состояние `error` из TanStack Query → единый `Toast`/inline-сообщение, никогда не проглатываются молча.
- Каждый route оборачивается своим `ErrorBoundary` (не один глобальный на всё приложение) — падение одной страницы не должно рушить навигацию и уже открытые данные на других.
- Ни одного пустого `catch {}` — см. §4.3.
- Сообщения пользователю — по каталогу ошибок из `backend-roadmap.md` §5.2 (один сценарий бэка = одна понятная фраза на фронте, а не сырой текст ошибки API).

## 9. Git / PR

- Conventional commits: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`.
- Один PR = одна стадия или подстадия из `PLAN.md` (например, "Stage 1: Chat — composer"). Не смешивать рефактор общего компонента с новой фичей в одном PR.
- В описании PR — ссылка на пункт `PLAN.md`, который закрывается, и явное подтверждение: "старый код по этой логике удалён" (или "не применимо, кода раньше не было").
- Definition of Done из `PLAN.md` §11 — чек-лист в шаблоне PR, не в голове.

## 10. Тестирование

- Юнит-тесты — на бизнес-логику (расчёт цены, склонения, фильтры, валидаторы), не на JSX-разметку.
- RTL-тесты — на пользовательские сценарии страницы ("покупка тарифа", "отправка сообщения с вложением"), через `role`/`label`, не через `data-testid` россыпью и не через CSS-классы.
- Тестируется поведение, а не реализация: если тест ломается от переименования внутренней переменной без изменения поведения — тест написан неправильно.

## 11. Чеклист ревью (кратко, перед approve)

- [ ] Нет старого кода рядом с новым по тому же назначению (§3)
- [ ] Значимые действия/ошибки залогированы через `logger`, ни одного пустого `catch` (§4)
- [ ] Нет сырых цветов/размеров мимо токенов (§7, `DESIGN_SYSTEM.md`)
- [ ] Нет `any` без обоснования, состояния загрузки — не россыпь булевых флагов (§6)
- [ ] PR = одна стадия из `PLAN.md`, Definition of Done отмечен
- [ ] Если менялся подход/паттерн — `instructions.md` обновлён
