# Zan — Техническое задание на бэкенд v2

Обновлено на основе интерактивного дизайн-прототипа (`Zan.dc.html`). Документ заменяет `zan-backend-tz.md` (v1) — ниже перечислены ключевые изменения, затем полная актуальная спецификация.

---

## 0. Что изменилось относительно v1

1. **Модель тарифов полностью пересобрана.** Вместо простых "пакетов из N консультаций" — двухуровневая модель: **Услуги** (Q&A и Документ, каждая со своей базовой ценой) → **Тарифы/бандлы**, собранные из услуг с произвольным количеством и скидкой. Плюс режим "свой набор" (custom) без готового тарифа.
2. **Баланс теперь по типам услуг**, а не общий счётчик консультаций: отдельно остаток по Q&A, отдельно по документам.
3. **Возврат на баланс при ошибке** — если запрос не удалось обработать (`status=error`), списанная услуга возвращается пользователю, а не оформляется денежный возврат.
4. **Удаление обращения** — в истории есть безвозвратное удаление треда (с подтверждением), не только отмена.
5. **Точные названия статусов**: `queued`, `processing`, `clarify`, `done`, `error`, `canceled`.
6. **В настройках 3 вкладки в одном экране**: Промпты, Тарифы (управление услугами и бандлами), Аналитика — а не отдельные разделы.
7. **Аналитика** дополнена метрикой удовлетворённости (% лайков от всех оценённых ответов).
8. **Онбординг** — 3 шага, показывается один раз при первом входе (управляется флагом на пользователе).
9. Уточнены точные лимиты и формулы расчёта цены (см. §4.2).

---

## 1. Обзор системы

Бэкенд обслуживает мобильный/веб-клиент юридического ассистента:
- Диалоговые консультации (Q&A) и работа с документами через два LLM-агента с настраиваемыми системными промптами
- Распознавание голосовых сообщений в текст (STT)
- Биллинг по модели "услуга за тред": первое сообщение в новом треде расходует 1 единицу услуги "Q&A" или "Документ" с баланса пользователя (либо оплачивается напрямую, если баланса нет); уточнения внутри треда бесплатны
- Гибкая система тарифов: услуги с базовой ценой + собираемые из них бандлы со скидкой, плюс "свой набор"
- Административный блок: промпты агентов, услуги/тарифы, аналитика (временно без ролевой проверки, с заделом под неё)

## 4. Ключевая бизнес-логика

### 4.1 Услуги и тарифы
- `Service` — источник истины по базовой цене. Изменение цены услуги в админке **не** пересчитывает уже оформленные `Payment`, но сразу меняет расчёт для новых `checkout`.
- `Tariff` — фиксированный набор `{service_id, qty}` + скидка. Цена всегда считается на лету по формуле из §2.3 (не хранится статично), чтобы не расходиться при изменении цены услуги.
- Режим "свой набор" (custom): пользователь указывает `qty` по каждой услуге (лимит **1–20** на услугу, как в прототипе), скидка не применяется — это эквивалент `kind=custom` в `/payments/checkout`.

### 4.2 Начисление и списание баланса
1. Успешный `payments/{id}/confirm` для `kind IN (tariff, custom)` → для каждого `{service_id, qty}` делает `UPSERT UserCredit(user_id, service_id) SET quantity = quantity + qty`.
2. При создании нового треда (`POST /threads`) с `service_id`:
   - Если `UserCredit(user, service_id).quantity > 0` → списать 1 единицу сразу (`quantity -= 1`), `thread.is_paid = true`, обработка стартует немедленно, отдельный `Payment` не создаётся (или создаётся с `provider=balance`, `amount=0`, для полноты истории — на усмотрение реализации, но лог обязателен).
   - Если баланс = 0 → тред создаётся с `is_paid=false`, клиент вызывает `checkout {kind: single_service, items: [{service_id, qty:1}], thread_id}` → после `confirm` начисляется 1 единица и сразу списывается по логике выше (фактически — сквозная операция "купил и тут же потратил").
3. **Возврат при ошибке**: если обработка треда завершилась `status=error`, списанная единица возвращается — `UserCredit.quantity += 1` для `thread.service_id`. Отражено в UI как "оплата возвращена на баланс".

### 4.3 Бесплатные уточнения внутри треда
- После `is_paid=true` выставляется `free_until = paid_at + N часов` (значение — конфигурируемый параметр, по умолчанию предлагается 72 часа, подтвердить с продуктом).
- Пока `now() < free_until` и `status != canceled`, `POST /threads/{id}/messages` не требует оплаты и не списывает баланс.
- По истечении `free_until` тред помечается `closed_at`; новое сообщение по теме — новый тред (новое списание).

### 4.4 Генерация документа
- Доступна из любого треда (`type` треда как такового больше нет — есть `service_id`, которым тред был открыт; генерация документа — всегда отдельная операция, платная отдельно от типа треда).
- `POST /threads/{id}/generate-document` → внутри использует ту же логику списания/оплаты, что и §4.2, но с `service_id="doc"`, привязывая `Payment.thread_id` к текущему треду.
- Результат — `FileAttachment(purpose=generated_output, output_formats=["pdf","docx"])`.
- Раздел "Редактировать" (`editDoc` в интерфейсе) на этом этапе — **вне скоупа бэкенда** (см. §6), пока не уточнено, редактирование прямо в браузере или через повторную генерацию по инструкции в чате.

### 4.5 Удаление и заголовок/превью треда
- `title` генерируется из первого сообщения пользователя (обрезка до ~60 символов) в момент создания треда.
- `preview_text` обновляется после каждого нового сообщения ассистента: либо короткая выжимка ответа, либо системный текст статуса (`"Ассистент готовит ответ…"` для `processing`, `"Запрос в очереди…"` для `queued` и т.п.) — конкретные тексты см. в переводах прототипа (`RU`/`KZ` словари).
- `message_count` увеличивается на 1 при каждой новой записи `Message`.
- `DELETE /threads/{id}` — soft delete (`deleted_at`), из списков (`GET /threads`) исключается сразу; окончательная физическая очистка — по регламенту хранения данных (см. §5).

### 4.6 Вызов LLM-агента
- Выбор промпта: `thread.service_id == "qa"` → `AgentPrompt(qa)`; вызов `generate-document` → `AgentPrompt(document)`.
- Промпт подтягивается из БД на каждый вызов (без долгого кеша), чтобы правки в `/admin/prompts` применялись сразу.
- В контекст — вся история сообщений треда + распознанное содержимое прикреплённых файлов.
- Ожидаемый структурированный ответ агента:
  ```json
  {
    "answer_text": "...",
    "sources": [{"ref": "...", "quote": "..."}],
    "findings": [{"title": "...", "body": "..."}],
    "needs_clarification": false
  }
  ```
  `needs_clarification: true` → статус треда → `clarify`.

### 4.7 Голосовой ввод
- `POST /voice/transcribe` — синхронный вызов STT, возвращает текст **до** отправки сообщения. Обработка аудио как есть ассистентом — вне скоупа.

## 5. Нефункциональные требования

- **Язык контента**: `ru`/`kz`, хранится на пользователе, передаётся агенту в системном контексте.
- **Тема** (`light`/`dark`) — хранится на пользователе для синхронизации между устройствами (в прототипе это чисто клиентский стейт, но раз есть профиль — логично сохранять).
- **Хранение файлов**: S3-совместимое хранилище, подписанные URL с ограниченным сроком жизни.
- **Безопасность**: access/refresh токены, rate limiting на `/auth/otp/send`, антивирус на загружаемые файлы, ограничение размера/типа.
- **Идемпотентность**: `POST /payments/{id}/confirm` безопасен к повторному вызову (не начислять баланс дважды).
- **Логирование**: `processing_time_ms` на каждое сообщение — источник для `/admin/analytics/overview`.
- **Персональные данные**: юридические консультации — чувствительная категория, шифрование текстов на уровне БД/хранилища, политика удаления по запросу пользователя (согласуется с реальным `DELETE /threads/{id}`, но также должен быть полный "забыть меня" на уровне аккаунта).
- **Расширяемость под реальный платёжный провайдер**: поле `provider` в `Payment` уже абстрагировано под замену `mock` → `kaspi`/`epay`/`halyk` без изменения модели данных.

## 6. Вне скоупа текущего этапа (явно)

- Реальная интеграция платёжного шлюза
- Проверка `role=admin` на роутах `/admin/*` (поле есть, middleware не подключён)
- Инлайн-редактирование сгенерированного документа (кнопка "Редактировать" в интерфейсе — фронтенд-заглушка на этом этапе)
- OCR прикреплённых сканов — можно закрыть базовым решением, но не обязателен production-grade

## 7. Открытые вопросы к продукту (уточнить до старта разработки)

1. Точное значение `free_until` — предложено 72 часа, нужно подтвердить.
2. Нужен ли возврат/докупка в закрытый тред (`reopen`), или всегда новый тред.
3. STT-провайдер — внешний API (Google/Yandex SpeechKit) или self-hosted (Whisper)?
4. Способ идентификации — телефон + OTP, или также email?
5. Формат текстов `preview_text` для статусов (`queued`/`processing`/`error`/`canceled`) — фиксированные системные фразы или динамическая выжимка от агента? В прототипе это захардкоженный текст — нужно решить, кто их генерирует в проде.
