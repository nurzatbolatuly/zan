# zan — AI-ассистент по законодательству РК

Веб-сервис, где пользователь описывает правовую проблему, а конвейер из ИИ-агентов (под
управлением оркестратора) находит применимые нормы права РК, проверяет их, объясняет
человеческим языком и по запросу генерирует шаблон документа.

- Полный план по этапам: [`PLAN.md`](./PLAN.md)
- Инструкция для разработки (стек, конвенции, структура): [`INSTRUCTIONS.md`](./INSTRUCTIONS.md)

## Статус

- **Этап 0** — фундамент репозитория (тулинг, структура воркспейсов, CI). Готово.
- **Этап 1** — ingestion c adilet.zan.kz (краулер, парсер, эмбеддинги, схема БД, синхронизация)
  был реализован и проверен на реальных данных, но архитектурное решение об офлайн-индексе дважды
  пересматривалось (см. `PLAN.md` §2 и `INSTRUCTIONS.md` §9 — сначала переход на локальный
  retrieval-корпус 2026-08-27, затем откат обратно на live-поиск 2026-08-28, т.к. ресинк корпуса
  требовал прямого сетевого доступа к adilet.zan.kz, которого не было из части инфраструктуры) —
  сейчас `ingestion/` не скрапит и не индексирует, пакет оставлен только как владелец миграций
  общей схемы БД (`requests`/`request_steps`/`documents`).
- **Этап 2** — backend-скелет и оркестратор (NestJS + BullMQ/Redis): `POST /requests` →
  очередь → оркестратор прогоняет 4 агента (пока заглушки) → статус и результат каждого
  шага видны через `GET /requests/:id`. Проверено вживую от HTTP-запроса до записи в БД
  (см. `backend/README.md`). Реальные агенты — Этапы 3–6.
- **Этап 3** — Агент 1 (поиск): живьём ищет применимые нормы через LLM со встроенным `web_search`,
  ограниченным adilet.zan.kz/zan.gov.kz, — не по памяти модели, локального индекса нет (см.
  `INSTRUCTIONS.md` §9 — офлайн-индекс пробовали 2026-08-27, откатили 2026-08-28: ресинк корпуса
  требовал сетевого доступа к adilet.zan.kz, которого не было из части инфраструктуры). Готово,
  см. `backend/src/agents/search/`.
- **Этап 4** — Агент 2 (верификация): независимая LLM-перепроверка со своим `web_search` —
  реально открывает каждую статью, упомянутую в черновике Агента 1, и сверяет номер, формулировку
  и статус (действующая/утратила силу/изменена). Возвращает список расхождений; они не блокируют
  пайплайн и не запускают переспрос Агента 1 (см. `INSTRUCTIONS.md` §9.5 — цикл переспроса убран
  2026-08-28), а идут дальше как есть вместе с исправленным ответом. Готово, см.
  `backend/src/agents/verification/`.
- **Этап 5** — Агент 3 (юридический редактор): пересобирает проверенный ответ Агента 2 в
  тёплом, человечном тоне живого юриста (не ИИ-ассистента) по структуре "суть вопроса → что
  говорит закон → что это значит → что можно сделать". Готово, см. `backend/src/agents/editor/`.
- **Этап 6** — Агент 4 (генератор документов): LLM генерирует только содержание документа
  (заголовок, шапку, пункты) строго валидным JSON, опираясь на проверенный ответ Агента 2;
  форматирование по формальным требованиям РК (A4, Times New Roman 14, шапка справа сверху,
  нумерация пунктов) реализовано программно в шаблонизаторе (пакет `docx`), а не текстовой
  просьбой к модели — формат гарантирован независимо от того, что вернула LLM. Результат —
  готовый DOCX-файл (base64 в `content`). Готово, см. `backend/src/agents/document/`.

  **Этап 15 (2026-09-12, см. `INSTRUCTIONS.md` §9.10):** Агенты 1–3 (Этапы 3–5 выше — search,
  verification, editor) слиты в одного — Агент "answer" (`backend/src/agents/answer/`): один
  вызов LLM с `web_search` вместо трёх последовательных, латентность и честность стриминга
  (промежуточный черновик сбивал пользователя с толку при показе в реальном времени, см. §9.9).
  Агент 4 (document) остался отдельным шагом.

- **Этап 7** — frontend (Next.js 16 App Router + TypeScript + Tailwind CSS 4): экран запроса
  → экран статуса обработки (видно, какой агент сейчас работает, с текстом ошибки при сбое)
  → экран результата (markdown-ответ Агента "answer" с кликабельными ссылками на статьи закона,
  скачивание сгенерированного DOCX прямо в браузере). Проверено вживую: полный цикл от
  отправки формы через реальный backend/очередь/агентов до отображения статуса, и отдельно —
  рендер финального ответа и реальное, открывающееся скачивание документа. Готово, см.
  `frontend/README.md`.

Весь MVP-путь (Этапы 0–7) пройден: пользователь отправляет вопрос и получает структурированный
ответ со ссылками на законодательство РК и, по запросу, готовый документ.

- **Этап 8** — безопасность: rate limiting (`@nestjs/throttler`, отдельный жёсткий лимит на
  `POST /requests`), обрезка/валидация пользовательского ввода, защита от prompt injection
  (пользовательский текст размечен как данные в промптах обоих агентов, см.
  `shared/src/security/userContent.ts`), безопасные HTTP-заголовки (`helmet`), CORS с
  конкретным origin вместо `*`, параметризованные SQL-запросы (без изменений — уже были),
  и разграничение доступа: анонимная cookie-сессия — `GET /requests/:id` отдаёт чужой запрос
  тем же 404, что и несуществующий id. Проверено вживую (curl): заголовки, cookie, rate
  limit, отказ в доступе к чужому/анонимному запросу. Готово, см. `backend/README.md`.
- **Этап 9** — наблюдаемость: структурированные (pino/JSON) логи на каждый HTTP-запрос и шаг
  пайплайна с PII-свободной сводкой (без текста вопроса/ответа — только счётчики и
  длительности) и `request_id`; Prometheus-эндпоинт `GET /metrics` — длительность каждого шага
  пайплайна и HTTP-запроса, количество замечаний Агента 2 при перепроверке, счётчик ошибок
  шагов пайплайна. Централизованный сборщик логов/алерты — вне кода приложения, настраиваются
  при деплое (Этап 11). Проверено вживую: заголовки/метрики/логи на реальном запуске backend.
  Готово, см. `backend/README.md`.
- **Этап 13** (бэклог) — реализовано всё, кроме дополнительных агентов (п. 3 — намеренно не
  делали, риск-агент/агент-переводчик не нужны на этом этапе):
  - **Личный кабинет и история обращений** — без регистрации, на основе анонимной
    cookie-сессии из Этапа 8 (`GET /requests`, `frontend` `/[locale]/history`).
  - **Многоходовой диалог** — ровно один раунд уточняющего вопроса перед Агентом 1 (не
    полноценный чат): оркестратор решает через LLM, достаточно ли вопроса, при необходимости
    останавливает пайплайн (статус `needs_clarification`) и ждёт ответ
    (`POST /requests/:id/clarification`). Не отдельный агент — вспомогательная проверка внутри
    оркестратора, fail-open при сбое LLM.
  - **Поддержка нескольких языков интерфейса** — русский и казахский
    (`frontend/src/i18n/`, маршруты `/[locale]/...`). Локализована только статическая обвязка
    интерфейса; ответ ассистента и документы остаются на русском (перевод юридического
    контента — отдельная, более рискованная задача, соответствует решению не добавлять
    агента-переводчика).
  - **Аналитика** — `GET /analytics/summary` + простой дашборд (`/[locale]/analytics`): запросы
    по статусу, среднее время обработки. ("Частые законы" и доля verified/rejected опирались
    на структуру статей старого индексного Агента 2 — убраны при пересмотре архитектуры,
    см. `PLAN.md` §2.)

  Проверено вживую (curl + браузер): история отдаёт только запросы своей сессии, аналитика
  агрегирует реальные данные БД, переключение ru/kk работает во всём интерфейсе с сохранением
  локали в URL. Готово, см. `backend/README.md` и `frontend/README.md`.

Дальше по плану — Этапы 10–12 (тестирование, деплой, юридическая проверка перед запуском).

## Структура

Монорепозиторий, npm workspaces:

- `frontend/` — веб-интерфейс (Next.js) — Этап 7, см. `frontend/README.md`
- `backend/` — API Gateway, оркестратор, 2 реальных агента — "answer" и "document" (NestJS) —
  Этапы 2–6, 15, см. `backend/README.md`
- `ingestion/` — только владелец миграций общей схемы БД (`requests`/`request_steps`/`documents`);
  ранее также синкал локальный корпус законодательства (`law_documents`/`law_articles`/
  `law_chunks`) — этот код и таблицы убраны 2026-08-28, см. §"Поиск по законодательству" ниже
- `shared/` — общие типы, утилиты, логирование — используется с Этапа 1

### Поиск по законодательству (live, без локального индекса)

Агент "answer" ищет применимые нормы права РК ЖИВЬЁМ, через LLM со встроенным `web_search`
(OpenAI Responses API), ограниченным доменами adilet.zan.kz и zan.gov.kz — на каждый запрос
пользователя, без локального индекса/корпуса, сам себя перепроверяет и сразу форматирует ответ за
один вызов (см. `INSTRUCTIONS.md` §9.10 — до 2026-09-12 это были три последовательных вызова:
search → verification → editor).

**История решения (см. `INSTRUCTIONS.md` §9 — полная хронология):** 2026-08-27 живой поиск на
каждый запрос был заменён офлайн-индексом (`ingestion/src/sync.ts` скачивал и эмбеддил курируемый
список документов в `law_chunks`/pgvector) — решало латентность одного вызова (десятки-сотни мс
вместо 15-100+с), но требовало периодического ресинка корпуса напрямую с adilet.zan.kz.
2026-08-28 решение отменено: доступа к adilet.zan.kz нет ни у разработчика, ни у прода — весь этот
код и схема БД под него удалены. 2026-09-12 latency решается не отказом от live-поиска, а
чейнингом Responses API диалога между шагами (§9.8) и слиянием трёх последовательных LLM-вызовов
в один (§9.10).

**Практическое следствие:** латентность одного запроса определяется ОДНИМ живым LLM-вызовом с
`web_search` (плюс отдельный шаг генерации документа, если запрошен) — вместо трёх
последовательных вызовов до 2026-09-12. Если латентность снова станет проблемой, следующий шаг —
не переизобретать локальный индекс (синк любого локального корпуса требует сетевого доступа к
adilet.zan.kz, который недоступен ни у разработчика, ни у прода, см. §9.6/9.8), а сначала снять
реальные метрики (`zan_llm_request_duration_ms{operation="responses"}`) и решать оттуда.

## Быстрый старт

```bash
npm install
npm run lint
npm run format:check
npm run typecheck
npm run test
```

Скопировать `.env.example` в `.env` и заполнить переменные окружения. Проект работает на прод
Supabase Postgres (`DATABASE_URL` в `.env` указывает на `db.<project>.supabase.co`, не на
локальный docker-compose postgres — см. `INSTRUCTIONS.md` §7.1), локальный `docker-compose up -d
postgres redis` нужен опционально только если хочешь поднять окружение полностью локально; схема
БД накатывается миграциями `npm run migrate -w ingestion` — либо, если удобнее вставить руками в
Supabase Dashboard → SQL Editor, тем же SQL из `ingestion/supabase-migrations.sql` (см.
`INSTRUCTIONS.md` §7.1, там же правило — держать этот файл в синке при добавлении новых миграций).
Никакого отдельного наполнения корпуса законодательства больше не требуется — Агент "answer" ищет
нормы живьём при каждом запросе (см. §"Поиск по законодательству" выше).
