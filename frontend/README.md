# @zan/frontend

Адаптивный минималистичный веб-интерфейс (Next.js 16 App Router + TypeScript + Tailwind CSS 4).

## Статус (Этап 7)

Законченный пользовательский путь от запроса до результата, готово:

- `src/app/[locale]/page.tsx` + `src/components/RequestForm.tsx` — экран запроса: описание
  проблемы (валидация 10–4000 символов, синхронизирована с `CreateRequestDto` backend'а),
  чекбокс «приложить документ» + тип документа, отправка `POST /requests`. (Путь под `[locale]/`
  — см. Этап 13 ниже, i18n; на момент Этапа 7 лежал прямо в `src/app/page.tsx`.) Тот же чекбокс —
  и в композере продолжения чата (`RequestStatusView.tsx`), не только на первом сообщении (Этап
  17, §9.13; между этим и Этапом 7 недолго пробовали автоопределение по тексту без чекбокса вообще
  — Этап 16, §9.12 — откатили в тот же день).
- `src/app/[locale]/requests/[id]/page.tsx` + `src/components/RequestStatusView.tsx` — экран
  статуса: живое обновление через WS (Этап 14, `lib/api.ts:requestEventsUrl`) вместо поллинга —
  ответ Агента "answer" печатается по мере генерации, а не появляется целиком в конце; поллинг
  `GET /requests/:id` каждые 2с остаётся фолбэком, если WS не подключился/оборвался раньше
  paused-статуса (`completed`/`failed`/`needs_clarification`, см. Этап 13).
- `src/components/MarkdownAnswer.tsx` — рендерит `resultSummary` от Агента "answer" (markdown с
  заголовками и кликабельными ссылками на статьи закона) через `react-markdown` +
  `@tailwindcss/typography`.
- `src/components/DocumentDownloadButton.tsx` — декодирует `document.content` (base64 DOCX от
  Агента "document") в `Blob` и скачивает файл прямо в браузере, без отдельного
  backend-эндпоинта.
- Персистентный дисклеймер в футере (`src/app/layout.tsx`) — см. INSTRUCTIONS.md, раздел
  "Границы ответственности сервиса".

Проверено вживую: полный цикл форма → создание запроса → поллинг → отображение ошибки шага
(реальный вызов OpenAI API с невалидным ключом) → и отдельно (с тестовыми данными в БД) —
рендер markdown-ответа со ссылками и скачивание реального, открывающегося DOCX-файла.

## Этап 13 (бэклог, кроме доп. агентов) — личный кабинет, уточнение, i18n, аналитика

- **i18n (`src/i18n/`)** — маршруты перенесены под `app/[locale]/...` (`ru`/`kk`, редирект `/`
  → `/ru`). Локализована только статическая обвязка интерфейса (лейблы, заголовки, кнопки);
  сам ответ ассистента и генерируемые документы остаются на русском независимо от локали —
  перевод юридического контента требует агента-переводчика, который в этом этапе сознательно
  не реализован (см. PLAN.md, Этап 13, п. 3). Словарь (`i18n/dictionary.ts`,
  `i18n/dictionaries/{ru,kk}.ts`) прокидывается клиентским компонентам через
  `DictionaryProvider`/`useDictionary()`/`useLocale()` — сам словарь вычисляется на клиенте из
  `locale` (строки), а не передаётся как проп из серверного `[locale]/layout.tsx`: часть строк
  словаря — функции (`minLengthHint`, `download`), а функции нельзя передать как проп из React
  Server Component в клиентский компонент.
- **Личный кабинет (`src/components/HistoryView.tsx`, `/[locale]/history`)** — история
  обращений на основе уже существующей анонимной cookie-сессии (Этап 8), без регистрации:
  `GET /requests` отдаёт только запросы текущей сессии.
- **Уточняющий вопрос (`src/components/ClarificationForm.tsx`)** — при статусе запроса
  `needs_clarification` `RequestStatusView` показывает вопрос и форму ответа
  (`POST /requests/:id/clarification`); поллинг статуса приостанавливается на время ожидания
  ответа и возобновляется вручную после отправки.
- **Аналитика (`src/components/AnalyticsView.tsx`, `/[locale]/analytics`)** — простой дашборд
  над `GET /analytics/summary`: запросы по статусу, среднее время обработки. ("Топ законов" и
  доля verified/rejected убраны при пересмотре архитектуры, см. `../PLAN.md` §2.) Цвета
  статусов — из фиксированной статусной палитры скилла dataviz (good/warning/critical), не
  тематизируются; см. комментарий в файле.

Проверено вживую в браузере: переключение ru/kk (включая редирект `/` и перевод всей обвязки),
отправка запроса на казахском с сохранением локали в URL результата (`/kk/requests/:id`),
история обращений подтягивает именно созданный в этой сессии запрос, дашборд аналитики
отображает реальные агрегаты из БД (статусы, среднее время обработки).

## Архитектурные решения

- **Типы API-контракта не переиспользуются из `backend/`, а объявлены заново в
  `src/lib/types.ts`** — backend отдаёт JSON, где даты сериализуются в строки (не `Date`), а
  не все поля backend-типов (`input`/`output` шага) вообще нужны фронтенду. Копия по фактической
  форме HTTP-ответа честнее, чем переиспользование internal-типа с несовпадающей семантикой.
- **Относительные импорты — без расширения `.js`.** `tsconfig.json` использует
  `moduleResolution: "bundler"` (не `NodeNext`, как в остальных пакетах монорепо) — так надо
  для Next.js; в этом режиме `tsc` и бандлер Next по-разному трактуют явное расширение `.js` у
  `.tsx`-файла, поэтому именно здесь (в отличие от backend/ingestion/shared) импорты
  пишутся без расширения.
- **Единый `.env` в корне монорепозитория** подхватывается через `dotenv` в начале
  `next.config.mjs` (тот же приём, что в `backend/src/config.ts`) — Next.js по умолчанию
  читает только `frontend/.env*`.
- Backend требует `FRONTEND_ORIGIN` для CORS (см. `backend/src/main.ts`) — по умолчанию
  `http://localhost:3001`, что совпадает с портом фронтенда ниже.

## Локальный запуск

```bash
npm run dev -w frontend   # http://localhost:3001 (backend ожидается на :3000)
```

## Типизация

```bash
npm run typecheck -w frontend
npm run build -w frontend   # next build — ловит больше ошибок, чем один только tsc
```
