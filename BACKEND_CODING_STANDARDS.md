# Zan Backend — стандарты разработки

Обязательны для всех, кто пишет `backend/` (Go) и `helper/` (Python). Это не пожелания — это критерии ревью: PR, который их нарушает, не мержится, пока не поправлен. Зеркалит по духу `FRONT_CODING_STANDARDS.md` (тот же принцип "один стандарт на команду, не изобретаем заново по ходу"), но конкретика — под Go/Python/gRPC, а не под TS/React.

Смежные документы:

- `BACKEND_PLAN.md` — что и в каком порядке строим (стадии, архитектурные решения верхнего уровня, контракт Go↔Python)
- `backend-roadmap.md` (= ТЗ v4) — источник правды по бизнес-логике, каталогу ошибок (§5), логированию (§6)
- `BACKEND_LOG.md` — живой журнал (заводится в Stage 0, см. `BACKEND_PLAN.md §8`) — обновляется вместе с этим файлом при любом отходе от стандарта, тот же принцип, что у фронтового `instructions.md`

## 1. Архитектурные слои и правила зависимостей

Оба сервиса — слои-адаптеры вокруг доменного ядра (порты и адаптеры / "чистая архитектура" в облегчённом виде — без фреймворка поверх, просто дисциплина импортов). Направление зависимостей — всегда внутрь, к домену; домен не знает о транспорте (HTTP/gRPC), фреймворке (`gin`/`grpc.aio`) или драйвере БД.

### 1.1 Go (`backend/`)

```
cmd/api/              → composition root: main(), сборка зависимостей руками (без DI-фреймворка)
internal/httpserver/  → тонкий: gin-хендлеры — парсинг запроса, вызов service, маппинг ошибки → HTTP-статус
internal/service/     → бизнес-логика (use cases), определяет интерфейсы репозиториев/клиентов, которые ей нужны
internal/domain/      → чистые типы (Thread, Session, Money...), НЕ импортирует gin/pgx/grpc — ноль внешних фреймворков
internal/repo/        → реализация репозиториев поверх pgx напрямую, имплементит интерфейсы из internal/service
internal/grpcclient/  → клиент к helper/, имплементит интерфейсы вида service.AgentSourceSearcher
internal/agent/       → сборка промпта, HTTP-клиент к LLM-провайдеру, парсинг ответа — имплементит service.Agent
internal/platform/    → logger, storage(s3), resilience (retry/breaker), clock, idgen — инфраструктурные утилиты без бизнес-логики
internal/genproto/    → сгенерировано buf, руками не редактируется, не импортируется напрямую вне grpcclient
```

Жёсткие правила:

- `internal/domain` не импортирует ничего, кроме стандартной библиотеки и других пакетов `domain`. Если типу нужен тег `json:`/`db:` — это нормально (данные же сериализуются), но не тег фреймворка и не встроенный `gin.Context`.
- Интерфейсы, которые нужны бизнес-логике (репозиторий, gRPC-клиент, LLM-клиент), **определяются в `internal/service`** (там, где используются), а не в пакете, который их реализует — это идиоматичный Go ("accept interfaces, return structs"), а не C#/Java-привычка заводить интерфейс рядом с реализацией. Реализация в `internal/repo`/`internal/grpcclient`/`internal/agent` просто удовлетворяет уже объявленный интерфейс.
- `internal/httpserver` не содержит бизнес-правил (проверка баланса, статус-машина треда) — только парсинг входа, вызов метода `service`, маппинг результата/ошибки в HTTP-ответ. Если хендлер разросся до `if`-каскада бизнес-условий — это сигнал, что логика не вынесена в `service`.
- **`internal/repo` — без codegen и без отдельных `.sql`-файлов.** SQL — строковый литерал прямо в методе, который его выполняет (`r.db.QueryRow(ctx, \`SELECT ...\`, args...)`), не в `internal/repo/queries/*.sql` и не в сгенерированном пакете (было — `sqlc`, снято решением пользователя, см. `BACKEND_LOG.md`). Причина: один запрос — одна функция, весь его смысл виден на месте, без прыжка в отдельный файл или сгенерированный код. Из этого правила осознанно исключены: (а) конвертация pgx-типов ⇄ `domain` (`parseUUID`/`toTimestamptz` и т.п., `internal/repo/convert.go`) — это не запрос; (б) маленький приватный тип-строка под `Scan` (`sessionRow`, `paymentRow`...) с методом `toDomain()` — тоже не запрос, а типобезопасная альтернатива десятку позиционных параметров в конвертере. Если один и тот же `SELECT` нужен в двух функциях (например, внутри транзакции и отдельным методом) — текст запроса дублируется в каждой, не выносится в общую функцию, которая сама делает вызов `Query`/`QueryRow`/`Exec`.

### 1.2 Python (`helper/`)

```
app/grpc/servicers/   → тонкий: реализация сгенерированных *Servicer — валидация protobuf-запроса, вызов app/services, маппинг исключения → grpc.StatusCode
app/services/         → бизнес-логика (extraction_service, render_service, rag_service, stt_service)
app/adapters/         → доступ к внешнему миру: db (asyncpg/SQLAlchemy для схемы rag), storage (S3-клиент), providers (обёртка над whisper/tesseract)
app/domain/           → внутренние dataclass/pydantic-модели, НЕ те же классы, что сгенерированы из .proto
app/genproto/         → сгенерировано buf, руками не редактируется
```

- `app/services/*` зависит от **протоколов** (`typing.Protocol` — структурная типизация, аналог Go-интерфейса), объявленных в том же пакете `services`, реализации — в `app/adapters`. Тот же принцип, что в Go: интерфейс живёт там, где используется.
- Protobuf-сгенерированные классы (`app/genproto/...`) не "протекают" дальше `app/grpc/servicers` — конвертация в/из `app/domain`-моделей происходит на границе сервисера, бизнес-логика (`app/services`) работает с доменными моделями, не с wire-типами.

## 2. Состояние — что где хранится и кто им владеет

| Тип состояния | Где | Пример |
|---|---|---|
| Конфигурация процесса (ENV) | Загружается один раз в `main()`/`app startup`, передаётся явно через конструкторы — без глобального синглтона-конфига, который читают откуда попало | DSN БД, `admin-secret`, ключ LLM-провайдера |
| Пул соединений с БД | Один `*pgxpool.Pool` (Go) / один `asyncpg.Pool` (Python) на процесс, создаётся в composition root, пробрасывается в репозитории конструктором | — |
| Request-scoped данные | `context.Context` (Go) / `contextvars` через middleware (Python) | `session_id`, `trace_id`, логгер с уже привязанными полями (`logger.With(...)`) |
| Состояние между запросами внутри процесса | Явная структура с мьютексом/атомиком, поле в composition root — не package-level `var` | rate limiter per-IP, состояние circuit breaker |
| Данные из БД, отданные наружу | Читаются заново на каждый запрос (или в рамках одной транзакции) — не кешируются в памяти процесса "для скорости" без явного TTL/инвалидации | `AgentPrompt` — намеренно без долгого кеша (v2 §4.6: "правки в `/admin/prompts` применяются сразу") |

**Никаких мутабельных package-level переменных** (`var db *pgxpool.Pool` в глобальной области видимости пакета) — весь стейт процесса собирается в `main()`/`cmd/api` и раздаётся явным пробросом через конструкторы. Это Go-эквивалент фронтового правила "один источник истины на сущность, не дублировать серверные данные в сторе для удобства" (`FRONT_CODING_STANDARDS.md §2`) — здесь про "одна точка владения зависимостью, без скрытых глобалов, которые не видно в сигнатуре конструктора".

## 3. Правило "чистая замена, а не наслоение"

Дословно то же правило, что у фронта (`FRONT_CODING_STANDARDS.md §3`), применяется без исключений и здесь:

- Смена подхода (например: REST-контракт Go↔Python → gRPC, как уже произошло на этапе планирования) — в этом же PR удаляется весь старый код по старому подходу: неиспользуемые HTTP-роуты, JSON-схемы контракта, клиентские обёртки. Ничего не остаётся "закомментированным на всякий случай".
- Сгенерированный код (`internal/genproto`, `app/genproto`) — не редактируется руками никогда. Если сгенерированное не устраивает — меняется `.proto` и перегенерируется, а не патчится вывод `buf generate`.
- `TODO` — только с привязкой к issue/тикету, не переживает больше одного PR-цикла без решения.
- Временное сосуществование двух реализаций (например, частичная миграция эндпоинта с mock-агента на реальный LLM) — допустимо **только** если явно объявлено в PR и зафиксировано в `BACKEND_LOG.md` как временное, с условием, когда оно должно исчезнуть.

**Проверка на ревью:** PR, который добавляет новую реализацию рядом со старой того же назначения, возвращается автору.

## 4. Логирование

Цель — та же, что на фронте: по логам восстанавливается вся цепочка одного запроса без переспрашивания пользователя. Контракт формата записи — `backend-roadmap.md §6.1` (JSON, обязательные поля `timestamp/level/service/trace_id/session_id/stage/message/context`), этапы — `§6.2` (14 стадий одного Q&A-запроса).

### 4.1 Единая точка

- Go: один `*slog.Logger` (JSON-хендлер), созданный в `main()`, обогащается request-scoped полями (`trace_id`, `session_id`) через `logger.With(...)` в middleware и кладётся в `context.Context`. Сервисы достают логгер из контекста (`platform.LoggerFromContext(ctx)`), не создают свой.
- Python: `structlog`, та же схема — `bind_contextvars(trace_id=..., session_id=...)` в gRPC-интерцепторе на входе, дальше `structlog.get_logger()` уже видит эти поля во всех записях внутри одного запроса.
- Сырой `fmt.Println`/`print()` в бизнес-коде — запрещён (кроме самого `platform/logger`/`core/logging.py`, где это реализация).

### 4.2 Что логируется автоматически

- Go: middleware `gin` (для HTTP) и client-interceptor `grpcclient` (для вызовов в Python) сами логируют старт/успех/ошибку каждого запроса/вызова — с длительностью и `trace_id`. Хендлер/сервис не логирует руками сам факт "пошёл в сеть".
- Python: серверный gRPC-интерцептор аналогично логирует каждый входящий вызов.

### 4.3 Что логируется руками, по месту — 14 этапов `§6.2`

Каждый переход статус-машины треда, каждый вызов LLM/RAG/extract/render/stt, `credit_refunded`, `response_sent` — отдельный явный вызов логгера **в месте, где это произошло** (`internal/service/threadsvc`, `internal/agent`), не восстанавливается постфактум парсингом других логов. Список — буквально таблица `backend-roadmap.md §6.2`, не сокращается и не пересобирается вольно.

- Ни одного проигнорированного `err != nil` (Go) / `except: pass` (Python) без логирования или явного, задокументированного решения, что ошибка безопасна и её правда можно отбросить (аналог фронтового "ни одного пустого catch", `FRONT_CODING_STANDARDS.md §4.3`).
- `recover()`-middleware (Go) / глобальный exception-handler (Python) — логирует `CRITICAL` с полным стеком при любой панике/необработанном исключении в обработке запроса.

### 4.4 Что никогда не логировать

- Полный текст пользовательских сообщений/сгенерированных документов на `INFO`+ уровне в проде (только `DEBUG`, только в dev — `§6.4` v3).
- Данные оплаты сверх `payment_id`/`amount`.
- PII сверх `session_id` (напоминание — его в системе и так по архитектуре нет, но это касается будущих полей).

## 5. Naming conventions

### 5.1 Go

- Пакеты: короткие, строчные, без подчёркиваний, без "stutter" (`thread.Repository`, не `thread.ThreadRepository`; вызывающий код читается как `thread.Repository`, не дублирует имя пакета).
- Файлы: `snake_case.go`.
- Экспортируемые идентификаторы — `PascalCase` с doc-комментарием, начинающимся с имени идентификатора; неэкспортируемые — `camelCase`.
- Интерфейсы — по поведению: односигнатурные — суффикс `-er` (`Extractor`, `Renderer`), многосигнатурные доменные — существительное по роли (`ThreadRepository`, `Agent`), не `IThreadRepository`/`ThreadRepositoryInterface`.
- Конструкторы — `NewXxx(...)`, возвращают `(*Xxx, error)`, если конструирование может упасть (например, требует пинга БД).
- Ошибки — sentinel-переменные `ErrXxx` на уровне пакета для ожидаемых доменных ошибок (`ErrThreadNotFound`, `ErrInsufficientBalance`), оборачиваются через `fmt.Errorf("...: %w", err)` вверх по стеку, проверяются через `errors.Is`/`errors.As`, не сравнением строк.
- Булевы поля/переменные — префикс `is`/`has`/`can` (`isPaid`, `hasSources`) — та же конвенция, что и на фронте.
- **Константы — `PascalCase`/`camelCase` по тем же правилам, что остальные идентификаторы, НЕ `UPPER_SNAKE_CASE`.** Это отличие от фронтового стандарта (JS/TS-конвенция) — в Go `UPPER_SNAKE_CASE` не идиоматичен, `golangci-lint` (`stylecheck`) будет ругаться.

### 5.2 Python

- PEP 8: функции/переменные — `snake_case`, классы — `PascalCase`, **модульные константы — `UPPER_SNAKE_CASE`** (здесь, в отличие от Go, это и есть идиома).
- Файлы: `snake_case.py`.
- Type hints — обязательны на всех публичных функциях/методах (`mypy --strict` или `pyright` строгий режим в CI, аналог `tsconfig strict` на фронте) — см. §6.2.
- Pydantic-модели (внутренние, не сгенерированные из `.proto`) — суффикс по смыслу (`ExtractedDocument`, не `ExtractedDocumentDto`/`ExtractedDocumentModel` — без обёрточного суффикса, если тип и так однозначен по контексту пакета `app/domain`).

## 6. Языковые правила

### 6.1 Go

- `context.Context` — всегда первый параметр функции, которая может делать I/O; никогда не хранится в структуре как поле (стандартное правило Go, `go vet` частично это ловит, но дисциплина — на ревью).
- Ошибка не игнорируется молча: `_ = someCall()` требует комментария в строке выше, почему это безопасно (тот же принцип, что "`any` без обоснования" на фронте, `FRONT_CODING_STANDARDS.md §6`).
- `panic` — только для программистских ошибок, пойманных на старте (`main()`, невалидный конфиг) или в тестах; в пути обработки запроса — только `recover()` на самом верхнем middleware, как страховка, не как механизм управления потоком.
- Множественные булевы/nullable-поля вместо явного состояния — запрещены, там где состояние взаимоисключающее. Пример — результат вызова агента:

```go
// плохо: три независимых поля, которые могут противоречить друг другу
type AgentResult struct {
    AnswerText  string
    IsError     bool
    IsClarify   bool
}

// хорошо: явный статус
type AgentResultStatus string

const (
    AgentResultDone    AgentResultStatus = "done"
    AgentResultClarify AgentResultStatus = "clarify"
    AgentResultError   AgentResultStatus = "error"
)

type AgentResult struct {
    Status     AgentResultStatus
    AnswerText string // валиден только при Status == AgentResultDone/Clarify
    Err        error  // валиден только при Status == AgentResultError
}
```

- Инструменты CI: `go vet`, `staticcheck`, `golangci-lint` (набор линтеров, включая `errcheck` — не даёт молча проигнорировать `error`) — обязательны на каждый PR, эквивалент ESLint на фронте.

### 6.2 Python

- `mypy --strict` (или `pyright` в строгом режиме) в CI — без `# type: ignore` без комментария, что именно и почему не типизируется (аналог `any` без обоснования).
- `async`/`await` — все I/O-операции в `app/adapters`/`app/services` асинхронные (сервер — `grpc.aio`), синхронный блокирующий вызов (например, `pytesseract` — блокирующая C-библиотека) — оборачивается в `asyncio.to_thread`, не вызывается напрямую в async-функции.
- Исключения — своя иерархия в `app/domain/errors.py` (`ExtractionError`, `RenderError`, `SttError`...), сервисеры на границе (`app/grpc/servicers`) ловят их и маппят на `grpc.StatusCode` явной таблицей — не пробрасывают `Exception` как есть наружу (см. §8).
- `ruff` (линт + форматирование) в CI — эквивалент ESLint/Prettier на фронте, единая конфигурация в `helper/pyproject.toml`.

## 7. gRPC / protobuf — стиль контракта

Полное обоснование выбора gRPC — `BACKEND_PLAN.md §1.1/§1.2/§3`. Здесь — обязательные правила при работе с `.proto`:

- Один `.proto`-файл на доменный сервис (`rag.proto`, `files.proto`, `documents.proto`, `stt.proto`) — не сваливать все RPC в один файл.
- Поля **никогда не переномеровываются и не удаляются** задним числом — только добавление новых с следующим свободным номером, устаревшие помечаются `[deprecated = true]`, физически убираются отдельным PR только после подтверждения, что ни один клиент их не шлёт/не ждёт.
- Опциональные примитивы — через `optional` (proto3), не через "0 = не задано" по соглашению: `int32 amount = 1;` не различает "0 тенге" и "поле не заполнено", `optional int32 amount = 1;` — различает.
- `buf lint`/`buf breaking` — обязательны в CI на любой PR, трогающий `proto/**` (детали — `BACKEND_PLAN.md §3.2`).
- Серверные и клиентские interceptor'ы — единая точка для сквозных забот (auth, `trace_id`, логирование, ретраи/circuit breaker на клиенте) — не дублируются вручную в каждом `Servicer`/каждом вызывающем месте.

## 8. Обработка ошибок

Принцип — как в v3 §5 (наследуется без изменений): пользователь никогда не видит сырую ошибку интеграции (текст исключения Go/Python, стектрейс, ответ LLM как есть) — только понятную фразу на его языке. Технический контекст — только в логах (§4).

- **Go, публичный HTTP-слой**: единый тип `apierror.Error{Code string, Message string, HTTPStatus int}` — известные бизнес-ошибки (`ErrInsufficientBalance` и т.п.) маппятся на конкретный `apierror.Error` в `internal/httpserver`; всё, что не распознано явно — общий `internal_error` / 500 с нейтральным текстом, оригинальная ошибка уходит только в лог. `Code` — то самое машиночитаемое поле из `BACKEND_PLAN.md §6` (пункт 6 таблицы открытых вопросов): `{code, message}` в теле ответа.
- **gRPC-слой (Go↔Python)**: таблица маппинга `codes.*` — уже зафиксирована в `BACKEND_PLAN.md §3.3`, реализуется один раз в `grpcclient`-interceptor'е (Go, разбор ответа) и в exception-handler'е сервисеров (Python, формирование ответа) — не переизобретается в каждом вызывающем месте.
- **Python, границы сервисера**: ни одно исключение из `app/services`/`app/adapters` не долетает до клиента как есть — либо явно смаплено на `grpc.StatusCode` с понятным `details`, либо (непредвиденное) — `codes.INTERNAL` с нейтральным текстом + полный traceback в лог на `ERROR`.
- Ни одного проигнорированного `error`/`except: pass` — см. §4.3.

## 9. Git / PR

- Conventional commits: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`, `proto:` (изменения `.proto`, чтобы такие PR было легко найти отдельно — они требуют `buf breaking` в ревью).
- Один PR = одна стадия или подстадия из `BACKEND_PLAN.md` (например, "Stage 4: Python — extract"). Не смешивать рефактор общего пакета с новой бизнес-логикой в одном PR.
- PR, меняющий `proto/**`, обязан явно указать в описании: ломает ли изменение существующих клиентов (по выводу `buf breaking`), и если да — почему это осознанно (major-версия контракта) или что это ещё не задеплоено, поэтому безопасно.
- В описании PR — ссылка на пункт `BACKEND_PLAN.md`, который закрывается, и подтверждение "старая реализация по этой логике удалена" (или "не применимо").
- Definition of Done — `BACKEND_PLAN.md §8`, чек-лист в шаблоне PR.

## 10. Тестирование

- **Go**: table-driven тесты (`testing` + `testify/assert`/`require`) на бизнес-логику без сети/БД (расчёт цены, статус-машина, верификация источников RAG) — обязательны для каждого нового публичного метода `service`. Интеграционные — `testcontainers-go` (реальный Postgres), для gRPC-клиента — `bufconn` (in-memory grpc-соединение без реальной сети, официальный паттерн `google.golang.org/grpc/test/bufconn`) против тестового сервера-заглушки, без поднятия реального `helper/` в юнит-тестах Go.
- **Python**: `pytest` + `pytest-asyncio`, юниты на `app/services/*` с замоканными `app/adapters/*` (через `Protocol`-based fake, не через monkeypatch внутренностей библиотек), интеграционные — реальный `grpc.aio`-сервер в тесте + сгенерированный клиент.
- **Сквозные (Go↔Python)**: т.к. форма сообщений гарантирована `.proto` (buf breaking в CI), сквозные тесты проверяют **поведение**, не форму — реальный `helper/` поднят в docker-compose/CI, Go-тесты гоняют настоящие gRPC-вызовы (см. `BACKEND_PLAN.md §3.3`).
- Тестируется поведение, а не реализация — тест, который ломается от переименования непубличной переменной без изменения поведения, написан неправильно (то же правило, что на фронте, `FRONT_CODING_STANDARDS.md §10`).

## 12. Схема БД — единый референс-файл

`backend/schema.sql` — один файл, в котором видна **вся** схема `core` целиком (все таблицы/индексы/constraint'ы в актуальном виде), а не по кускам из N файлов `backend/migrations/`. Не инструмент, а читаемый референс для онбординга/ревью — golang-migrate по-прежнему работает только с `backend/migrations/*.up.sql`/`*.down.sql` (`BACKEND_PLAN.md §1.1`), эта договорённость не меняется.

- **Любая миграция, меняющая схему `core`, обновляет `backend/schema.sql` в том же PR.** Новый файл миграции без обновлённого `schema.sql` — незакрытый PR, тот же принцип, что и у `openapi.yaml` (§ниже, DoD `BACKEND_PLAN.md §8`: "правка контракта — в этом же PR, до кода").
- **Формат правки — обязательно "комментарий, что изменилось, затем код под ним"**, для каждого изменённого/добавленного объекта (таблица, колонка, индекс, constraint):

  ```sql
  -- Stage N (NNNNNN_migration_name): что именно изменилось и почему
  -- (2-4 строки, если обоснование не развёрнуто уже в самой миграции —
  -- тогда достаточно ссылки на неё).
  CREATE TABLE ...   -- или ALTER TABLE / CREATE INDEX и т.п. — сам SQL сразу под комментарием
  ```

- `schema.sql` — это **снимок текущего состояния**, не журнал `ALTER`'ов: если колонка меняла тип дважды, в файле остаётся один блок с финальным типом и комментарием, фиксирующим последнее изменение (история "как дошли до этого" — в `BACKEND_LOG.md` и в самих файлах миграций, не дублируется здесь).
- Порядок объектов в файле — по нумерации сущностей `zan-backend-tz-v2.md §2` (Session → Service → Tariff → UserCredit → Payment → Thread → ...), не по хронологии миграций — если новая колонка ссылается (FK) на таблицу, которая по этому порядку идёт позже, колонка добавляется через `ALTER TABLE` сразу после определения таблицы-цели (пример — `payments.thread_id` → `core.threads`), чтобы файл оставался исполняемым сверху вниз одним `psql < schema.sql` на пустой БД (это тоже способ проверить его на ошибку перед PR).
