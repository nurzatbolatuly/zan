# Zan Backend — инструкции и журнал изменений

Живой журнал `backend/` + `helper/` + `proto/`, по образцу фронтового `instructions.md` (см. `BACKEND_PLAN.md`, Stage 0, и `BACKEND_CODING_STANDARDS.md` §9). Документы команды:

- `BACKEND_PLAN.md` — стадии, архитектурные решения, контракт Go↔Python
- `BACKEND_CODING_STANDARDS.md` — слои, паттерны, naming, логирование, обработка ошибок, тесты
- `backend-roadmap.md` (ТЗ v4) — источник правды по бизнес-логике/каталогу ошибок/логированию
- `BACKEND_LOG.md` (этот файл) — живой журнал: что реализовано, какие решения приняты по ходу

## ⚠️ Правило

Обновляется **после каждой стадии/подстадии**, не в конце. После любого изменения в коде:

1. Запись в «Журнал изменений» (дата, что сделано, какой стадии из `BACKEND_PLAN.md` соответствует).
2. Новый паттерн/конвенция — в «Конвенции», чтобы следующая стадия не изобретала свою.
3. Если решение меняет что-то из `BACKEND_PLAN.md`/`BACKEND_CODING_STANDARDS.md` — правится и сам документ, в том же PR, не только этот журнал.

Подробности, обоснование границ правила (что не считается "запросом") и список затронутых файлов — в записи «Журнал изменений» ниже и в `BACKEND_CODING_STANDARDS.md §1.1`.

Проверка Stage 0 — не список ручных шагов, а одна команда:

```
make verify   # lint + test + smoke — то же самое гоняет CI (backend-ci.yml) на каждый PR
```

`make verify` = `make lint` (статический анализ обоих сервисов) + `make test` (юнит-тесты обоих сервисов) + `make smoke` (`scripts/smoke-test.sh` — поднимает весь `docker compose` стек, ждёт `healthy` у всех четырёх контейнеров, применяет миграции, гоняет реальные сценарии файлов/голоса/тредов через настоящий Go↔Python gRPC-контракт, и гарантированно опускает стек в конце — успех или провал, не важно). Ничего из этого не нужно проверять/запускать руками — `make smoke` и job `smoke` в CI гоняют один и тот же скрипт, так что то, что зелено локально, зелено и на PR.

Что именно проверяет `make smoke` (для справки, не для ручного повторения):

- `curl :8080/healthz` (Go) → `{"status":"ok"}`, с корректным `X-Trace-Id`.
- `curl :8001/healthz` (Python health-HTTP) → `{"status":"ok"}`.
- `grpcurl -plaintext :9090 list` → `zan.rpc.v1.{FilesService,DocumentsService,SttService}` + `ServerReflection` (Stage 4 — реальный бизнес-контракт, не только рефлексия, как было на Stage 0).
- `CREATE EXTENSION vector` на постгресе (образ `pgvector/pgvector:pg16` — готов под Stage 5 RAG).
- `minio` health-эндпоинт.
- **Stage 4:** `migrate up` (golang-migrate CLI — не входит в образ backend, ставится отдельно, см. `.github/workflows/backend-ci.yml`), `POST /sessions` → `POST /files/upload` реальным PDF (`scripts/fixtures/smoke-test.pdf`) → ожидает `processing_status=processed` (значит, `FilesService.Extract` реально отработал через gRPC) → `GET /files/{id}` отдаёт presigned-ссылку, которая реально скачивается → `POST /voice/transcribe` реальным WAV (`scripts/fixtures/smoke-test.wav`, тишина) → принимает `200` или `422 empty_transcript` (оба значат, что `SttService.Transcribe`/faster-whisper реально отработал) → `POST /threads {input_type: file, file_ids: [...]}` создаёт тред с вложением.

Логи обоих сервисов при этом — валидный JSON по контракту `backend-roadmap.md §6.1` (`timestamp/level/service/trace_id/message/context`, `service` = `go-core`/`python-agent` буквально как в ТЗ) — проверено при разработке скрипта, отдельной автоматической проверки на конкретные поля лога пока нет (не блокирует Stage 0, не забыто).

**Параллельная сессия на этой же машине (`zan-68`) — координировано, не конфликт.** Во время Stage 0 в `backend/internal/{domain,repo,apierror,agent,platform/{clock,idgen,resilience,storage}}` и `internal/service/{billing,catalog,file,prompt,session,thread}` обнаружились файлы, которых эта сессия не создавала. `ListAgents` подтвердил вторую активную Claude-сессию в этом же репозитории; после обмена сообщениями (см. запись 2026-09-20 ниже) выяснилось — пользователь напрямую попросил `zan-68` заскаффолдить hexagonal/ports-and-adapters слои по `BACKEND_CODING_STANDARDS.md §1.1/§1.2`, отдельно от Stage 0-инфраструктуры этой сессии. ## Конвенции (заполняется по ходу)

**`backend/schema.sql` — единый читаемый снимок всей схемы `core`, обновляется вместе с каждой миграцией (`BACKEND_CODING_STANDARDS.md §12`).** Не используется тулингом (`golang-migrate` по-прежнему читает только `backend/migrations/*.sql`) — только для онбординга/ревью, чтобы не собирать схему по кускам из N файлов миграций в голове. Формат правки — обязательно комментарий "что изменилось и почему/ссылка на миграцию", сразу под ним — сам SQL в актуальном (финальном) виде, не журнал ALTER'ов. Файл исполняем сверху вниз одним `psql < backend/schema.sql` на пустой БД — это же способ проверить его перед PR (если объект ссылается на таблицу, которая по порядку `zan-backend-tz-v2.md §2` идёт позже, колонка добавляется отдельным `ALTER TABLE` сразу после определения таблицы-цели, пример — `payments.thread_id`).

**Проверка "работает ли Stage N" — всегда один скрипт/команда, не список шагов в этом файле.** `scripts/smoke-test.sh` (запускается через `make smoke`, а всё разом — через `make verify`) — единственное место, где живёт логика "поднять стек, дождаться healthy, проверить контракты, опустить стек". CI (`backend-ci.yml`, job `smoke`) гоняет тот же скрипт, не дублирует шаги в YAML. Когда Stage 1+ добавит новые публичные проверки (например, реальный `POST /sessions`) — новая проверка дописывается в `scripts/smoke-test.sh`, а не заводится отдельным ad-hoc `curl` в описании журнала, которое никто не будет перезапускать.

**Кодогенерация протобуф — раздельная по языкам, не одним `buf generate` на оба таргета.** `proto/buf.gen.yaml` генерирует только Go (локальные плагины `protoc-gen-go`/`protoc-gen-go-grpc`, `go install`). Python генерируется отдельным вызовом `python -m grpc_tools.protoc` (см. `Makefile#proto`) — `grpc_tools` несёт собственный протобuf-компилятор и не нуждается ни в системном `protoc`, ни в `buf`-remote-плагинах (которые требуют сети до `buf.build` и не проверялись в этом окружении). Оба таргета читают один и тот же `proto/`, поэтому контракт остаётся единым источником правды несмотря на разный тулинг генерации.

**Ни один сегмент proto-пакета/директории под `proto/` не называется `internal`.** `buf.gen.yaml` генерирует Go с `paths=source_relative` — выходной путь зеркалит путь `.proto`-файла один в один внутри уже-`internal` `backend/internal/genproto/`. Второе вхождение `internal` создаёт собственную Go-границу видимости и делает сгенерированный пакет невидимым для всего остального `backend/internal/*` (найдено и исправлено на Stage 4 — было `zan.internal.v1`, стало `zan.rpc.v1`, см. запись ниже). Новые `.proto` (`rag.proto`, Stage 5) — сразу в `zan.rpc.v1` (или следующей версии `zan.rpc.v2`), не в `*.internal.*`.

**`helper/app/bootstrap_genproto.py` — добавляет `app/genproto` в `sys.path`, импортируется первой строкой в `app/main.py` и `tests/conftest.py`.** Сгенерированный код cross-импортирует себя как `from zan.internal.v1 import x_pb2` (по пути `.proto`, без ведома о нашей обёрточной директории `app/genproto/`) — без этого шага `rag.proto`, импортирующий `common.proto` (со Stage 5), сломался бы на `ModuleNotFoundError`. Единообразие обязательно: всегда `zan.internal.v1.xxx_pb2`, никогда `app.genproto.zan.internal.v1.xxx_pb2` — два пути импорта одного модуля дали бы дублирование в protobuf descriptor pool.

**`ruff`/`mypy` — `app/genproto` исключён через `extend-exclude`, не `exclude`.** Голый `exclude` в `[tool.ruff]` **полностью заменяет** дефолтный список ruff (который и так исключает `.venv`/`.git`/...), а не дополняет его — с `exclude = ["app/genproto"]` ruff начинал линтить содержимое `.venv` целиком (реально найдено и исправлено при первом прогоне `make lint`, не гипотетически).

**Docker-образ `minio/minio` на Docker Hub недоступен (`pull access denied`) — актуальный источник `quay.io/minio/minio`.** Обнаружено эмпирически при первом `docker compose up`, не бралось из документации заранее — `docker-compose.yml` использует `quay.io/minio/minio:latest`.

**`backend/go.mod` требует `go 1.25.0`, не выбранный вручную `1.23`.** `go mod tidy` сам поднял версию до минимума, который требует один из транзитивных пакетов (`google.golang.org/grpc`/`protobuf`). `backend/Dockerfile` использует `golang:1.25-alpine` как билд-стадию — синхронизировать при следующем `go mod tidy`, если версия снова поднимется.

**Docker HEALTHCHECK для `backend/` (distroless, без shell/curl) — реализован в самом бинаре, не `CMD-SHELL`.** `cmd/api/healthcheck.go#runHealthcheck` — режим `api healthcheck`, дергает собственный `/healthz` через `net/http` и возвращает код возврата процесса. `helper/` (`python:3.12-slim`, интерпретатор есть) — аналогично, но отдельным маленьким скриптом `helper/healthcheck.py` (`python healthcheck.py` в `HEALTHCHECK CMD`), не встроено в `app/main.py`, т.к. не требует того же обхода "нет shell", что у Go.

**`helper/requirements.txt` дублирует `[project.dependencies]` из `pyproject.toml` — осознанно, не забытый рассинхрон.** Нужен только для Docker-слоя зависимостей: `pip install .` из `pyproject.toml` с `hatchling`-бэкендом потребовал бы исходники `app/` уже на этапе установки зависимостей, что сломало бы кэширование Docker-слоя (зависимости меняются реже кода). При изменении рантайм-зависимостей в `pyproject.toml` — обновить и `requirements.txt` в том же PR (комментарий в файле указывает на это же место).

**Пул-реквест-уровня CI (`\.github/workflows/backend-ci.yml`) — три параллельных джоба (`proto`/`backend`/`helper`), не один общий.** `proto` гоняет `buf lint`/`buf breaking` (только Go-кодогенерацию, т.к. remote-плагины для Python в CI не настраивались — та же причина, что и в конвенции про кодогенерацию выше); `backend`/`helper` — независимые тулчейны, зависят только от изменений в своих путях (`paths:` в триггере).

**Stage 3 — StubAgent живёт в `internal/service/thread`, не в `internal/agent`.** `internal/agent` с Stage 0 документирован как "HTTP-клиент к LLM-провайдеру" — это Stage 5 реализация `thread.Agent`. Временная заглушка Stage 3 (`thread.StubAgent`, `stub_agent.go`) объявлена там же, где сам порт `thread.Agent` (`agent.go`) — оба удовлетворяют `BACKEND_CODING_STANDARDS.md §1.1/§3` ("временное сосуществование — явно объявлено"), заменяется в Stage 5 одной строкой в `cmd/api/main.go` (`thread.NewStubAgent()` → `agent.NewClient(...)`), без изменений в `service`/`httpserver`.

**Атомарные переходы статус-машины треда — тот же паттерн, что `billing_repo.MarkPaymentSuccess`: guarded `UPDATE ... WHERE status = ANY($from)`, 0 строк = гонка/повторный вызов, не ошибка.** `thread_repo.go#UpdateStatus`/`ActivatePaid` возвращают `(domain.Thread, bool, error)` — `internal/service/thread` на `ok=false` перечитывает текущее состояние (`refetch`), не считает это ошибкой транспорта. `status = ANY($4::text[])` — массив-параметр `[]string` из Go напрямую в `pgx`-запрос, один запрос вместо N веток `OR`.

**`GET /threads` — total одним запросом через `COUNT(*) OVER()` (window function), не отдельным `SELECT count(*)`.** Одно поле `total_count` в `SELECT` рядом с колонками `threads` и та же оконная функция — one round-trip к БД вместо двух с одинаковым `WHERE`, и не расходится, если фильтры поменяются в одном месте, а не в двух.

**`free_until`/`closed_at` — закрытие треда ленивое (on-access), не отдельная фоновая задача.** В отличие от `billing.ExpireStalePending` (сработавший таймер обязателен — просроченный `pending`-платёж иначе никто не переведёт в `failed`), просроченный `free_until` не нужно "спешить" закрывать: `thread.Service.AddMessage` сам проверяет `now() >= free_until` при каждом обращении и лениво проставляет `closed_at`, если ещё не проставлен (`Thread.IsClosed`). Более простой код, тот же результат для пользователя — фоновая задача добавится, только если появится сценарий, которому важно именно "закрыт прямо в момент истечения", а не "закрыт при следующем обращении".

**Self-hosted по умолчанию за портом-интерфейсом — не только для STT (`BACKEND_PLAN.md §6 п.10`), но и для embeddings (Stage 5).** `app/adapters/embeddings.FastEmbedProvider` — `fastembed` (ONNX-рантайм, без зависимости от `torch`), модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (384 измерения, многоязычная — `ru` покрыт хорошо, `kz` слабее, это ограничение всех доступных self-hosted мультиязычных моделей на эту пару языков, не что-то специфичное для этого выбора). Решение архитектора для MVP: не заводить внешний платный API (OpenAI/Voyage embeddings) только ради одной этой RPC, когда self-hosted-паттерн уже принят и работает для STT — тот же `EmbeddingProvider`-порт, та же возможность заменить на внешний API позже без переписывания `RagService`. Веса скачиваются на этапе сборки Docker-образа (`ARG EMBEDDING_MODEL`, `helper/Dockerfile`), тот же приём, что `WHISPER_MODEL_SIZE`.

**pgvector-индекс — HNSW, не IVFFlat (открытый вопрос `BACKEND_PLAN.md §1.3`, закрыт на Stage 5).** IVFFlat требует параметр `lists`, посчитанный от ожидаемого размера корпуса на момент создания индекса — не подходит для MVP, где сид-корпус на старте (единицы-десятки записей) растёт на порядки без предсказуемого расписания переиндексации. HNSW не требует этой настройки и не деградирует по качеству по мере роста корпуса — разумный дефолт, пересмотреть при реальном росте/метриках latency прод. `vector_cosine_ops` — та же метрика (`<=>`), что использует `PgVectorStore.search`.

**Схема `rag` (Postgres) — отдельная, ограниченная роль `zan_rag`, а не тот же `DATABASE_URL`, что у Go (`BACKEND_PLAN.md §1.3`).** `scripts/postgres-init/01-rag-role.sh` (`docker-entrypoint-initdb.d`, гоняется один раз на пустом томе) заводит роль `zan_rag` + `CREATE SCHEMA rag AUTHORIZATION zan_rag` + `REVOKE ALL ... FROM PUBLIC` (иначе дефолтные гранты Postgres на схему её владельца сделали бы изоляцию фикцией). **Изоляция реализована только в одну сторону**: Python не может выйти за пределы схемы `rag` (заявленная цель — "предотвращает случайную связность мимо gRPC-контракта" — эта сторона закрыта полностью), но роль `zan` (bootstrap-суперпользователь официального образа `postgres`, которым по-прежнему пользуется Go/`golang-migrate`) физически не ограничена схемой `core` — полная симметричная изоляция потребовала бы вводить отдельную непривилегированную роль и для Go, пересоздавая существующие Stage 1-4 миграции под новым владельцем, что не оправдано объёмом этой стадии. Осознанно отложено до Stage 8 (hardening) — зафиксировано здесь, не молча пропущено. Существующие локальные тома Postgres не подхватят новую роль автоматически (`docker-entrypoint-initdb.d` не гоняется повторно) — нужно один раз пересоздать том (см. комментарий в самом скрипте).

**`RAG_DATABASE_URL` — один и тот же DSN и для рантайма (`app.adapters.db.PgVectorStore`), и для миграций (`helper/migrations`, Alembic).** Роль `zan_rag` уже владеет схемой `rag` к моменту первого запуска `alembic upgrade head` (создана `scripts/postgres-init/`), поэтому, в отличие от Go (`golang-migrate` и рантайм тоже формально разделены, но оба используют один и тот же суперпользовательский `DATABASE_URL`), здесь не нужен отдельный "админский" DSN только для миграций — `CREATE TABLE`/`CREATE INDEX` внутри своей же схемы не требуют повышенных прав.

**Любая ошибка `RagService.Search` — деградация Go-стороны, не только явный `grpcclient.IsUnavailable`.** `internal/agent.Client.searchSources` ловит любую ошибку (breaker открыт, таймаут, `INTERNAL` от Python, что угодно) и продолжает вызов LLM без RAG-контекста, логируя `rag_search_completed{degraded:true}` — RAG никогда не должен быть единственной причиной, по которой пользователь не получил ответ (`backend-roadmap.md §5.2`). Симметрично на стороне Python: `app.main._run` не роняет весь процесс, если пул к схеме `rag` не поднялся при старте (например, старый том без `scripts/postgres-init/`) — `Files`/`Stt`/`Documents` не зависят от `rag` и не должны страдать из-за её недоступности; `PgVectorStore(pool=None)` вместо этого поднимает `RagUnavailableError` на каждый вызов `search()`, замапленную в `INTERNAL` (`app/grpc/error_mapping.py`), что Go всё равно трактует как деградацию по пункту выше.

**Этапы логирования 7/8/9 (`rag_search_*`/`llm_call_*`, `backend-roadmap.md §6.2`) — логируются в `internal/agent.Client.Process`, не в `internal/service/thread`.** `thread.Service.runAgentAndFinish` раньше (Stage 3, со `StubAgent`) сам оборачивал вызов агента общими `agent_call_started`/`agent_call_completed` — с реальным LLM это перестало иметь смысл: только `internal/agent` реально знает `prompt_version` (хэш фактического системного промпта, включая RAG-контекст конкретного вызова), `sources_count_in_context`, `matches_count`, `degraded` — `thread.Service` этого не видит и не должен восстанавливать постфактум. `agent_call_started`/`agent_call_completed` убраны из `thread.go` целиком (не задублированы рядом с новыми) — `thread.Service` логирует только то, что реально видно на его уровне (переходы статуса, `message_saved`, `credit_refunded`, `response_sent`).

**`verifySources(llmSources, ragMatches) → bool` — чистая функция без сети/состояния, юнит-тестируемая отдельно (`internal/agent/verify.go`, явное требование `BACKEND_PLAN.md` Stage 5).** Сверка по `ref` (регистронезависимо, без пробелов по краям — "то же обозначение статьи", не байт-в-байт). Пустой `llmSources` → `false` (нечего проверять). Непустой `llmSources` при пустом/недоступном `ragMatches` → `true` — не с чем сверить, значит не подтверждено, тот же принцип, что и обычное несовпадение.

**Технический контракт структурированного JSON-ответа LLM (`internal/agent/prompt.go#jsonContractInstructions`) не хранится в `core.agent_prompts` и не редактируется через `/admin/prompts`.** `PromptText` из БД — только "человеческая" часть (тон/охват/поведение), редактируемая продуктом/юристами без деплоя (`zan-backend-tz-v2.md §4.6`). Формат ответа (`answer_text`/`sources`/`findings`/`needs_clarification`) добавляется поверх этого текста самим `internal/agent.buildSystemPrompt` — если бы это было частью редактируемого промпта, правка в админке могла бы случайно сломать парсинг ответа (`response.go` жёстко рассчитывает на эту форму).

**Возврат кредита при `status=error` — не при каждой ошибке треда, а только если тред ещё ни разу не получил успешный ответ.** `zan-backend-tz-v2.md §4.2 п.3` описывает возврат буквально для одного платежа/одного треда, но не уточняет случай "бесплатное уточнение внутри `free_until` упало после того, как основной платный ответ уже был `done`". Решение (не в ТЗ явно, зафиксировано здесь): `refundEligible = (статус до начала этого раунда обработки) != Done` — т.е. возврат происходит для первого раунда (`Queued`/`Clarify` → `Error`), но не для повторного бесплатного раунда после уже состоявшегося `Done` (услуга уже была оказана один раз, второй раз её не покупали). Пересмотреть, если продукт явно скажет иное.

**Неуспех вторичного шага ПОСЛЕ того, как первичный результат уже сохранён в БД — не `error` в сигнатуре сервисного метода, отдельное явное поле результата (Stage 6, `document.Service.Generate` → `(domain.Message, filesReady bool, error)`).** Тот же принцип, что уже применялся к `confirmPaymentHandler`/`thread.ActivateAfterPayment` (Stage 3, "платёж уже успешен, тред не стартовал синхронно — клиент разберётся через отдельный запрос") — здесь формализован как повторяемый паттерн: если операция уже необратимо сохранила что-то полезное (сообщение в чате), последующий шаг (рендер файла), который может упасть независимо, не должен превращать HTTP-ответ в ошибку — вызывающий код получает `(результат, ok bool, nil)`, не пытается втиснуть два независимых исхода в один `error`. Следующая стадия с похожей формой (успешный шаг A, необязательный шаг B) — переиспользовать этот приём, не изобретать заново.

**`internal/platform/ratelimit` ("не чаще, чем") и `internal/platform/bruteforce` ("после N неудач — заблокирован на фиксированный срок") — два разных примитива, не один параметризованный (Stage 7).** Rate limit плавно пропускает трафик с постоянной скоростью и никогда не запрещает один конкретный последующий запрос навсегда; brute-force lockout — жёсткий стоп на весь `blockDuration`, проверяется ДО бизнес-проверки (сравнения токена), не после. Путать их — значит либо давать перебору секрета возможность идти с постоянной небольшой скоростью бесконечно (rate limit это разрешает — он не понимает "неудача", только "слишком часто"), либо блокировать легитимный трафик на фиксированный срок за то, что является штатной нагрузкой, не атакой (bruteforce lockout это дал бы, если бы использовался как обычный rate limit). Когда следующей стадии понадобится "N неудач — блокировка" для чего-то ещё (не `/admin/*`) — переиспользовать `internal/platform/bruteforce`, не городить это поверх `ratelimit.Store`.

**`app/grpc/error_mapping.py` — единая таблица исключение → `grpc.StatusCode` (`BACKEND_CODING_STANDARDS.md §8`), не размазана по трём сервисерам.** `UntrustedFileURLError`/`ExtractionError`/`SttError`/`RenderError` → `INVALID_ARGUMENT` (не ретраится) — с отдельным WARN `ssrf_attempt_blocked` для первого (security-инцидент, не просто плохой запрос). `DownloadError` (собственный storage недоступен) → `INTERNAL` с ERROR-логом — не `INVALID_ARGUMENT`: это сбой Python-инфраструктуры, не проблема запроса, и `resilience.Breaker` на Go всё равно копит его как неудачу (считает любую ошибку, не только `UNAVAILABLE`). Всё остальное — `CRITICAL` + полный traceback + `INTERNAL` с нейтральным текстом.

**`app/adapters/render.py` — `DocxTplRenderer`/`WeasyPrintRenderer`, оба реализуют `render_service.Renderer` для своего `RenderFormat`.** DOCX-шаблон (`app/adapters/templates/document_template.docx`) — реальный `.docx`-файл с `docxtpl`-тегами, сгенерирован и закоммичен как бинарный ассет (не текстовый файл, обычный git-объект). **Находка при построении шаблона:** синтаксис `{%tr for ... %}`/`{%tr endfor %}` (docxtpl "row loop") требует, чтобы тег стоял **один**, без другого содержимого, в отдельной строке таблицы — `docxtpl.patch_xml` вырезает весь `<w:tr>` целиком, оставляя только сам тег, и если в той же строке было что-то ещё (например, `{{ s.title }}` в соседней ячейке той же строки, что и сам тег `{%tr for %}`), оно молча пропадает вместе со строкой. Рабочая структура — 4 строки: header, строка только с `{%tr for s in sections %}`, строка с `{{ s.title }}`/`{{ s.body }}` (репликируется), строка только с `{%tr endfor %}`. **Архитектурное решение — генерация документа НЕ идёт через `thread.Service`/`thread.Agent.Process`, отдельный пакет `internal/service/document` с собственной оркестрацией.** Явно предусмотрено ещё в Stage 5 (`internal/agent/agent.go#toAgentType`: `"doc"` не проходит маппинг на `qa`-флоу) и в `zan-backend-tz-v2.md §4.4` ("генерация документа — всегда отдельная операция"). `document.Service` — тот же паттерн, что `thread.Service`: оркестрирует billing/catalog/agent/render/storage через узкие порты, объявленные в самом пакете (`BACKEND_CODING_STANDARDS.md §1.1`), реализуемые структурно уже существующими `*billing.Service`/`*catalog.Service`/`*repo.ThreadRepo`/`*repo.FileRepo`/`*storage.Client` без единого адаптера. `document.ErrThreadNotFound` — не новый сентинел с тем же смыслом, а прямой алиас `thread.ErrThreadNotFound` (`var ErrThreadNotFound = thread.ErrThreadNotFound`) — единственный импорт пакета `thread` в `document`, тот же приём "документированное исключение", что уже применяет `thread.go` к `billing.ErrInsufficientBalance`.

**`internal/agent` — общая часть `Process`/`GenerateDocument` вынесена в приватный `runLLM(ctx, agentType, history) (llmOutcome, error)` (`agent.go`), само `GenerateDocument` — в новом `document.go`.** До Stage 6 промпт+RAG+вызов LLM+разбор ответа+верификация источников+лог `llm_call_started/completed` были частью тела `Process` целиком; вынесены без изменения наблюдаемого поведения `Process` (тот же порядок логов, те же поля — юнит-тесты `agent_test.go` не менялись и прошли как есть). `runLLM` параметризован `domain.AgentType`, а не жёстко "qa" — `GenerateDocument` вызывает его с `domain.AgentTypeDocument`, получая `AgentPrompt(document)` (засеян миграцией `000005_stage5_agent`, не тронут) вместо `AgentPrompt(qa)`. `ErrDocumentNeedsClarification` — новый сентинел (`document.go`): в отличие от Q&A (`needs_clarification=true` → `AgentResultClarify`, устойчивый статус треда), у генерации документа нет промежуточного состояния — недостаточно контекста трактуется как обычный неуспех генерации, `document.Service` не различает эту причину от отказа модели/невалидного JSON/таймаута дальше по стеку (единый `document.ErrGenerationFailed`).

**Одна генерация — оба формата, не рендер по требованию.** `document.Service.Generate` вызывает `grpcclient.Client.RenderDocument` дважды (`pdf`+`docx`) в одном запросе `POST /threads/{id}/generate-document` — закрывает буквальное требование v2 §4.4 (`FileAttachment(..., output_formats=["pdf","docx"])`) и делает `GET /threads/{id}/document?format=` простой выдачей уже готового файла, без рендера на лету (не нужно персистить черновик документа между запросами, LLM вызывается ровно один раз на одну генерацию).

**`core.file_attachments.thread_id` — новый nullable столбец (миграция `000006_stage6_documents`), только для `purpose=generated_output`.** Каждый рендер (`pdf`/`docx`) — своя строка `FileAttachment` (не одна строка с двумя ключами — `object_key` в схеме принципиально singular, введён Stage 4 и не пересматривался), `thread_id` — прямая ссылка, чтобы `GET /threads/{id}/document?format=` не требовал `JOIN core.messages`. `output_formats=["pdf","docx"]` записывается на **обе** строки одинаково — декларативно "документ доступен в этих форматах", не "эта строка содержит оба". `internal/repo/file_repo.go` — два новых метода, `CreateGenerated`/`GetLatestGenerated`, свои SQL-литералы (не переиспользуют `Create`/`GetByID`, у которых `message_id` захардкожен в `NULL` — другая семантика вставки, `BACKEND_CODING_STANDARDS.md §1.1`); `fileRow`/`toDomain`/существующие `Create`/`GetByID` обновлены под новую колонку.

**Частичный рендер не откатывается.** `document.Service.renderAll` останавливается на первой ошибке формата — уже успешно отрендеренный (например, `pdf`, если следом упал `docx`) файл остаётся доступным для скачивания, не удаляется. Осознанное упрощение: `backend-roadmap.md §5.2` не разбирает частичный случай отдельно ("doc-кредит возвращается" — это про весь вызов, не про формат), а частично готовый результат лучше отсутствующего.

**Возврат `(domain.Message, filesReady bool, error)`, а не `(domain.Message, error)` — неуспех рендера не транспортная ошибка.** Текст ответа уже сохранён в БД (`AppendMessage` к этому моменту закоммичен) к моменту, когда рендер падает — `Generate` возвращает `(msg, false, nil)`, не оборачивает это в `error`. Тот же принцип, что `confirmPaymentHandler` уже применяет к `thread.ActivateAfterPayment` (Stage 3): операция, породившая ошибку, — вторичный шаг относительно уже успешно сохранённого результата, клиент разбирается через отдельный запрос (`GET /threads/{id}/document` вернёт `document_not_generated`, пока пользователь не повторит генерацию), а не через код ответа на этот. `internal/httpserver/document.go#generateDocumentResponse` — `Message` + `files_ready` одним объектом, а не два отдельных вызова. Настоящая транспортная ошибка (`document.ErrGenerationFailed` — ничего не сохранено вообще, `document.ErrThreadNotFound`, `billing.ErrInsufficientBalance`) — обычный `apierror`, `502`/`404`/`409` соответственно (`502`, не `500` — сигнализирует именно отказ вышестоящей зависимости, LLM, а не непредвиденный баг backend'а, чтобы отличаться от общего `internal_error`).

**Оплата — тот же checkout/confirm-контракт, что уже есть, без нового хука.** `POST /payments/checkout {items:[{service_id:"doc",qty:1}], thread_id}` + `confirm` — существующий путь `confirmPaymentHandler` уже вызывает `threadSvc.ActivateAfterPayment` на любой платёж с непустым `thread_id` (Stage 3); для `doc`-платежа на уже оплаченном/не-`Queued` треде это безопасный no-op (`ActivateAfterPayment` проверяет `status==Queued && !IsPaid` и рано выходит) — новый эндпоинт подключать к этому хуку не пришлось, никакого "отложенного" состояния генерации документа не заводится: недостаточно баланса → `409 payment_required` сразу, без создания частично-сохранённой сущности (в отличие от `CreateThread`, которому есть что сохранить — сам тред — Stage 6 нечего сохранять до вызова LLM).

**`internal/service/document` вызывается дважды из `cmd/api/main.go` с собственными `repo.NewThreadRepo(pool)`/`repo.NewFileRepo(pool)`, не переиспользует экземпляры `threadSvc`/`fileSvc`.** Тот же приём, что уже применяется ко всем остальным `service.New(...)` в `main.go` — тонкие stateless-обёртки над одним `*pgxpool.Pool`, конструировать второй экземпляр дешевле и проще, чем протаскивать через `Deps`/публичный API уже собранных сервисов внутренний репозиторий, который они не экспортируют.

**Конвенции.** **`CREATE SCHEMA IF NOT EXISTS <name>;` (без `AUTHORIZATION`) требует привилегии `CREATE` на уровне БАЗЫ ДАННЫХ у вызывающей роли, даже если схема уже существует и ничего реально не создаётся — Postgres проверяет привилегию РАНЬШЕ, чем "IF NOT EXISTS".** Поймано вживую при первом прогоне миграций под `zan_core` (`docker compose`+`migrate`) — миграция `000002_core_schema.up.sql` падала с `permission denied for database zan` ровно на этой строке, хотя схема `core` уже была создана и авторизована на `zan_core` в `02-core-role.sh` парой минут раньше тем же прогоном. У `zan_core` не было привилегии `CREATE` на саму базу (по умолчанию Postgres даёт `PUBLIC` только `CONNECT`+`TEMP` на новую базу, не `CREATE` — в отличие от объектов внутри уже-своей схемы, где привилегии владельца достаточно). Исправлено добавлением `GRANT CREATE ON DATABASE "$POSTGRES_DB" TO zan_core;` в конец `02-core-role.sh` — не открывает доступ к `rag` (изоляцию держит `REVOKE` в `01-rag-role.sh`, не отсутствие этого гранта). **Если следующая стадия заведёт ещё одну непривилегированную роль под свою схему — держать в уме эту привилегию отдельно от `CREATE SCHEMA ... AUTHORIZATION`, одно не покрывает другое.** Локальный `docker`-том Postgres пришлось пересоздать один раз, чтобы `02-core-role.sh` вообще применился (`docker-entrypoint-initdb.d` не гоняется на уже существующем томе, тот же нюанс, что и у `01-rag-role.sh` на Stage 5) — если у кого-то есть свой локальный том с прошлых стадий, тот же шаг потребуется и ему, см. предупреждение в самом `02-core-role.sh`.

**CORS — новый `internal/httpserver.CORS` (`CORS_ALLOWED_ORIGINS`, env, точные origin'ы через запятую, не wildcard).** Wildcard (`*`) с самого начала не подходил: сессия — httpOnly-cookie, а `Access-Control-Allow-Credentials: true` по спецификации CORS нельзя сочетать с `Access-Control-Allow-Origin: *` — нужен origin эхом из запроса, если он есть в allow-листе. Пусто по умолчанию — CORS-заголовки не выставляются вообще (безопасный дефолт: SPA+API за одним origin и non-browser клиенты продолжают работать, браузерный кросс-ориджин фронт без явной настройки будет просто заблокирован браузером, не тихо разрешён). **Найден и задокументирован (не исправлен — чужой код) зазор на фронте**: `frontend/src/shared/lib/api.ts#apiFetch` не передаёт `credentials: "include"` — при разных origin'ах фронта и бэка браузер не пошлёт cookie сессии кросс-доменно вообще, независимо от корректности CORS-заголовков бэка. Задокументировано в `instructions.md` «Деплой» п.3 с тремя вариантами решения (добавить `credentials: "include"`, держать один domain через reverse-proxy, перейти на `Authorization: Session` на вебе) — решение за фронт-командой.

**`scripts/load-test.sh` (+ `make load-test`) — нагрузочный smoke-тест `POST /threads → LLM → ответ` (`BACKEND_PLAN.md §7`).** Сознательно НЕ через `k6`/`hey`/`ab` (новая внешняя зависимость ради одного скрипта) — bash+curl, тот же приём, что `scripts/smoke-test.sh`. Масштаб теста (5 параллельных сессий × 3 треда) ограничен НЕ ленью, а самим API: `POST /sessions` лимитирован per-IP (`burst=5`), `POST /threads` — per-`session_id` (`burst=3`) — тест держится в пределах burst-квоты каждого барьера, чтобы измерять именно путь `POST /threads → LLM`, а не рейт-лимитер на создании сессий. Прогнан вживую: 15 конкурентных `POST /threads` с одного IP → 10×`201`, 5×`429` (per-IP burst=10 на сам `POST /threads` превышен пятью запросами) — ожидаемое, задокументированное поведение rate limiter'а под нагрузкой, не баг; `0` неожиданных `5xx`; латентность avg=0.2s/max=0.5s. Тест падает (`FAIL`) только на неожиданный `5xx` или на "вообще ни одного `201`" — `429` под нагрузкой считается штатным результатом, не поводом для провала.

### 2026-09-22 — LLM-провайдер заменён с Anthropic на OpenAI (по прямому запросу пользователя)

`internal/agent` изначально был написан против Anthropic Messages API (Stage 5) — пользователь работает с ключом OpenAI, не Anthropic, попросил заменить везде. Затронут только `internal/agent` (HTTP-клиент к LLM) — `internal/service/thread`/`internal/service/document`/весь остальной бэкенд не знают, какой провайдер за портом `thread.Agent`/`document.Generator`, ничего в них не изменилось (тот же Strategy, ради которого провайдер был спрятан за портом ещё на Stage 5).

**`internal/agent/llm_client.go` переписан на OpenAI Chat Completions API (`POST /v1/chat/completions`, `Authorization: Bearer <key>`) вместо Anthropic Messages API (`POST /v1/messages`, `x-api-key`+`anthropic-version`).** Ключевое структурное отличие: у Anthropic `system` — отдельное поле верхнего уровня запроса, у OpenAI system-промпт — просто первое сообщение с `role="system"` в общем массиве `messages` (`llmClient.doRequest` собирает его сам, вызывающий код `agent.go`/`prompt.go` не изменился по сигнатуре — `call(ctx, systemPrompt, messages)` остался). Ответ тоже проще: Anthropic возвращает массив `content`-блоков (может быть несколько, разных `type`), OpenAI — один `choices[0].message.content` строкой — `extractText`/`parseAgentResponse` (response.go) упрощены соответственно, тесты на "несколько text-блоков"/"non-text блоки" убраны как не применимые к новой форме ответа.

**`response_format: {"type": "json_object"}` — новое, у Anthropic-версии эквивалента не было (полагались только на инструкцию в промпте + `stripMarkdownFence` как защиту).** Требует, чтобы слово "JSON" встречалось в messages — `jsonContractInstructions` (prompt.go, не менялась) уже содержит его на русском ("JSON-объектом"), проверено реальным вызовом. `stripMarkdownFence` оставлена как есть (defense-in-depth, не мешает).

**`refusalStopReason="refusal"` (Anthropic-специфичный, экспериментальный stop_reason) заменён на `refusalFinishReason="content_filter"` (OpenAI, `finish_reason` при блокировке модерацией).** Семантика та же (thread.status=error, `ErrModelRefused`), сама проверка переехала с `resp.StopReason` (поле верхнего уровня у Anthropic) на `resp.Choices[0].FinishReason` (OpenAI кладёт это внутрь каждого choice, не в ответ целиком).

**`shouldRetryLLM` — убран Anthropic-специфичный `statusOverloaded=529` (нестандартный HTTP-код, у OpenAI такого нет), добавлен `504 Gateway Timeout` (стандартный, раньше не был в списке).** Остальной набор ретраев (429/500/502/503 + сетевой таймаут) не изменился.
