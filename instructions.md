# Zan Frontend — инструкции и журнал изменений

Документы команды (обязательны для всех троих фронтендов):

- `PLAN.md` — что строим, по каким стадиям
- `FRONT_CODING_STANDARDS.md` — архитектура, принципы, naming, логирование, git/PR, ревью-чеклист
- `FRONT_DESIGN_SYSTEM.md` — зафиксированные токены: цвет, типографика, spacing, радиусы, тени, z-index, breakpoints
- `instructions.md` (этот файл) — живой журнал + место, где видно, что из трёх документов выше уже реализовано, а что ещё нет

**Структура репозитория (монорепо):** сам фронтенд-проект лежит в `frontend/` (`frontend/package.json`, `frontend/src/...`), эти 4 документа и `Design/`/`backend-roadmap.md` — на корневом уровне, общие для всего проекта. Все пути вида `shared/lib/api.ts`, `app/layout/Header.tsx` и т.п. в этих документах — **относительно `frontend/src/`** (т.е. `shared/lib/api.ts` = `frontend/src/shared/lib/api.ts`), если не сказано иначе. Когда появится бэкенд — предполагается `backend/` рядом с `frontend/`.

## ⚠️ Правило (для себя и для будущих сессий)

Этот файл обновляется **после каждого этапа имплементации**, не в конце проекта.
После любого изменения в коде:

1. Добавить запись в «Журнал изменений» ниже (дата, что сделано, какой стадии из `PLAN.md` соответствует).
2. Если изменение вводит новый паттерн/конвенцию (новый способ доставать данные, новая структура папки, новая библиотека) — зафиксировать его в «Конвенции», чтобы следующая стадия делалась так же, а не изобретала свой вариант.
3. Если решение отменяет или меняет что-то из `PLAN.md`, `FRONT_CODING_STANDARDS.md` или `FRONT_DESIGN_SYSTEM.md` — поправить соответствующий файл в том же коммите, а не оставлять его расходиться с реальностью. Это касается и токенов: если в коде понадобилось новое значение цвета/отступа/z-index — сначала строка в `FRONT_DESIGN_SYSTEM.md`, потом код.
4. Не копить здесь "мусор": если конвенция перестала действовать (например, библиотеку заменили) — её запись в этом файле обновляется/удаляется, а не оставляется рядом с новой как история. Это же правило "чистой замены" из `FRONT_CODING_STANDARDS.md` §3 — применяется и к документации, не только к коду.

## Конвенции (заполняется по ходу — раздел растёт вместе с кодом)

**Структура компонента.** `PascalCase.tsx`, тест — рядом как `PascalCase.test.tsx` (пример: `shared/ui/Button.tsx` + `Button.test.tsx`). Стили — Tailwind-классы прямо в JSX через `cn()` (`shared/lib/cn.ts`); кастомный CSS-файл рядом с компонентом заводится, только когда Tailwind не покрывает (в Stage 0 такого не понадобилось ни разу, кроме двух глобальных keyframes в `shared/styles/index.css`).

**`className`-проп UI-кита — только для добавления**, не для переопределения внутренних размеров/цветов компонента (нет `tailwind-merge`, конфликт классов резолвится порядком в сгенерированном CSS, а не порядком в строке — см. комментарий в `shared/lib/cn.ts`). Нужен другой размер — это новый `variant`/`size`-проп у компонента (так сделано в `Button`), а не className-хак.

**Touch-таргеты.** `IconButton` — единственный размер 44×44px, без пропа `size`: сознательно, чтобы никто не сделал 30px-кнопку как в прототипе. `QuantityStepper` из-за этого крупнее прототипа — так и задумано (FRONT_DESIGN_SYSTEM.md §9).

**Общие модалки.** Сторы `useConfirmModalStore` / `usePaymentModalStore` (`shared/stores`) + компоненты `ConfirmModal` / `PaymentModal` (`shared/ui`), смонтированные один раз в `AppShell`. Страница **не рендерит свою модалку** — вызывает `useConfirmModalStore.getState().open({ title, message, onConfirm })` (аналогично `usePaymentModalStore`). Обе модалки построены на общем примитиве `shared/ui/Modal.tsx` (портал + focus-trap + Esc) — новая модалка (BundleEditModal, CustomOrderModal, OnboardingModal) тоже строится поверх `Modal`, а не копирует его логику.

**Все модалки приложения — только по центру экрана, без варианта "низовой шит".** Явное требование пользователя ("все модалки должны быть в середине экрана"). Изначально `Modal` поддерживал `align?: "center" | "bottom"` (дефолт `"bottom"`), и часть модалок (`PaymentModal`, потом и `ConfirmModal`/`OnboardingModal`) постепенно обрастала явным `align="center"` поштучно — к моменту, когда пользователь попросил центрировать ещё и `CustomOrderModal`, выяснилось, что уже вообще ни одна модалка в приложении не использует `"bottom"`. Проп `align` целиком убран из `Modal.tsx` (не оставлен неиспользуемым вариантом "на будущее" — `FRONT_CODING_STANDARDS.md` §3), контейнер модалки всегда `items-center`; все явные `align="center"` в вызовах (`ConfirmModal`, `PaymentModal`, `OnboardingModal`) убраны как ставшие избыточными. `CustomOrderModal`/`BundleEditModal` ничего передавать не должны — центр теперь единственное и единственно верное поведение примитива. Если когда-нибудь понадобится низовой шит — это новый явный проп с обоснованием в PR, а не возврат старого дефолта молча.

**`Card` получил проп `tone?: "default" | "spotlight"`** (`shared/ui/Card.tsx`, Stage 3 — правки после Stage 5). Первая версия была `tone="accent"` с плоским `--accent-soft` — по фидбеку пользователя ("привлекательную с точки зрения маркетинга... может микс цветов") заменена на `spotlight`: анимированный градиент `.tone-spotlight` (`shared/styles/index.css`) на трёх новых токенах `--spotlight-1/2/3` (`FRONT_DESIGN_SYSTEM.md` §1 — два стопа переиспользуют `--accent-soft`/`--warn-soft`, третий — новый бледно-синий, светлота подобрана в том же диапазоне, чтобы `--ink`-текст оставался читаемым без отдельной проверки контраста под каждый кадр). Анимация (`background-position`, 8s) не обнуляется отдельно — подчиняется общему `prefers-reduced-motion`-правилу из `index.css` (Stage 5). `tone="accent"` не сосуществовал с `spotlight` ни одного коммита — чистая замена, не наслоение (`FRONT_CODING_STANDARDS.md` §3), единственный потребитель обоих — `CustomOrderCard`. Цвет рамки — часть объекта `TONES` вместе с фоном (не отдельный базовый класс) — фон и рамка одного тона всегда в одной строке, иначе рамка резолвилась бы порядком в сгенерированном CSS, а не порядком в коде (см. предупреждение в `shared/lib/cn.ts`). `tone="spotlight"` — для одной "цепляющей взгляд" карточки на экран, не для массового использования; следующая карточка, которую нужно выделить обычным (не маркетинговым) фоном — новый `tone` в этом же объекте, не `className`-хак.

**Логирование.** Единственная точка — `shared/lib/logger.ts` (`logger.debug/info/warn/error`). `no-console` включён в ESLint везде, кроме этого файла. `shared/lib/api.ts` логирует каждый HTTP-запрос автоматически (старт/успех/ошибка) — фича логирует руками только доменные события (открытие оплаты, подтверждение, ошибки в catch), не сам факт похода в сеть.

**i18n.** Пока один пример — `shared/locales/nav.ts` (строки шапки/навигации, не принадлежат ни одной фиче), форма `Record<Lang, Dictionary>` с `Lang = "ru" | "kz"`. Фичевые словари в Stage 1+ — `features/<name>/locales.ts` (или `.../locales/*.ts`, если словарь вырастет) по той же форме, использовать напрямую как `dictionary[lang]`, без библиотеки i18n (решение PLAN.md §3).

**API/данные.** `shared/lib/api.ts` даёт `api.get/post/patch/delete`, `QueryClientProvider` подключён в `app/providers/AppProviders.tsx`. Ни один `useQuery`/`useMutation` ещё не написан — паттерн именования ключей кэша зафиксируется здесь при первом реальном запросе (Stage 1 или Stage 6).

**Мобильный композер (контракт для Stage 1).** Нижний таб-бар (`app/layout/MobileNav.tsx`) виден на всех роутах < md и резервирует высоту через CSS-переменную `--mobile-nav-h` (`shared/styles/index.css`). Композер чата — тоже `fixed`-элемент внизу — должен позиционироваться `bottom-[var(--mobile-nav-h)] md:bottom-0`, а не поверх таб-бара.

**Дебаунс инпутов.** `shared/hooks/useDebouncedValue.ts` — общий хук (значение + задержка в мс), не привязан к домену. История использует его для поиска (300мс); следующей фиче с дебаунсом (например, поиск в Settings→Tariffs) — переиспользовать этот хук, не писать свой `setTimeout` в компоненте.

**Бизнес-логика фильтров — чистая функция, а не внутри хука/компонента.** Пример: `features/history/filterThreads.ts` — чистая функция `(threads, search, status) → Thread[]`, юнит-тестируется без рендера React; `useThreadHistory.ts` только вызывает её в `useMemo` и держит состояние/сайд-эффекты (открытие confirm-модалки, toast, logger). Та же схема — для будущих фильтров (Tariffs, Settings→Tariffs список услуг).

**Доменные типы фичи (например, `Thread`) живут в `features/<name>/types.ts`**, пока используются только этой фичей — не заводятся в `shared/types` заранее «про запас». Переносятся в `shared/types`, когда второй фиче реально понадобится тот же тип (FRONT_CODING_STANDARDS.md §5) — для `Thread` это, вероятно, случится в Stage 1 (Chat читает `?thread=:id`) или Stage 6.

**Локализация `useConfirmModalStore`.** У стора RU-дефолты (`confirmLabel: "Удалить"`, `cancelLabel: "Отмена"`) — это заглушка Stage 0, не мультиязычный текст. Фича, открывающая confirm на экране с реальным `lang` (не только RU), обязана передавать `confirmLabel`/`cancelLabel`/`title`/`message` явно из своего словаря (см. `features/history/useThreadHistory.ts#requestDelete`), а не полагаться на дефолты стора.

**Даты.** `shared/lib/format.ts#formatDate` — `ДД.ММ.ГГГГ` из ISO-строки, читает поля в UTC (не через локальный часовой пояс браузера), одинаково для ru/kz. Общая утилита — не дублировать форматирование дат по фичам.

**Длительность.** `shared/lib/format.ts#formatDuration(seconds, lang)` — компактные сокращения (`"2 мин 14 с"`, `"1 ч 05 мин"`, ru: ч/мин/с, kz: сағ/мин/сек), не полные слова со склонением — тот же стиль, что у остальных meta-полей карточки (дата, статус-бейдж). Общая утилита, не только History (Chat может показывать время ответа тем же способом).

**Мок-даты, от которых зависит фильтр по периоду, — относительно `Date.now()` в момент импорта модуля, не захардкожены.** Пример: `features/history/threads.mocks.ts#hoursAgoIso`. Причина: фильтр "Сегодня"/"7 дней" на фиксированных датах прототипа через пару недель после написания стал бы показывать пустой список — мок обязан оставаться демонстрируемым в любой день, когда кто-то откроет приложение. То же правило — для любого будущего мока, который читает фильтр "по давности".

**`IconButton` вариант `ghost-danger`.** Как `ghost` (`border-transparent`, для кнопки внутри уже обрамлённого блока — например, верхний угол карточки), но hover красный (`hover:text-danger`, фон `hover:bg-surface-2` — не `bg-danger/10`: та же причина, что и у `Badge` tone="danger", Tailwind не режет alpha у `var(--danger)`). Используется, когда destructive-кнопка сидит без своей рамки внутри контейнера с уже готовой рамкой (`ThreadCard.tsx`) — обычный `danger-hover` в этом случае дал бы двойную рамку.

**Сложное состояние экрана — `useReducer` + чистый reducer в отдельном файле.** Пример: `features/chat/chatReducer.ts` (экспортирует `ChatState`/`ChatAction`/`chatReducer`) + `useChatThread.ts`, который только вызывает `dispatch` и делает сайд-эффекты (лог, открытие `PaymentModal`, таймер мок-задержки ответа). Reducer — чистая функция, юнит-тестируется без рендера (`chatReducer.test.ts`), switch без `default` с проверкой `never` на выходе — компилятор ловит забытый кейс при добавлении нового action. Та же схема — для любого экрана с > 3-4 связанных полей состояния и переходов между ними (в Stage 2 для более простого случая хватило `useState`+чистой функции `filterThreads` — reducer нужен именно когда состояний/переходов много, не по умолчанию).

**Мок-ответы фичи с демо-контентом на двух языках — сообщение хранит только `kind`, не переведённый текст.** Пример: `AssistantChatMessage.replyKind` (`"qa" | "contract-review" | "document"`), сам текст/источники/находки достаются из `mocks.ts#getAssistantReplyContent(kind, lang)` в момент рендера. Если бы текст клался в сообщение при отправке, переключение языка не отражалось бы на уже отправленных сообщениях (или пришлось бы хранить обе локали в каждом сообщении — дублирование). Пользовательский текст (то, что реально ввёл человек) в `UserChatMessage.text`, наоборот, хранится как есть и никогда не переводится.

**`usePaymentModalStore` теперь принимает локализуемые подписи** (`amountFieldLabel`, `confirmLabel`, `cancelLabel`, `note` — с RU-дефолтами для обратной совместимости), а не только `title`/`description`/`amountLabel` как в Stage 0. Тот же паттерн, что уже был у `useConfirmModalStore` (`confirmLabel`/`cancelLabel`) — см. пункт выше про его локализацию. Chat — первая фича, которая реально открывает `PaymentModal` на экране с переключаемым `lang`, поэтому неполный набор локализуемых полей стал видимой проблемой именно сейчас.

**`IconButton` — добавлены варианты `accent` (заполненная акцентным цветом кнопка — отправка сообщения, активная запись голоса) и `ghost` (прозрачный фон — кнопка вложения, неактивная запись голоса).** Оба варианта — **без своей рамки** (`border-transparent`): обе живут внутри уже обрамлённого контейнера (пилюля композера), собственная рамка поверх чужой рамки — лишняя (изначально `accent` был с `border-accent`, что при активной записи голоса давало заметный двойной контур — поправлено тем же решением от 2026-09-20, что убрало toggle «Подготовить документ»). Это `variant`, не правка через `className` (см. правило выше «className — только для добавления»); размер остаётся единственным — 44×44px.

**Размер файла.** `shared/lib/format.ts#formatFileSize` — байты → `"248 KB"`/`"1.5 MB"` (KB/B без десятых, MB/GB с одной). Общая утилита для любой карточки вложения (Chat сейчас, History/Settings — если там появятся файлы).

**`QuantityStepper` больше не хардкодит русский текст в aria-label.** До Stage 3 у компонента не было ни одного реального потребителя, а его `aria-label` кнопок +/− собирался как `` `Уменьшить: ${label}` ``/`` `Увеличить: ${label}` `` — то есть всегда по-русски, независимо от языка приложения. Это чистая замена (FRONT_CODING_STANDARDS.md §3, не наслоение — старого потребителя не было): теперь три обязательных пропа — `decreaseLabel`/`increaseLabel` (полный локализованный aria-label кнопки) и `inputLabel` (aria-label поля) — вызывающая фича обязана собрать их из своего словаря (тот же принцип, что и у `useConfirmModalStore`, см. пункт выше про его локализацию). Следующий реальный потребитель (`BundleEditModal`, Settings→Tariffs, Stage 4b) обязан делать так же, не возвращать старый префиксный вариант.

**Оплата пакета/своего набора идёт через ту же `PaymentModalStore`, что и Chat — второй реальный потребитель M3.** В прототипе кнопка «Оплатить картой» внутри модалки своего набора (`payCustom`, Zan.dc.html:1074) завершала покупку напрямую, минуя общую платёжную модалку M3 — демо-шорткат, не архитектура. Раз `PLAN.md` §1 прямо описывает M3 как общую для Chat и Tariffs, `CustomOrderModal` (`features/tariffs`) только считает сумму и закрывается, открывая `usePaymentModalStore` с этой суммой — единая точка реальной оплаты остаётся одна на всё приложение, а не по одной на каждую фичу.

**После подтверждения оплаты пакета/своего набора баланс в шапке (`useSessionStore.balance`) пополняется на число купленных консультаций (`qa`).** Баланс — это счётчик только для `qa` (см. `BalanceIndicator`/`consultationsLeft`, Stage 0), не кошелёк по всем услугам, поэтому покупка пакета из одних документов баланс не меняет — это ожидаемо, не баг. Чтение/запись — через `useSessionStore.getState()` (не через реактивный селектор), тот же паттерн, что уже используют `usePaymentModalStore.getState().open(...)` в `useChatThread.ts`, — актуальное значение на момент подтверждения, а не значение на момент рендера хука.

**Цены услуг (`qa`/`doc` = 2900/4900 ₸) продублированы в `features/chat/mocks.ts` и `features/tariffs/mocks.ts`, а не вынесены в общий модуль.** Это осознанно, а не забытый рефакторинг: `PLAN.md` §5 требует, чтобы Stage 1-4 работали независимо друг от друга на своих моках; общий источник появится только в Stage 6 (`/tariffs`), и тогда оба места заменятся реальным запросом одновременно, а не через промежуточный shared-мок, который всё равно исчезнет.

**`ServiceId`/`PriceTable`/`BundleItem`/`BundleTariff` переехали из `features/tariffs/types.ts` в `shared/types/tariff.ts`, формула скидки (`computeBundlePrice`/`computeItemsSubtotal`) — из `features/tariffs/pricing.ts` в `shared/lib/tariffPricing.ts`.** Это ровно тот момент, который уже был предсказан записью в «Общем словаре FE↔BE» при реализации Stage 3 ("переедет в shared/types, когда Settings→Tariffs/Stage 4b тоже введёт услуги") — публичные тарифы (Stage 3) и админский CRUD тарифов (Stage 4b) оперируют одними и теми же сущностями с двух разных экранов, а не двумя независимыми доменами (в отличие от цен из мока выше, которые остаются раздельными до Stage 6). `features/tariffs/types.ts`/`pricing.ts` **реэкспортируют** промотированные имена — ни один вызывающий код Stage 3 (`useTariffs.ts`, `components/*`, `pricing.test.ts`) не переписывался. Тесты на саму формулу скидки — тоже переехали, в `shared/lib/tariffPricing.test.ts`; `features/tariffs/pricing.test.ts` оставляет только то, что там реально определено (`computeCustomOrderPrice`/`quantityOf`). Админский `Bundle` (Settings) — не псевдоним `BundleTariff`, а `BundleTariff & { name: string }`: у Stage 3 имя тарифа — фиксированный demo-текст по `id` из `locales.ts#bundleName`, у админки имя вводит человек и хранить его негде, кроме самой сущности.

**Guard на несохранённые изменения — общий `shared/stores/useUnsavedChangesStore.ts`, а не блокировка роутинга.** Роутинг собран на декларативном `<Routes>` (`app/router.tsx`), не на data-роутере (`createBrowserRouter`), поэтому `useBlocker` из `react-router` недоступен (кидает ошибку вне `RouterProvider`) — мигрировать весь роутинг ради одной формы на Settings было бы явно непропорционально. Вместо этого: любая форма зовёт `useUnsavedChangesStore.getState().setDirty(isDirty, message)` (пример — `usePromptsForm.ts`, сбрасывает на `false` и при успешном сохранении, и в cleanup при размонтировании — иначе флаг мог бы "залипнуть", если экран ушёл не через `guard`); `Header.tsx`/`MobileNav.tsx` перехватывают клик по нав-ссылке и, если `isDirty`, зовут `.guard(action, copy)`, который открывает общий `ConfirmModal` и выполняет переход только после согласия; `SettingsPage.tsx` использует тот же `guard(...)` при смене вкладки. Дополнительно — `shared/hooks/useUnsavedChangesGuard.ts` вешает нативный `beforeunload` (закрытие/обновление вкладки браузера — единственный случай, который `guard()` не покрывает). Copy для confirm — общая (`shared/locales/nav.ts#unsavedTitle/unsavedConfirm/unsavedCancel`), текст причины (`message`) — от конкретной формы. Следующая форма с несохраняемым состоянием — использует этот же стор, не пишет свой `beforeunload`/свою confirm-модалку.

**`Tabs` получил проп `layout?: "column" | "sidebar"`.** До Stage 4 был только один вариант (вертикальный список, History фильтры такого не используют). Settings — первый экран с боковыми табами на `lg` (`FRONT_DESIGN_SYSTEM.md` §7), которые на мобильном должны стать горизontальным скроллящимся рядом (боковой колонке негде поместиться) — новый `variant`-проп, а не className-переопределение layout (правило «className — только для добавления»).

**Второй реальный потребитель RHF + Zod (после того, как они лежали в зависимостях с Stage 0 неиспользуемыми) — `usePromptsForm.ts` и `useBundleForm.ts`.** Оба — обычный `useForm` + `zodResolver`; `useBundleForm.ts` дополнительно показывает паттерн для степпера внутри RHF-формы — `Controller` вокруг `QuantityStepper` (компонент сам не завязан на RHF, `Controller` — единственное место, которое об этом знает). Ошибка на уровне всей формы (zod `.refine` с `path: ["quantities"]`, "добавьте хотя бы одну услугу") типизируется react-hook-form неоднозначно для record-полей (`.message` резолвится в `FieldError`, а не `string`, из-за индексной сигнатуры) — приводим явным `as { message?: string }` с комментарием на месте, не боремся с типами `FieldErrors` глубже.

**Админские `services`/`bundles` (Settings→Tariffs) инициализируются из мока текущего языка один раз (`useState(() => MOCK[lang])`), без пересборки при смене `lang`.** Это отличается от контента чата/тарифов, который специально пересобирается по языку при каждом рендере (см. запись про `AssistantChatMessage.replyKind` выше) — там контент не редактируется пользователем, здесь — редактируется (это админская форма). Пересборка по `lang` молча стёрла бы несохранённые правки админа при переключении RU/KZ. Плата за это — при переключении языка после правки текст останется таким, каким его ввёл админ, а не переведётся; это осознанный компромисс (данные важнее демо-перевода), не забытый кейс.

**Видимый фокус для составного текстового поля без собственной рамки — `focus-within:border-accent` на контейнере, не `outline` на самом поле.** `Input`/`Textarea`/`Select`/`QuantityStepper` — все с собственной рамкой, у них `outline-none` + `focus:border-accent` на самом элементе. `Composer` (Chat) — единственное текстовое поле, вёрстка которого не даёт полю своей рамки (оно сидит внутри общей «таблетки» с кнопками-иконками) — рамка есть только у контейнера, поэтому фокус вешается через `focus-within` на него, а не на `<textarea>`. Следующее составное поле с похожей вёрсткой (поле + кнопки в одном обрамлении) — тот же паттерн, не `outline` на внутреннем элементе (визуально он ничего не даст — рамки у него нет).

**app-shell-строки, которые не принадлежат ни одной фиче (`app/NotFoundPage.tsx`, `app/ErrorBoundary.tsx`, `aria-label` шапки/таб-бара, close-label тоста) — тот же `shared/locales/nav.ts`, что уже хранит `unsavedTitle` и т.п., не новый словарь.** До Stage 5 в `nav.ts` просто не было повода класть туда что-то, кроме шапки — аудит нашёл, что 404/ErrorBoundary были захардкожены на русском с самого Stage 0 и никогда не переключались по `lang`. Классовый `ErrorBoundary` не может звать `useLangStore(selector)` как хук — читает `useLangStore.getState().lang` в `render()`, тот же non-reactive паттерн, что уже используют точечные чтения стора вне реактивного цикла (см. запись про баланс после оплаты выше) — оправдан здесь тем же: экран ошибки рендерится один раз за случай падения, а не по каждому изменению языка.

**Решения/правки по ходу (стоит знать, если возвращаться к этому коду):**

- `vitest` поднят с `^2.1.8` до `^5.0.1`, `react-router-dom` с `^6.28.1` до `^7.18.4` — исходно запиненные версии тянули уязвимый транзитивный `vite@5`/старый `react-router` (`npm audit`: 1 critical, 1 high, 5 moderate, все в дев-тулинге + один open-redirect в react-router). После апгрейда — 0 уязвимостей. Публичный API обеих библиотек, который мы используем, не изменился.
- В `tailwind.config.ts` **нет** `darkMode` — тема целиком на CSS-переменных (`bg-surface` = `var(--surface)`, которая сама меняется по `[data-theme]`), Tailwind-вариант `dark:` нигде не используется. Включать `darkMode` без единого `dark:`-класса в коде — точно тот мусор, которого договорились избегать.

Взят паттерн статус-бейджа из самого прототипа (Zan.dc.html:898).
- `FRONT_DESIGN_SYSTEM.md` §5 поправлен во время имплементации: было два имени переменной (`--shadow-card` / `--shadow-card-dark`), стало одно имя, переопределяемое под `[data-theme="dark"]` — как у всех остальных токенов.

## Деплой

Фронтенд — чистый SPA-билд (`frontend/dist/`), без SSR. Ничего специфичного под конкретный хостинг пока не добавлено (решили не выбирать платформу заранее, см. `PLAN.md` §9) — но следующее нужно решить **до первого деплоя**, кто бы его ни делал:

1. **SPA fallback обязателен.** Роутинг — `react-router-dom` (`BrowserRouter`, клиентская история). Прямой заход/обновление страницы на `/history`, `/tariffs`, `/settings` (не `/`) должен отдавать `index.html`, а не 404 от хостинга. Конкретная реализация зависит от платформы:
   - Vercel — `vercel.json` с rewrite `"/(.*)" → "/index.html"`
   - Netlify — `frontend/public/_redirects` с `/* /index.html 200`
   - Nginx/свой сервер — `try_files $uri /index.html;`
     Файл добавляется в `frontend/`, когда платформа выбрана — не раньше (см. `FRONT_CODING_STANDARDS.md` §3: не тащить конфиг под то, что не используется).
2. **Обязательные env-переменные на хостинге** (панель проекта, не файл — `.env` не коммитится):
   - `VITE_API_BASE_URL` — **обязательна**. Без неё приложение намеренно падает с понятной ошибкой при первом запросе к API (`shared/lib/env.ts`), а не молча шлёт запросы на `"undefined/..."`. Если после деплоя пусто/белый экран при переходе на функциональность — первое, что проверять.
   - `VITE_ENABLE_VERBOSE_LOGS` — опциональна, по умолчанию `false` (на реальном проде оставлять `false`, см. `FRONT_CODING_STANDARDS.md` §4.1).
3. **CORS — со стороны бэкенда, реализовано Stage 8** (`internal/httpserver.CORS`, `CORS_ALLOWED_ORIGINS` — env, точные origin'ы через запятую, см. `.env.example`). ⚠️ Требует действия и от фронта: сессия — httpOnly-cookie (`session_middleware.go`), а `apiFetch` (`shared/lib/api.ts`) сейчас **не** передаёт `credentials: "include"` — при разных origin'ах фронта/бэка браузер не отправит cookie кросс-доменно, и всё, что требует сессии, будет отвечать 401 несмотря на корректный CORS. Один из трёх вариантов до деплоя на разных origin'ах: (а) добавить `credentials: "include"` в `apiFetch` — тогда backend уже готов (именно поэтому `Access-Control-Allow-Credentials`, а не wildcard-origin); (б) держать фронт и бэк за одним доменом (reverse-proxy по пути, `/api/*` → backend) — CORS вообще не участвует; (в) на вебе перейти на `Authorization: Session <token>` вместо cookie (бэк это уже поддерживает, `session_middleware.go`). Выбор — за фронт-командой, бэк не блокирует ни один вариант.
4. **Root directory / build command**, если хостинг настраивается через UI:
   - Root directory: `frontend`
   - Install: `npm install` (или `npm ci` в CI)
   - Build: `npm run build`
   - Output: `dist`
   - Node: `^20.0.0 || >=22.0.0` (см. `engines` в `frontend/package.json`, совпадает с требованием Vite 6)
5. **Логи с фронта** (`/logs/client`, `shared/lib/logger.ts`) идут на тот же `VITE_API_BASE_URL` — отдельный эндпоинт настраивать не нужно, но бэк должен принимать `POST /logs/client` без авторизации (или с той же сессионной, что и остальные роуты — зависит от решения по §5 «Открытых вопросов» ниже).
