# Zan — единая инструкция проекта

Этот файл — единственный документ проекта (все остальные `.md`-файлы, включая `BACKEND_PLAN.md`, `BACKEND_CODING_STANDARDS.md`, `BACKEND_LOG.md`, `PLAN.md`, `FRONT_CODING_STANDARDS.md`, `FRONT_DESIGN_SYSTEM.md`, `backend-roadmap.md`, `zan-backend-tz-v2.md`, `zan-backend-tz-v3.md`, консолидированы сюда и удалены). Код по-прежнему ссылается на них в комментариях по имени и разделу (`"BACKEND_CODING_STANDARDS.md §1.2"`, `"BACKEND_PLAN.md Stage 5"` и т.п.) — эти ссылки теперь мёртвые (файлов не существует), сознательное решение при консолидации: не переписывать сотни комментариев в коде ради переименования. Смысл ссылки в подавляющем большинстве случаев понятен по контексту метки (`Stage N`, `§N`) и разделам этого файла ниже.

**Структура репозитория (монорепо):** `frontend/` (React/TS SPA), `backend/` (Go, ядро — сессии, биллинг, треды, вызов LLM), `helper/` (Python, ML-задачи — извлечение текста, STT, рендер документа, RAG), `proto/` (общий protobuf-контракт Go↔Python), `openapi/openapi.yaml` (контракт Go↔Frontend), `scripts/` (smoke/load-тесты, Postgres bootstrap-роли), `design/` (`Zan.dc.html` — исходный интерактивный прототип, единственный файл со всеми экранами; `support.js`/`.thumbnail` — его ассеты). Пути вида `shared/lib/api.ts` — относительно `frontend/src/`, если не указано иное.

## ⚠️ Правило

Этот файл обновляется **после каждого значимого изменения**, не в конце проекта: новая стадия, новый паттерн/конвенция, отход от зафиксированного решения. Если решение меняет что-то из зафиксированного ниже — правится этот же файл в том же коммите/PR, а не оставляется расходиться с реальностью. Правило "чистая замена, а не наслоение" (см. «Конвенции обеих команд» ниже) применяется и к самой документации: устаревшая конвенция удаляется/обновляется, не остаётся рядом с новой как история.

## 1. Продукт

**Zan** — юридический ассистент для жителей Казахстана (Q&A по законодательству РК с цитированием статей + генерация документов). Аудитория — обычные люди без юридического образования, обращаются нечасто (не ежедневно) → интерфейс и ответы должны быть понятны с первого захода, без канцелярита и без обучения. Эмоция дизайна — доверие и спокойствие (тема тревожная для пользователя, интерфейс не должен пугать). Mobile-first, полностью адаптивно, светлая/тёмная тема, RU/KZ.

**Основные функциональные блоки:**

- **Чат-тред** с ассистентом — не разовая форма "вопрос→ответ", а полноценный диалог. Ввод текстом/голосом (STT, редактируемо перед отправкой)/файлом (анализ вложенного документа). Ответ — простой текст + сворачиваемый блок источников (статьи закона) + 👍/👎. Быстрые темы на пустом экране для новых пользователей.
- **Генерация документов** (заявление, претензия, договор и т.д.) на основе диалога — отдельная платная операция, результат — PDF и DOCX на скачивание. Решение продукта: явного UI-переключателя "подготовить документ" нет — определяется бэком по контексту сообщения.
- **История обращений** — список тредов со статусами (`queued`/`processing`/`clarify`/`done`/`error`/`canceled`), поиск, фильтр по статусу и по периоду, удаление (soft delete).
- **Тарифы** — услуги (`qa`/`doc`) с базовой ценой → собираемые из них бандлы со скидкой, плюс режим "свой набор" (произвольное количество без готового тарифа). Оплата — mock (без реальной интеграции платёжного шлюза на этом этапе).
- **Настройки** (пока доступны всем — заглушка `useRole()`, реальных ролей пользователей в системе нет и не планируется в этом скоупе) — 3 вкладки: Промпты агентов (редактируемый текст без деплоя), Тарифы-админ (CRUD услуг/бандлов), Аналитика (агрегаты по тредам).

**Явно вне скоупа:** реальный платёжный шлюз, полноценная авторизация/аккаунты/роли пользователей (сессии вместо неё — `session_id`, без логина), перенос баланса/истории между устройствами (следствие отказа от аккаунтов — осознанный компромисс, не забытый баг), инлайн-редактирование сгенерированного документа, многопользовательские аккаунты/командная работа, централизованная система сбора логов (Loki/ELK — предполагается, инструмент не выбран).

## 2. Архитектура и стек

Монорепо: `frontend/` реализован, `backend/` (Go, ядро — весь публичный трафик и генерация ответа LLM) + `helper/` (Python, специализированные ML-задачи без генерации ответа) связаны общим `proto/`-контрактом (gRPC). Публичный контракт Go↔Frontend — REST/JSON, `openapi/openapi.yaml` (contract-first, единственный источник правды для путей/схем/enum'ов).

### Frontend

| Область | Выбор | Почему |
|---|---|---|
| Сборка | Vite + React 18 + TypeScript (`strict`, `noUncheckedIndexedAccess`) | Быстрый dev-цикл |
| Роутинг | React Router v6/v7, lazy per-page | Каждая страница — свой чанк |
| Стили | Tailwind CSS поверх CSS-переменных темы (`shared/styles/tokens.css`) | Прототип уже на CSS-токенах — формализуем, не переизобретаем |
| Состояние UI | Zustand, отдельные независимые слайсы (тема/язык/сессия/модалки) | Не общий 20-полей `state`, как в прототипе |
| Серверное состояние | TanStack Query | Кэш/retry/статусы из коробки |
| Формы | React Hook Form + Zod | Валидация без лишних перерендеров |
| i18n | Свой типизированный словарь, отдельный на фичу (`feature/locales.ts`), НЕ библиотека | Всего 2 языка — `i18next` избыточен |
| Иконки | `lucide-react` (SVG, не emoji) | Нужны `aria-label`/масштабируемость |
| Тесты | Vitest + React Testing Library | Юнит на бизнес-логику + RTL на сценарии |
| HTTP-клиент | Тонкая обёртка над `fetch` (`shared/lib/api.ts`) | `X-Trace-Id` сквозной, автологирование, не тянуть axios |

### Backend (Go)

| Область | Выбор | Почему |
|---|---|---|
| Роутер | `gin` | Middleware-цепочка под каталог ошибок |
| Доступ к БД | `pgx` напрямую, **без codegen** (было `pgx`+`sqlc`, снято по запросу пользователя) | SQL остаётся SQL — нужен `SELECT ... FOR UPDATE` для атомарного списания баланса, тяжёлый ORM это прячет |
| Миграции | `golang-migrate` (отдельный CLI) | Не завязан на рантайм приложения |
| Конфигурация | `caarlos0/env/v11`, один файл `internal/config`, без глобального синглтона | — |
| Логирование | `log/slog` (JSON-хендлер) | Контракт §5 ниже |
| Связь с Python | gRPC (`google.golang.org/grpc`), клиентские interceptor'ы для ретраев/breaker/лога/trace-id | Внутренний трафик самый частый и чувствительный к латентности — protobuf/HTTP2 дешевле JSON/HTTP1.1, строгий контракт ловит рассинхрон на сборке |
| HTTP-клиент к LLM | Обёртка над `net/http.Client`, ретраи+backoff+circuit breaker (`sony/gobreaker`) | **OpenAI API** (изначально был Anthropic, заменён по запросу пользователя — см. «Смена LLM-провайдера» в §8) |
| Codegen protobuf | `buf` (`buf generate`/`buf lint`/`buf breaking` в CI) | Единая точка генерации Go+Python, `buf breaking` ловит несовместимые изменения на PR |
| Аутентификация сессии | opaque-токен: `session_id` (UUID) + HMAC-SHA256 подпись, без персональных данных | JWT-подобный, но без пользовательских данных внутри — 20 строк `crypto/hmac`, не библиотека |
| Файлы | S3-совместимый клиент (`aws-sdk-go-v2`), MinIO локально/в docker-compose | — |
| Rate limiting | `golang.org/x/time/rate`, in-memory per-IP/per-session | MVP single-instance; вынести в Redis, если деплой станет multi-instance — явно зафиксированное ограничение, не забытый недостаток |
| Тесты | `testing`+`testify` + `testcontainers-go` (реальный Postgres) | Юнит без сети/БД, интеграционные — реальный Postgres, не моки SQL |

### Helper (Python)

| Область | Выбор | Почему |
|---|---|---|
| Сервер контракта | `grpc.aio` — весь бизнес-контракт Go↔Python на gRPC, не REST | Асинхронный сервер под I/O (эмбеддинги, OCR, внешние STT) |
| HTTP рядом с gRPC | Тонкий `starlette`+`uvicorn` только под `GET /healthz` | gRPC health-checking избыточен для docker-compose/k8s liveness на этом масштабе |
| Схемы | Protobuf из `proto/` — единственный источник правды wire-формата; Pydantic — только для внутренней валидации | Нельзя случайно разойтись с Go — оба генерируются из одного файла |
| RAG | `pgvector` (расширение на том же Postgres, отдельная схема `rag`, отдельная роль `zan_rag`) + self-hosted embeddings (`fastembed`/ONNX, `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, 384 измерения) | Одна инфраструктура вместо отдельного vector DB на MVP-масштабе; self-hosted — не заводить внешний платный API ради одного RPC, когда тот же паттерн уже принят для STT |
| pgvector-индекс | HNSW, не IVFFlat | IVFFlat требует параметр `lists`, посчитанный от размера корпуса заранее — не подходит, когда сид-корпус растёт непредсказуемо |
| Извлечение текста | PyMuPDF (PDF), python-docx (DOCX), pytesseract+pdf2image (OCR-фолбэк для сканов) | Стандартный набор без внешних платных API |
| Рендер документа | `docxtpl` (DOCX из шаблона), `WeasyPrint` (HTML→PDF) | Не нужен headless-браузer ради PDF |
| STT | `faster-whisper` (self-hosted) за интерфейсом `SttProvider` | Открытый вопрос продукта не закрыт — архитектура должна допускать оба варианта (self-hosted/внешний API) без переписывания вызывающего кода |
| Внутренняя аутентификация | shared secret в gRPC-метадате (`x-internal-secret`) + сеть закрыта (docker network/VPC) | Вторая линия обороны, не единственная |
| Логирование | `structlog`, тот же JSON-контракт, что Go | Один агрегатор логов должен склеивать цепочку по `trace_id` |

### Общая инфраструктура

- **Postgres — один инстанс, две схемы, две БД-роли**, полностью симметрично изолированные (см. готчу в §8). `core` (все таблицы бизнес-домена — Session/Service/Tariff/UserCredit/Payment/Thread/Message/FileAttachment/AgentPrompt) — владеет и мигрирует только Go, роль `zan_core`. `rag` (векторный индекс НПА) — владеет и мигрирует только Python (Alembic), роль `zan_rag`. Ни одна роль не имеет прав на чужую схему.
- **`proto/` в корне** — единственный источник правды контракта Go↔Python, не принадлежит ни одному сервису по отдельности. Один `.proto`-файл на доменный сервис (`rag.proto`, `files.proto`, `documents.proto`, `stt.proto`, `common.proto` — общие типы). Пакет — `zan.rpc.v1` (**не** `zan.internal.v1` — см. готчу в §8). Payload — файлы/аудио передаются по ссылке (`file_url` на собственный S3, не байтами в сообщении) — избегает лимита на unary-сообщение gRPC и необходимости стриминга.
- **`docker-compose.yml` в корне** — `postgres` (pgvector), `minio`, `clamav`, `backend`, `helper`. Один `docker compose up` поднимает весь стек.
- **Трассировка `trace_id`** — сквозная, два механизма на двух хопах: фронт→Go — HTTP-заголовок `X-Trace-Id`; Go→Python — та же величина в gRPC-метадате (`x-trace-id`), interceptor на обеих сторонах, не руками в каждом вызове. Go генерирует `trace_id`, если фронт не передал.
- **Схема БД — единый читаемый референс `backend/schema.sql`** (не инструмент — `golang-migrate` по-прежнему работает только с `backend/migrations/*.sql`), обновляется в том же PR, что и любая миграция, меняющая схему `core`. Снимок текущего состояния, не журнал `ALTER`'ов — формат правки: комментарий "что изменилось и почему/ссылка на миграцию", сразу под ним сам SQL в финальном виде.

### Ключевая бизнес-логика (реализовано, не пересказ ТЗ)

- **Услуги/тарифы.** `Service` — источник правды по базовой цене; смена цены в админке не пересчитывает уже оформленные платежи, только новые `checkout`. `Tariff` — фиксированный набор `{service_id, qty}` + скидка, цена всегда считается на лету по формуле (округление до 10 тенге), не хранится статично — не расходится при смене цены услуги. Формула **побитово совпадает** между Go (`internal/service/pricing`) и фронтом (`shared/lib/tariffPricing.ts`) — при любой правке формулы менять оба места. Режим "свой набор" — `qty` 1–20 на услугу, без скидки.
- **Баланс.** Успешный `confirm` для `kind IN (tariff, custom)` → `UPSERT UserCredit(session_id, service_id) quantity += qty`. `POST /threads {service_id}`: баланс > 0 → списать 1 сразу, `is_paid=true`, обработка стартует немедленно; баланс = 0 → тред создаётся `is_paid=false`, клиент оплачивает (`checkout {kind:single_service, items:[{service_id,qty:1}], thread_id}`) → после `confirm` баланс начисляется и сразу списывается. Списание — атомарно, `SELECT ... FOR UPDATE` (гонка на последней единице баланса — второй запрос видит 0 после первого). **Возврат при ошибке**: `status=error` → списанная единица возвращается на баланс — но только если тред ещё ни разу не получил успешный ответ (`refundEligible` = статус до этого раунда обработки != `Done` — повторное бесплатное уточнение после уже состоявшегося успешного ответа при ошибке кредит не возвращает: услуга уже была оказана один раз).
- **Бесплатные уточнения.** После `is_paid=true` → `free_until = paid_at + N часов` (дефолт 72ч, ENV-конфигурируемо). Пока `now() < free_until` — новые сообщения в тред бесплатны. Закрытие треда по истечении `free_until` — **ленивое** (on-access при следующем обращении, не отдельная фоновая задача — в отличие от просроченных `pending`-платежей, которым фоновая задача обязательна, иначе их никто не переведёт в `failed`).
- **Генерация документа** — всегда отдельная операция (не "тип треда"), доступна из любого треда, использует ту же логику списания с `service_id="doc"`. Рендерятся **оба** формата (PDF+DOCX) за один вызов, не по требованию — LLM вызывается ровно один раз на генерацию. Неуспех рендера **после** того, как текстовый ответ уже сохранён в чате, не откатывает уже сохранённое — изолированный результат `(message, filesReady bool, error)`, `doc`-кредит возвращается отдельно.
- **Вызов LLM-агента.** Промпт — `AgentPrompt(qa)` для обычного треда, `AgentPrompt(document)` для генерации документа; подтягивается из БД на каждый вызов без кеша (правки в `/admin/prompts` применяются сразу). В контекст — вся история сообщений треда + текст из вложенных файлов. Ожидаемый структурированный ответ: `{answer_text, sources:[{ref,quote}], findings:[{title,body}], needs_clarification}`. `needs_clarification=true` → статус треда `clarify` (не ошибка, кредит не возвращается). Технический контракт JSON-формата ответа **не** хранится в редактируемом `AgentPrompt` и не редактируется через админку — правка текста промпта продуктом/юристами не должна иметь возможности сломать парсинг ответа.
- **Верификация источников** — отдельная чистая функция `verifySources(llmSources, ragMatches) → unverified_sources bool`: сверяет то, что процитировала LLM, с тем, что реально вернул RAG (регистронезависимо) — защита от "галлюцинации закона" (LLM цитирует несуществующую статью). Пустой список источников от LLM → `false` (нечего проверять). Любая ошибка RAG (не только явная недоступность) — деградация Go-стороны: вызов LLM продолжается без источников, `sources_degraded=true` в логе — RAG никогда не единственная причина, по которой пользователь не получил ответ.

## 3. Конвенции обеих команд (обязательны, критерии ревью)

Правила ниже одинаковы по духу для `frontend/` и `backend/`+`helper/` — где отличается конкретика (Go vs TS/Python), указано отдельно.

### 3.1 Архитектурные слои

**Frontend:**
```
app/        → знает про всех
features/   → знает только про shared, НЕ знает про другие features
shared/     → не знает ни про app, ни про features
```
`features/a` никогда не импортирует напрямую из `features/b` — общий кусок функциональности переезжает в `shared/`. Компонент страницы (`ChatPage.tsx`) — точка входа фичи, почти без логики. Разделение логика/рендер: нетривиальная логика — в хуках, компонент только рендерит готовые значения.

**Backend (Go, порты-и-адаптеры облегчённо, без DI-фреймворка):**
```
cmd/api/              → composition root: main(), сборка зависимостей руками
internal/httpserver/  → тонкий: gin-хендлеры — парсинг, вызов service, маппинг ошибки → HTTP
internal/service/     → бизнес-логика, определяет интерфейсы репозиториев/клиентов, которые ей нужны
internal/domain/      → чистые типы, НЕ импортирует gin/pgx/grpc
internal/repo/        → репозитории поверх pgx напрямую
internal/grpcclient/  → клиент к helper/
internal/agent/       → промпт + HTTP-клиент к LLM + парсинг ответа
internal/platform/    → logger, storage(s3), resilience, clock, idgen — без бизнес-логики
internal/genproto/    → сгенерировано buf, не редактируется руками
```
Интерфейсы объявляются **там, где используются** (`internal/service`), не там, где реализованы — идиоматичный Go, реализация в `repo`/`grpcclient`/`agent` просто удовлетворяет уже объявленный интерфейс структурно. `internal/repo` — без codegen и без `.sql`-файлов: SQL — строковый литерал прямо в методе (исключения: конвертация pgx↔domain и тип-строка под `Scan` — не запрос). Один и тот же `SELECT`, нужный в двух функциях — дублируется текстом в каждой, не выносится в общий хелпер.

**Helper (Python):**
```
app/grpc/servicers/   → тонкий: валидация protobuf, вызов app/services, маппинг исключения → grpc.StatusCode
app/services/         → бизнес-логика, зависит от Protocol (структурная типизация), объявленных в том же пакете
app/adapters/         → доступ к внешнему миру (db, storage, providers)
app/domain/           → dataclass/pydantic-модели, НЕ те же классы, что из .proto
app/genproto/         → сгенерировано, не редактируется
```
Protobuf-классы не "протекают" дальше `app/grpc/servicers` — конвертация на границе сервисера.

### 3.2 Состояние

**Frontend:** локальное компонента — `useState`/`useReducer`; кросс-компонентное — Zustand-стор в `shared/stores`; серверные данные — TanStack Query; форма с валидацией — RHF+Zod. Никогда не дублировать серверные данные в Zustand/useState "для удобства" — один источник истины; производные данные — `useMemo`, не отдельное поле state.

**Backend:** конфигурация — загружается один раз в `main()`, передаётся явно через конструкторы, без глобального синглтона. Пул БД — один на процесс, из composition root. Request-scoped — `context.Context`(Go)/`contextvars`(Python). Состояние между запросами внутри процесса (rate limiter, circuit breaker) — явная структура с мьютексом/атомиком, поле в composition root, **не package-level `var`**. Данные из БД — читаются заново на каждый запрос, не кешируются без явного TTL (`AgentPrompt` — намеренно без кеша).

### 3.3 Правило "чистая замена, а не наслоение" — ключевое, без исключений

При **любом** изменении подхода (смена паттерна/рефакторинг/замена библиотеки): в этом же PR удаляются **все** места старого способа в затронутом коде, старая реализация убирается полностью (функции/типы/стили/тесты/неиспользуемые импорты/feature-флаги) — ничего не остаётся "на всякий случай" или закомментированным. Похожий старый код — в git-истории, не в закомментированном блоке. `TODO` — только с привязкой к issue, не переживает больше одного PR-цикла без решения. Временное сосуществование двух подходов — допустимо **только** если явно объявлено в PR и зафиксировано здесь как временное, с условием исчезновения. **Ревью:** PR, добавляющий новую реализацию рядом со старой того же назначения — возвращается автору. (Backend: сгенерированный код `internal/genproto`/`app/genproto` не редактируется руками никогда — меняется `.proto` и перегенерируется.)

### 3.4 Логирование

Цель — по логам восстановить всю цепочку одного запроса без переспрашивания пользователя.

**Единая точка:** Frontend — `shared/lib/logger.ts` (`debug/info/warn/error`), `no-console` в ESLint везде кроме него. Backend — один `*slog.Logger`(Go)/`structlog`(Python), обогащается `trace_id`/`session_id` в middleware, кладётся в контекст; сервисы достают из контекста, не создают свой. Сырой `console.log`/`fmt.Println`/`print()` в бизнес-коде — запрещён.

**Автоматически:** HTTP-клиент фронта и gRPC client/server interceptor'ы бэка сами логируют старт/успех/ошибку каждого запроса (длительность, `trace_id`) — разработчик **не должен** руками логировать сам факт похода в сеть.

**Руками, по месту:** значимые действия пользователя (отправка сообщения, покупка, удаление, сохранение промпта), нетривиальные переходы состояний, открытие/закрытие платёжной модалки. **Ни одного пустого `catch`/проигнорированного `err != nil`/`except: pass`** — минимум `logger.error`/явное задокументированное решение, что ошибка безопасна.

**14 этапов одного Q&A-запроса** (`backend-roadmap.md §6.2`, таблица-источник для `internal/service/thread`+`internal/agent`, не сокращается вольно): `request_received` → `balance_checked` → `payment_required`/`payment_confirmed` → `thread_status_changed` → `file_extract_started/completed` → `stt_started/completed` → `rag_search_started/completed` (matches_count, degraded) → `llm_call_started` (agent_type, prompt_version-хэш, sources_count_in_context) → `llm_call_completed` (success/fail, needs_clarification, unverified_sources) → `document_render_started/completed` → `message_saved` → `thread_status_changed`(финал) → `credit_refunded` (только при error) → `response_sent`.

**Формат записи** (JSON, оба сервиса): `{timestamp, level, service: "go-core"|"python-agent", trace_id, session_id, stage, message, context}`.

**Уровни:** `DEBUG` — только dev, детали промптов/сырых ответов LLM. `INFO` — штатные переходы. `WARN` — восстановимые сбои (сработал ретрай, файл не распознан, но обработка продолжилась). `ERROR` — операция отказала, пользователь увидел ошибку, данные скорректированы (возврат кредита). `CRITICAL` — инфраструктурный сбой всего сервиса (Python недоступен целиком, БД недоступна).

**Никогда не логировать:** полный текст пользовательских сообщений/документов на INFO+ в проде (только DEBUG/dev), данные оплаты сверх `payment_id`/`amount`, PII сверх `session_id`.

**`trace_id`** — генерируется один раз на пользовательское действие, передаётся сквозь весь запрос (фронт: `X-Trace-Id`; Go→Python: та же величина в gRPC-метадате) — не создавать новый на каждый внутренний вызов одной операции.

### 3.5 Naming

**Frontend:** компоненты `PascalCase.tsx`, тест рядом `PascalCase.test.tsx`; хуки `useXxx.ts`; типы `PascalCase` в `types.ts`; булевы — `is`/`has`/`can`/`should`; обработчики-пропсы `onXxx`, внутренние `handleXxx`; константы `UPPER_SNAKE_CASE`; моки — `*.mocks.ts`.

**Backend Go:** пакеты короткие строчные без "stutter" (`thread.Repository`, не `thread.ThreadRepository`); файлы `snake_case.go`; экспортируемые — `PascalCase` с doc-комментарием от имени идентификатора; интерфейсы — по поведению (`-er` для односигнатурных, существительное для доменных — `ThreadRepository`, не `IThreadRepository`); конструкторы `NewXxx(...)`; ошибки — sentinel `ErrXxx`, оборачиваются `fmt.Errorf("...: %w", err)`, проверяются `errors.Is`/`errors.As`; булевы — `is`/`has`/`can`; **константы — `PascalCase`/`camelCase`, НЕ `UPPER_SNAKE_CASE`** (отличие от TS — не идиоматично в Go, `golangci-lint` ругается).

**Python (`helper/`):** PEP 8 — `snake_case` функции/переменные, `PascalCase` классы, **`UPPER_SNAKE_CASE` модульные константы** (здесь, в отличие от Go, это идиома); файлы `snake_case.py`; type hints обязательны на публичных функциях (`mypy --strict`); Pydantic-модели без обёрточного суффикса, если тип однозначен по контексту пакета.

### 3.6 TypeScript / Go-языковые правила

**TS:** `strict: true`, `any` запрещён без комментария-обоснования. Публичные сигнатуры хуков/утилит — явные типы возврата. Состояния загрузки — discriminated union (`{status:"idle"|"loading"|"success",data}|{status:"error",error}`), не россыпь булевых флагов.

**Go:** `context.Context` — всегда первый параметр I/O-функции, никогда не поле структуры. Ошибка не игнорируется молча без комментария почему. `panic` — только программистские ошибки на старте или в тестах; в пути обработки запроса — только `recover()` на верхнем middleware. Множественные булевы/nullable вместо явного статуса — запрещены там, где состояние взаимоисключающее (пример — `AgentResult{Status, AnswerText, Err}` вместо трёх независимых полей). `go vet`/`staticcheck`/`golangci-lint` обязательны на PR.

**Python:** `mypy --strict` в CI без `# type: ignore` без комментария. Все I/O в `adapters`/`services` — `async`, блокирующий синхронный вызов (`pytesseract`) — оборачивается `asyncio.to_thread`. Исключения — своя иерархия в `app/domain/errors.py`, маппятся на границе сервисера явной таблицей, не пробрасываются как есть. `ruff` (линт+формат) в CI.

### 3.7 Стили (frontend)

Все значения — из design-токенов (§4 ниже) через Tailwind-классы; сырой hex/инлайн `style={{color:...}}` в JSX фичи — запрещён. `className`-проп UI-кита — только для добавления, не переопределения внутренних размеров/цветов (нет `tailwind-merge`) — другой размер/цвет = новый `variant`/`size`-проп компонента. Тёмная тема — те же классы поверх других значений CSS-переменных (`[data-theme="dark"]`), компонент не знает, какая тема сейчас.

### 3.8 Обработка ошибок

Общий принцип (обе стороны): пользователь никогда не видит сырую ошибку интеграции (текст исключения, стектрейс, ответ LLM как есть) — только понятная фраза на его языке. Технический контекст — только в логах.

**Backend, публичный HTTP-слой:** единый тип `apierror.Error{Code, Message, HTTPStatus}` — известные бизнес-ошибки маппятся явно в `internal/httpserver`, всё нераспознанное — `internal_error`/500 с нейтральным текстом, оригинал только в лог. Полный каталог кодов — `openapi/openapi.yaml#ApiErrorCode` (см. §6 «Общий словарь FE↔BE» — 25 кодов с фиксированным HTTP-статусом на каждый).

**gRPC-слой:** фиксированная таблица маппинга — `DEADLINE_EXCEEDED` (таймаут, Go ретраит), `UNAVAILABLE` (Python недоступен целиком, открывает circuit breaker), `INVALID_ARGUMENT` (не ретраится), `INTERNAL` (необработанный сбой, ERROR-лог) — реализуется один раз в interceptor'е, не в каждом вызывающем месте.

**Frontend:** сетевые ошибки — состояние `error` TanStack Query → единый Toast/inline, никогда не проглатываются. Каждый route — свой `ErrorBoundary` (не один глобальный) — падение одной страницы не рушит остальные.

### 3.9 Тестирование

**Frontend:** юнит — на бизнес-логику (цена, склонения, фильтры), не на JSX-разметку. RTL — на пользовательские сценарии через `role`/`label`, не `data-testid` россыпью. Тестируется поведение, не реализация.

**Backend Go:** table-driven (`testify`) на бизнес-логику без сети/БД — обязательны для каждого нового публичного метода `service`. Интеграционные — `testcontainers-go` (реальный Postgres); gRPC-клиент — `bufconn` (in-memory, без реального `helper/`). Сквозные (Go↔Python) — проверяют поведение (реальный `helper/` в docker-compose/CI), не форму сообщения (её уже гарантирует `.proto`+`buf breaking`).

**Python:** `pytest`+`pytest-asyncio`, юниты на `app/services/*` с `Protocol`-фейками (не monkeypatch внутренностей библиотек), интеграционные — реальный `grpc.aio`-сервер.

### 3.10 Git/PR

Conventional commits (`feat:`/`fix:`/`refactor:`/`chore:`/`docs:`/`test:`, backend дополнительно `proto:` для изменений `.proto`). Один PR = одна стадия/подстадия. PR, меняющий `proto/**` — явно указывает, ломает ли изменение клиентов (`buf breaking`).

## 4. Design system (frontend, зафиксированные токены)

Единственный источник значений для стилей — ничего не подбирается "на глаз" повторно в коде. Источник — `design/Zan.dc.html` (прототип уже задаёт палитру/шрифты), формализовано в `shared/styles/tokens.css`+`tailwind.config`.

**Цвет** (light/dark — оба через `[data-theme]`, одно имя переменной на оба значения): `--bg`/`--surface`/`--surface-2` (фон страницы/карточек/вложенных блоков), `--ink`/`--muted` (текст основной/вторичный, контраст ≥4.5:1 обязателен на новом использовании), `--line` (границы), `--accent`/`--accent-ink`/`--accent-soft` (акцент+текст поверх+фон акцентных блоков), `--warn`/`--warn-soft`, `--danger` (только через переменную, не отдельный "красный", не переключающийся в dark — Tailwind не режет alpha у `var(--danger)`, `bg-danger/10` не работает). Spotlight-градиент (`--spotlight-1/2/3`, `Card tone="spotlight"`) — материал только для одной "цепляющей взгляд" карточки на экран (маркетинговый акцент), не для массового использования.

**Типографика:** Manrope (UI) + IBM Plex Mono (мета — даты/статусы/цена мелким видом). Шкала: `display`(34px) → `h1`(28) → `h2`(22) → `h3`/`body-lg`(17) → `body`(15) → `body-sm`(14) → `caption`(13) → `micro-mono`(11, uppercase+letter-spacing). Минимум для читаемого текста — 13px. Базовый размер 16px, line-height 1.5.

**Spacing** — 4px-шаг: `space-1`(4) … `space-14`(56). Отступ между интерактивными элементами — минимум `space-2`(8px).

**Радиусы:** `radius-sm`(8, мелкие элементы) → `radius-pill`(999, бейджи/круглые кнопки).

**Тень** — одно имя переменной на обе темы (`--shadow-card`, переопределяется под `[data-theme="dark"]`), `--shadow-modal` фиксированная (не завязана на тему).

**Z-index:** `z-sticky`(20) < `z-composer`(15, sic — композер ниже sticky-хедера) < `z-overlay`(40, обычная модалка) < `z-overlay-high`(50, модалка поверх модалки) < `z-overlay-top`(60, confirm — всегда самая верхняя) < `z-toast`(70). Новый оверлей — выбор из таблицы, не `z-index: 9999`.

**Breakpoints (mobile-first):** base(0) → `sm`(640, композер шире) → `md`(768, полная навигация вместо таб-бара) → `lg`(1024, боковые табы Settings) → `xl`(1280, контейнер `max-width: 1080px`). Ни одна страница не даёт горизонтальный скролл на base.

**Иконки:** `lucide-react`, сетка 16/20/24px, `stroke-width: 2`. Любая icon-only кнопка — обязателен `aria-label`. Не emoji вместо иконок.

**Touch targets:** минимум 44×44px для любого интерактивного элемента, минимум `space-2`(8px) между соседними — обязательное свойство вёрстки, не только пункт аудита постфактум.

## 5. Каталог ошибок и HTTP-статусы (backend, актуальная реализация)

Полный формальный список — `openapi/openapi.yaml#ApiErrorCode` (25 кодов). Сценарии по областям (актуальны, не переопределены Stage 8 сверх кодов ошибок):

**Оплата:** несуществующий `tariff_id`/пустые `items` → 400, `Payment` не создаётся. Повторный `confirm` уже подтверждённого платежа → идемпотентно, без повторного начисления. `pending` дольше 30 минут без `confirm` → фоновая задача помечает `failed`. Мок-отказ → `status=failed`, баланс не меняется.

**Файлы:** неподдерживаемый тип → 415, размер > лимита (20 МБ) → 413, антивирус (ClamAV) пометил как опасный → файл не сохраняется + security-инцидент в лог, `Extract` не смог прочитать (битый скан) → `processing_status=error`, сообщение всё равно уходит агенту с пометкой "файл не удалось прочитать" (это `needs_clarification`, не ошибка треда).

**Голос:** лимит 15 МБ. STT-ошибка/таймаут → ошибка клиенту без создания сообщения. Тишина (пустой текст) → то же, без сообщения.

**Баланс/сессии:** гонка на последней единице — атомарное списание (`FOR UPDATE`), второй запрос получает штатный "баланс закончился". Невалидная подпись токена → 401, без автосоздания сессии.

**Инфраструктурные:** Python недоступен целиком → circuit breaker открывается после серии отказов, новые треды сразу `error` без долгого ожидания (не таймаут на каждый). БД недоступна → 503.

**Злоупотребления:** rate limiting на `POST /sessions`/`POST /threads` по IP и по `session_id` — два разных примитива (`internal/platform/ratelimit` — плавно пропускает с постоянной скоростью, никогда не запрещает один запрос навсегда; `internal/platform/bruteforce` — жёсткий стоп на весь `blockDuration` после N неудач подряд, проверяется **до** сравнения секрета, не после) — не путать, не городить одно поверх другого. Блокировка `/admin/*` после N неудачных `X-Admin-Token`.

**LLM/RAG (обработка запроса агентом):** таймаут/5xx LLM → до 2 ретраев+backoff, не помогло → `status=error`+возврат кредита. Невалидный JSON от LLM → то же. LLM процитировала не найденный RAG источник → не блокирует ответ, `unverified_sources=true`. Отказ модели/модерация → `status=error`, без показа формулировки отказа. RAG недоступен → деградация (ответ без источников, `sources_degraded=true` в логе), не блокировка. `needs_clarification=true` → `status=clarify`, не ошибка. Рендер документа упал после успешного текстового ответа → изолировано, `doc`-кредит возвращается, чат не откатывается.

## 7. Деплой

Фронтенд — чистый SPA-билд (`frontend/dist/`), без SSR. Платформа хостинга не выбрана заранее — следующее нужно решить **до первого деплоя**, кто бы его ни делал:

1. **SPA fallback обязателен.** Прямой заход/обновление страницы на `/history`, `/tariffs`, `/settings` должен отдавать `index.html`, не 404. Vercel — `vercel.json` rewrite; Netlify — `frontend/public/_redirects`; Nginx — `try_files $uri /index.html;`. Файл добавляется, когда платформа выбрана — не раньше.
2. **Обязательные env на хостинге фронта** (панель проекта, не файл): `VITE_API_BASE_URL` — обязательна, без неё приложение падает с понятной ошибкой при первом запросе (не молча шлёт на `"undefined/..."`). `VITE_ENABLE_VERBOSE_LOGS` — опционально, `false` в проде.
3. **CORS — реализовано на бэке** (`internal/httpserver.CORS`, ENV `CORS_ALLOWED_ORIGINS` — точные origin'ы через запятую, не wildcard: сессия — httpOnly-cookie, `Access-Control-Allow-Credentials: true` по спецификации нельзя сочетать с `Allow-Origin: *`). ⚠️ Требует действия и от фронта: `apiFetch` (`shared/lib/api.ts`) сейчас **не** передаёт `credentials: "include"` — при разных origin'ах фронта/бэка браузер не отправит cookie кросс-доменно, всё, что требует сессии, ответит 401 несмотря на корректный CORS. Один из трёх вариантов: (а) добавить `credentials:"include"` в `apiFetch` — бэк уже готов; (б) один домен через reverse-proxy (`/api/*` → backend) — CORS не участвует вообще; (в) на вебе перейти на `Authorization: Session <token>` вместо cookie (бэк уже поддерживает).
4. **Root directory/build**, если хостинг настраивается через UI: root `frontend`, install `npm ci`, build `npm run build`, output `dist`, Node `^20.0.0 || >=22.0.0`.
5. **Логи с фронта** (`/logs/client`) — тот же `VITE_API_BASE_URL`, эндпоинт без авторизации (только rate limit по IP — barebones anti-spam, не auth).

**Backend — обязательные ENV на хостинге** (см. .env.example для полного списка с примерами): `ADMIN_TOKEN`/`SESSION_HMAC_SECRET`/`INTERNAL_SECRET` — 32+ символов, `openssl rand -hex 32` на каждый (backend отказывается стартовать при более коротком значении или известном dev-плейсхолдере — `internal/config.validateSecrets`); `RAG_DB_PASSWORD`/`CORE_DB_PASSWORD` — пароли Postgres-ролей; `OPENAI_API_KEY` — настоящий ключ (без него агент отвечает 401/502 предсказуемо, не падает); `CORS_ALLOWED_ORIGINS` — origin фронта; остальные `S3_*`/`POSTGRES_*` — под реальную инфраструктуру (MinIO обычно заменяется на реальный S3-совместимый сервис в проде — например, Cloudflare R2/Backblaze B2/AWS S3; ключевое требование — `S3_PUBLIC_ENDPOINT` должен быть URL, реально достижимым из браузера пользователя, не внутренний адрес docker-сети/приватной сети хостинга).

**`scripts/` — что нужно на деплое, а что нет:** `scripts/postgres-init/{01-rag-role,02-core-role}.sh` — **обязательны**, монтируются в Postgres-контейнер (`docker-entrypoint-initdb.d`) и заводят обе роли на пустом томе при первом старте (не гоняются повторно на уже существующем томе — если меняете эти скрипты после первого деплоя, нужно пересоздавать том). `scripts/smoke-test.sh`/`scripts/load-test.sh` — только dev/CI-инструменты верификации, не нужны в продовом окружении. `scripts/fixtures/` — используются только `smoke-test.sh`.

**ClamAV на ARM-хостинге:** официальный образ `clamav/clamav` публикуется только под `linux/amd64`. На ARM-сервере (например, AWS Graviton) нужен либо amd64-инстанс, либо эмуляция (медленнее). На обычном x86-хостинге — не проблема.

**Зачем `openapi/openapi.yaml`, если он не деплоится:** это контракт API, не рантайм-зависимость — ничего его не читает при исполнении. Существует, чтобы фронт-команда знала точную форму запросов/ответов/enum'ов/кодов ошибок без чтения Go-исходников, и чтобы инструменты (Swagger UI/Postman/codegen) могли его импортировать.

## 8. Готчи и решения, о которых легко забыть

**`CREATE SCHEMA IF NOT EXISTS <name>;` (без `AUTHORIZATION`) требует привилегии `CREATE` на уровне БАЗЫ ДАННЫХ у вызывающей роли, даже если схема уже существует.** Postgres проверяет привилегию раньше, чем "IF NOT EXISTS". Пойман вживую при переводе backend на непривилегированную роль `zan_core` — миграция падала с `permission denied for database` на этой строке, хотя схема уже была создана `AUTHORIZATION zan_core` парой минут раньше тем же прогоном. Фикс — `GRANT CREATE ON DATABASE ... TO zan_core;` в `scripts/postgres-init/02-core-role.sh`. Не открывает доступ к чужой схеме (изоляцию держит отдельный `REVOKE ALL ... FROM PUBLIC`) — если заводите ещё одну непривилегированную роль под новую схему, держите эту привилегию в уме отдельно от `CREATE SCHEMA ... AUTHORIZATION`.

**Postgres-роли `core`/`rag` — изоляция должна быть симметричной, не однонаправленной.** Бутстрап-суперпользователь официального образа `postgres` (`POSTGRES_USER`) обходит вообще любые `GRANT`/`REVOKE` — если backend ходит под этой ролью (было так до Stage 8), `REVOKE ALL ON SCHEMA rag FROM PUBLIC` его не касается, и заявленная изоляция схем — фикция с одной стороны. Обе стороны обязаны ходить под собственной непривилегированной `LOGIN`-ролью (`zan_core`/`zan_rag`), не под суперпользователем.

**`docker-entrypoint-initdb.d`-скрипты (роли Postgres) гоняются РОВНО ОДИН РАЗ, только на пустом томе.** Если меняете `scripts/postgres-init/*.sh` на уже существующем локальном/прод томе — новая роль/грант не применится автоматически, нужно пересоздать том (`docker compose down -v` затрагивает только том Postgres, если volume-имя не общее с другими сервисами).

**Смена LLM-провайдера (Anthropic → OpenAI, Stage 8, по прямому запросу пользователя).** Затронут только `internal/agent` — остальной backend не знает, какой провайдер за портом `thread.Agent`, ничего в нём не изменилось (ради этого провайдер и был спрятан за портом). Структурное отличие: у Anthropic `system` — отдельное поле верхнего уровня запроса, у OpenAI Chat Completions — первое сообщение с `role="system"` в общем массиве `messages`. Ответ: Anthropic — массив `content`-блоков произвольной длины/типа, OpenAI — один `choices[0].message.content` строкой. `response_format:{"type":"json_object"}` (OpenAI, гарантирует синтаксически валидный JSON) — эквивалента в Anthropic-версии не было, требует слова "JSON" где-то в messages. Отказ модели: было `resp.StopReason == "refusal"` (поле верхнего уровня, экспериментальное у Anthropic), стало `resp.Choices[0].FinishReason == "content_filter"` (стандартное поле OpenAI, внутри каждого choice). `max_completion_tokens`, не устаревший `max_tokens`. ENV: `ANTHROPIC_*` → `OPENAI_*`, дефолт модели `gpt-4o`.

**Presigned S3-ссылки требуют два клиента с разными `endpoint_url`, если внутренний и внешний адрес storage различаются.** Ссылка, подписанная с `endpoint_url="http://minio:9000"` (docker DNS), не резолвится снаружи docker-сети (браузер, `curl` с хоста). Оба сервиса (Go `internal/platform/storage`, Python `app/adapters/storage.py`) держат два клиента с одними и теми же credentials — internal (реальные S3-операции + ссылки для другого сервиса внутри той же сети) и public (`S3_PUBLIC_ENDPOINT` — для прода с одним публичным адресом дефолт = internal). Подпись не зависит от того, каким из клиентов выпущена — S3 проверяет её относительно реально пришедшего `Host`.

**SSRF-защита на `FilesService/Extract`:** Python скачивает `file_url` только если его host совпадает с собственным настроенным S3-эндпоинтом (`UntrustedFileURLError` иначе, отдельный WARN `ssrf_attempt_blocked`) — Python не должен ходить по произвольному URL, который прислал Go.

**`docxtpl` row-loop синтаксис (`{%tr for %}`/`{%tr endfor %}`) требует, чтобы тег стоял один, без другого содержимого, в отдельной строке таблицы шаблона.** `docxtpl.patch_xml` вырезает весь `<w:tr>` целиком — если в той же строке было что-то ещё, оно молча пропадает вместе со строкой. Рабочая структура — 4 отдельные строки: header / строка только с `{%tr for %}` / строка с полями (репликируется) / строка только с `{%tr endfor %}`.

**Python 3.14 (локальный venv) vs 3.12 (Docker) — PEP 649 (отложенная оценка аннотаций) в 3.14 тихо прячет баги, которые проявляются только в Docker/проде.** Конкретный случай: аннотация `grpc.RpcMethodHandler[Any, Any]` падала `TypeError: not subscriptable` на `python:3.12-slim` (рантайм-класс grpcio не `Generic`), но не локально. Фикс — `from __future__ import annotations` там, где нужна такая аннотация. **Правило: любое изменение в `helper/` проверять реальным Docker-билдом/`docker compose up`, не только локальным `pytest` в `.venv`** — несовпадение версий интерпретатора маскирует классы ошибок.

**`minio/minio` на Docker Hub недоступен (`pull access denied`) — источник `quay.io/minio/minio`.**

**Ни один сегмент пути `proto/`-пакета не называется `internal`.** Генератор Go использует `paths=source_relative` — выходной путь зеркалит путь `.proto` один в один внутри уже-`internal` `backend/internal/genproto/`; второе вхождение `internal` создаёт свою Go-границу видимости, делая сгенерированный пакет невидимым для остального `backend/internal/*`. Пакет — `zan.rpc.v1`, не `zan.internal.v1`.

**gRPC unary-сообщения — лимит поднят до 16 МБ (`maxMessageSize` в Go на `Dial`, `MAX_MESSAGE_SIZE` в Python на `grpc.aio.server`) — дефолт grpc (4 МБ) мал для `Extract` на большом PDF.** Файлы/аудио всё равно передаются по ссылке (`file_url`), не байтами — лимит на случай, если кто-то future-proof решит стримить бинарь через этот же контракт.

**`ruff`/`mypy exclude` для `app/genproto` — использовать `extend-exclude`, не голый `exclude`.** Голый `exclude` в `[tool.ruff]` **полностью заменяет** дефолтный список (который и так исключает `.venv`/`.git`), а не дополняет его.

**Protobuf-кодогенерация раздельная по языкам.** `buf generate` — только Go (локальные плагины). Python — отдельный `python -m grpc_tools.protoc` (`Makefile#proto`) — не нуждается в системном `protoc`/`buf`-remote-плагинах (требуют сети до `buf.build`).

**`helper/requirements.txt` дублирует зависимости `pyproject.toml` осознанно** — нужен только для Docker-слоя: `pip install .` (hatchling) потребовал бы исходники `app/` уже на этапе установки зависимостей, что сломало бы кэширование Docker-слоя. При изменении рантайм-зависимостей обновлять оба файла.

**Docker HEALTHCHECK для `backend/` (distroless, без shell) — реализован в бинаре** (`cmd/api/healthcheck.go`, режим `api healthcheck`), не `CMD-SHELL`. `helper/` (`python:slim`, интерпретатор есть) — маленький отдельный скрипт `healthcheck.py`.
