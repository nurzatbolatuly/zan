# @zan/backend

API Gateway + оркестратор + 2 агента (NestJS, TypeScript, запускается через `tsx`).

## Статус (Этап 15 — search/verification/editor слиты в один агент "answer")

Пайплайн работает end-to-end: `POST /requests` → задача в очередь (BullMQ/Redis) → воркер
вызывает оркестратор → оркестратор прогоняет answer → (опционально) document, каждый шаг
персистится в `request_steps` → `GET /requests/:id` и WS (`realtime/`) отдают статус и
результат в реальном времени, включая потоковый текст ответа по мере генерации.

До 2026-09-12 здесь было 3 последовательных LLM-вызова (search → verification → editor, см.
`../INSTRUCTIONS.md` §9.0-9.9) — слиты в один: латентность (один вызов быстрее трёх) и честность
стриминга (промежуточный черновик, который потом дважды переписывался, сбивал пользователя с
толку при показе в реальном времени, см. §9.9-9.10).

**Агент "answer"** (`src/agents/answer/`):

- `law-answer.agent.ts` — один вызов LLM с `web_search`, без БД/эмбеддингов: ищет применимые
  нормы на `adilet.zan.kz`/`zan.gov.kz`, перепроверяет сам себя перед финальным ответом (не
  показывая эту проверку пользователю) и сразу форматирует ответ в тёплом человечном тоне по
  структуре "что говорит закон → что это значит → что можно сделать". Стримится в реальном
  времени (`completeWithWebSearchMetaStream`) — то, что видит пользователь по мере генерации,
  уже финальный ответ, никто его больше не переписывает.

**Агент "document"** (`src/agents/document/`):

- `docx-template.ts` — шаблонизатор на пакете `docx`: A4, Times New Roman 14pt, шапка
  (recipientLines) выровнена справа сверху, пункты основного текста нумеруются автоматически,
  фиксированный футер с датой/подписью. Формальные требования реализованы программно, а не
  текстовой просьбой к LLM — соответствие формату гарантировано независимо от ответа модели
  (это не зависело от индекса и не менялось при пересмотре архитектуры).
- `law-document.agent.ts` — LLM отвечает только за содержание (заголовок, шапка, пункты),
  строго валидным JSON, опираясь на ответ Агента "answer" как правовую основу; указывает номер
  статьи только если уверена в её точности, иначе формулирует общими фразами. Невалидный JSON
  от LLM — ошибка шага (оркестратор пометит запрос `failed`), а не частично сгенерированный
  документ. Результат — DOCX-файл, закодированный в base64 (поле `content` в БД — `TEXT`,
  без миграции под бинарные данные).

`src/agents/agents.module.ts` остаётся единственной точкой подмены реализации агента на
будущее — без изменений в оркестраторе.

## Два жёстких правила этого backend'а (см. также `../INSTRUCTIONS.md`)

Backend собирается через `tsx` (esbuild), который **не** поддерживает TypeScript
`emitDecoratorMetadata`. Из-за этого:

1. **DI только через явный `@Inject(TOKEN)`** — неявный DI по типу конструктора
   (`constructor(private readonly x: Foo)` без `@Inject`) резолвится в `undefined`
   молча, без ошибки. Проверено вручную на смоук-тесте перед выбором архитектуры.
2. **Валидация тела запроса — только через `validateDto()`** (`src/common/validate-dto.ts`),
   не через `@Body() dto: SomeDto` + глобальный `ValidationPipe` — Nest не может определить
   DTO-класс параметра без `emitDecoratorMetadata` и тихо пропускает валидацию.

## Безопасность (Этап 8)

- **Rate limiting**: `@nestjs/throttler` — 60 запросов/мин на IP глобально
  (`app.module.ts`), и отдельно 5/мин на `POST /requests` (`requests.controller.ts`), так как
  каждый такой запрос запускает минимум 1-2 платных вызова OpenAI. Капча при подозрительной
  активности из плана намеренно не реализована — она требует стороннего сервиса (frontend-
  виджет + серверная проверка токена) и вне рамок этого этапа; rate limiting — минимальный
  практичный барьер от abuse без внешних зависимостей.
- **Валидация и санитизация ввода**: `class-validator`/`class-transformer` в
  `CreateRequestDto` — как раньше, плюс `@Transform` обрезает пробелы по краям `queryText`/
  `documentType` до проверки длины (иначе строка из одних пробелов проходила `MinLength`).
- **Защита от prompt injection**: пользовательский текст (`queryText`) при передаче в LLM
  оборачивается в `<user_query>` (см. `@zan/shared` → `security/userContent.ts`), и в
  system-промпт каждого из 2 агентов добавлено явное предупреждение: содержимое
  `<user_query>` — данные для анализа, а не инструкции агенту. Это не устраняет prompt
  injection полностью (это в принципе невозможно на уровне промпта), но снижает вероятность,
  что вопрос вида "игнорируй прошлые инструкции..." изменит поведение агента.
- **XSS/CSRF/SQLi**:
  - SQL — везде параметризованные запросы (`pg`, `$1/$2/...`), без конкатенации строк.
  - XSS — `react-markdown` (frontend) не рендерит сырой HTML по умолчанию; ссылки в ответе
    Агента "answer" дополнительно рендерятся с `rel="noopener noreferrer"` (см.
    `frontend/src/components/MarkdownAnswer.tsx`).
  - Безопасные заголовки — `helmet()` в `main.ts` (CSP, HSTS, X-Content-Type-Options и т.д.).
  - CSRF — `SameSite=Lax` у cookie сессии (см. ниже) + CORS ограничен конкретным
    `FRONTEND_ORIGIN`, а не `*`.
- **Разграничение прав доступа** ("пользователь видит только свои запросы"): полноценных
  аккаунтов ещё нет (Этап 13 — личный кабинет), поэтому владение запросом привязано к
  анонимной сессии — backend выдаёт браузеру httpOnly-cookie со случайным токеном
  (`common/session.ts`), а в БД (`requests.owner_token_hash`) хранится только SHA-256 хэш
  этого токена, не сам токен. `GET /requests/:id` для чужой сессии (или её отсутствия)
  отвечает тем же `404`, что и для несуществующего id — не подтверждает факт существования
  чужого запроса.
- **Секреты**: без изменений с Этапа 0 — `.env` (gitignored) + `.env.example` без значений.
- **HTTPS/безопасные заголовки**: `helmet()` включает `Strict-Transport-Security` — реальный
  эффект только за TLS-терминацией на реверс-прокси в проде (Этап 11), локально не проверить.

## Наблюдаемость (Этап 9)

- **Структурированные логи на каждом шаге**: без изменений в контракте с Этапа 2
  (`request_id`, `stage`, `status`, `duration_ms`) — дополнительно каждый шаг пайплайна теперь
  пишет отдельную строку `orchestrator.<agent>.summary` с PII-свободной сводкой (счётчики:
  `answerLength`, `contentSize` — не текст вопроса и не текст ответа), плюс HTTP-логи на
  каждый запрос к API
  (`common/http-logging.middleware.ts`: метод, путь с нормализованным `:id`, статус,
  длительность, замаскированный IP, `x-request-id`).
- **Централизованный сборщик + алерты**: логи пишутся структурированным JSON в stdout (pino) —
  готовы к подключению любого коллектора (Loki/ELK/Cloud Logging) без изменений в коде; сам
  коллектор и алерты на сбои — вне кода приложения, настраиваются на инфраструктурном уровне
  при деплое (Этап 11).
- **Метрики** — `GET /metrics` в формате Prometheus (`src/metrics/`): время обработки запроса
  (`zan_pipeline_step_duration_ms` по агенту/статусу, `zan_http_request_duration_ms` по
  маршруту), ошибки шагов пайплайна как прокси на ошибки LLM API
  (`zan_pipeline_step_total{status="failed"}`), плюс базовые метрики процесса Node.js. Эндпоинт
  не защищён аутентификацией (как обычно для Prometheus-скрейпинга) — в проде закрывается на
  уровне сети, не кода.
- **Полная трассируемость запроса**: `request_steps` в БД (с Этапа 2) + структурированные логи
  с `request_id` на каждом шаге дают возможность восстановить путь любого запроса от
  `POST /requests` до финального статуса.

## Этап 13 (бэклог, кроме доп. агентов) — личный кабинет, уточнение, аналитика

- **Личный кабинет и история обращений** — без полноценных аккаунтов (см. Этап 8: анонимная
  cookie-сессия уже разграничивает доступ). `GET /requests` (`RequestsController.listMine`)
  отдаёt до 50 последних запросов текущей сессии, новые сверху; без cookie — пустой список, а
  не поход в БД с `null` (иначе вернулись бы чужие "бесхозные" записи, см.
  `RequestsRepository.isOwnedBy`).
- **Многоходовой диалог — ровно один раунд уточнения перед Агентом "answer"** (не полноценный
  чат): `orchestrator/clarification-check.ts` — не отдельный агент (нет DI-токена/модуля/контракта
  в `agents/agent.types.ts`, не персистится как `request_step`), а вспомогательная проверка
  внутри `OrchestratorService.resolveEffectiveQueryText`, использующая уже существующий
  `CHAT_CLIENT`. Fail-open, а не fail-closed: недоступность LLM или невалидный JSON не блокируют
  пайплайн — уточнение помогает точности, но не является барьером безопасности. Гарантия "ровно
  один раунд" — по данным, а не по коду: проверка запускается, только если
  `requests.clarification_question IS NULL`; статус `needs_clarification` +
  `POST /requests/:id/clarification` (`RequestsService.submitClarification`) возобновляют
  пайплайн с `queryText`, дополненным ответом пользователя.
- **Аналитика** — `GET /analytics/summary` (`src/analytics/`): запросы по статусу и среднее
  время обработки — простая SQL-агрегация по `requests`, без LLM-вызовов. Без аутентификации,
  как `/metrics`.

Проверено вживую: `POST /requests`/`GET /requests` под одной cookie-сессией отдают именно её
историю, `POST /requests/:id/clarification` возвращает 400 на запрос не в статусе
`needs_clarification` и 404 на чужую сессию/несуществующий id, `GET /analytics/summary`
агрегирует реальные строки `requests`/`request_steps`. Сценарий "LLM решает, что нужно
уточнение" проверен юнит-тестами оркестратора (нет доступа к реальному OpenAI для живой
проверки этой конкретной ветки) — см. `orchestrator/orchestrator.service.test.ts`.

## Структура

```
src/
├── main.ts                 # bootstrap
├── app.module.ts            # корневой модуль, подключение Redis/BullMQ
├── config.ts                 # переменные окружения
├── common/validate-dto.ts    # явная валидация DTO (см. правило выше)
├── common/session.ts         # анонимная cookie-сессия (Этап 8)
├── common/http-logging.middleware.ts, all-exceptions.filter.ts   # Этап 9
├── db/                       # DB_POOL — pg.Pool за DI-токеном, @Global()
├── metrics/                  # Prometheus-метрики, GET /metrics (Этап 9)
├── analytics/                # GET /analytics/summary (Этап 13)
├── requests/                 # HTTP API: POST/GET /requests, GET /requests/:id, POST /requests/:id/clarification
├── agents/                   # интерфейсы 2 агентов + DI-токены + реальные реализации
├── orchestrator/              # OrchestratorService (пайплайн) + clarification-check.ts (Этап 13)
└── queue/                     # BullMQ: очередь + воркер (Processor)
```

## Локальный запуск

```bash
# Инфраструктура (Postgres+pgvector, Redis)
docker compose up -d postgres redis

# Схема БД — общая с ingestion, единый node-pg-migrate
npm run migrate -w ingestion

npm run start:dev -w backend   # с автоперезапуском при изменениях
# либо
npm run start -w backend
```

Проверить:

```bash
curl -X POST http://localhost:3000/requests \
  -H "Content-Type: application/json" \
  -d '{"queryText":"Меня уволили без предупреждения, законно ли это?"}'

curl http://localhost:3000/requests/<id из ответа>
```

## Тесты

```bash
npm run test -w backend
```

Оркестратор и `RequestsService` покрыты тестами с фейковыми репозиторием/агентами/очередью
(без реальной БД/Redis) — быстрые unit-тесты на бизнес-логику пайплайна.
