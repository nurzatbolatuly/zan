# Zan — план реализации бэкенда

Источники, на основе которых собран план:

- `zan-backend-tz-v2.md` — модель данных (§2), базовый API (§3), бизнес-логика биллинга/тредов (§4)
- `zan-backend-tz-v3.md` — сессии вместо авторизации (§2), каталог ошибок (§5), логирование (§6)
- `backend-roadmap.md` (= ТЗ v4, актуальная версия) — разделение Go/Python, контракт Go↔Python (§1), обновлённый каталог ошибок (§5.2), обновлённое логирование (§6.2)
- `PLAN.md`, `instructions.md` — что уже реализовано на фронте, раздел «Общий словарь FE↔BE» (`instructions.md`) — список расхождений, которые бэк обязан закрыть

v4 меняет только распределение задач между Go и Python (генерация ответа теперь в Go), остальное — данные/API/ошибки/логи — наследуются из v2/v3 без изменений. Этот план следует v4 как единственному источнику правды по архитектуре.

Архитектурные слои, паттерны, naming, логирование, обработка ошибок, git/PR, тестирование и чеклист ревью — зафиксированы отдельно в `BACKEND_CODING_STANDARDS.md` (аналог `FRONT_CODING_STANDARDS.md` для бэка), обязательны с первого коммита Stage 0, не переизобретаются по ходу.

Репозиторий — монорепо: `frontend/` (реализован), `backend/` (Go, ядро), `helper/` (Python, ML-задачи, gRPC-сервер), `proto/` (общий protobuf-контракт Go↔Python, см. §3). Ниже — план по `backend/` и `helper/`, по аналогии с тем, как `PLAN.md` резал фронт на стадии.

## 1. Архитектурные решения (зафиксированы здесь, не переизобретаются по ходу)

### 1.1 Go (`backend/`)

| Область | Выбор | Почему |
|---|---|---|
| Роутер | `gin` | Зафиксировано пользователем. Middleware-цепочка (`gin.HandlerFunc`) даёт то же линейное чтение обработки ошибок, что нужно под каталог `§5.2` v4 — каждый сценарий (таймаут LLM, невалидный JSON, отказ модерации и т.д.) оформляется отдельным middleware/error-mapper через `c.Error()` + централизованный `gin.RecoveryWithWriter`/кастомный error-handler, а не разбросанными `if` внутри хендлеров. |
| Доступ к БД | `pgx` напрямую, без codegen | Зафиксировано пользователем (Stage 1→2 правка — было `pgx` + `sqlc`, см. `BACKEND_LOG.md`). SQL остаётся SQL (нужен `SELECT ... FOR UPDATE` для атомарного списания баланса, §4.2 v2 — тяжёлый ORM это прячет и мешает); каждый запрос — строковый литерал в методе `internal/repo`, который его выполняет (`BACKEND_CODING_STANDARDS.md §1.1`), не в отдельном `.sql`-файле и не в сгенерированном пакете — компромисс в пользу локальности (запрос виден там же, где используется) вместо типобезопасности codegen. |
| Миграции | `golang-migrate` | Отдельный бинарь/CLI, не завязан на рантайм приложения — миграции гоняются в CI/деплое независимо от старта сервиса. |
| Конфигурация | `env`-based struct (`caarlos0/env` или свой загрузчик ~50 строк) | Полный список ENV — в `backend/internal/config`, один файл, без библиотек для YAML/Consul на этом этапе (не нужны). |
| Логирование | `log/slog` (стандартная библиотека, Go 1.21+) | Зафиксировано пользователем. `slog.NewJSONHandler` даёт структурированный JSON без внешней зависимости; под контракт `backend-roadmap.md §6.1/§6.2` заводится один `slog.Logger` с обязательными полями по умолчанию (`service`, `trace_id`, `session_id`, `stage`) через `logger.With(...)`, прокидываемый в `context` middleware'ом Gin — так каждый хендлер/сервис достаёт уже привязанный к запросу логгер, а не собирает поля заново. |
| Связь с Python (`helper/`) | **gRPC** (`google.golang.org/grpc` + `google.golang.org/protobuf`), поверх — клиентские interceptor'ы для ретраев/circuit breaker/лога/`trace-id` | Зафиксировано пользователем (ускорение процесса). Внутренний трафик Go↔Python — самый частый путь в системе (RAG на каждый Q&A, extract на каждый файл) и самый чувствительный к задержке — protobuf/HTTP2 даёт меньше накладных расходов на (де)сериализацию и переиспользуемые мультиплексированные соединения по сравнению с JSON/HTTP1.1; строго типизированный контракт на обеих сторонах компилируется из одного `.proto` — рассинхрон полей ловится на этапе сборки, а не в проде (см. §3). |
| HTTP-клиент к LLM-провайдеру | обёртка над `net/http.Client` с ретраями (свой backoff) + circuit breaker (`sony/gobreaker`) | Anthropic API — внешний REST/JSON, не наш контракт, gRPC тут неприменим. Тот же паттерн ретраев/breaker, что и у gRPC-клиента к Python — одна общая реализация `internal/platform/resilience`, переиспользуемая обоими клиентами. |
| Codegen контракта | `buf` (`buf generate`, `buf lint`, `buf breaking` в CI) | Индустриальный стандарт поверх `protoc` — единая точка генерации для Go и Python из одного `proto/`, плюс `buf breaking` ловит несовместимые изменения контракта на PR, до мержа, а не при деплое. |
| Аутентификация сессии | opaque-токен: `session_id` (UUID) + `HMAC-SHA256` подпись на секрете сервера, без персональных данных внутри | Ровно то, что описывает v3 §2.1 ("JWT-подобный, но без пользовательских данных"). Не тянем полноценную JWT-библиотеку ради одного use case — 20 строк `crypto/hmac`. |
| Файловое хранилище | S3-совместимый клиент (`aws-sdk-go-v2`), MinIO локально/в docker-compose | v2 §5 требует S3-совместимое хранилище + подписанные URL. |
| Rate limiting | `golang.org/x/time/rate` (in-memory, per-IP/per-session) на старте; вынести в Redis, если деплой станет multi-instance | MVP — один инстанс Go, in-memory достаточно и проще эксплуатировать; явно фиксируем как ограничение, не как забытый недостаток (см. §7 Stage 8). |
| Тесты | стандартный `testing` + `testify` (assert/require) + `testcontainers-go` для интеграционных тестов с реальным Postgres | Юнит — бизнес-логика (расчёт цены, статус-машина, sources-верификация) без БД; интеграционные — реальный Postgres в контейнере, не моки SQL. |
| Публичный API-контракт (Go↔Frontend) | `openapi/openapi.yaml`, contract-first | Единственный источник правды для путей/схем публичного REST/JSON API — из него сверяется фронт (`instructions.md`, «Общий словарь FE↔BE»). Генерация серверных заглушек — опционально (`oapi-codegen`), не обязательна с первого дня. Контракт Go↔Python — отдельно, через `proto/` (gRPC, см. §3), не через OpenAPI. |

### 1.2 Python (`helper/`)

| Область | Выбор | Почему |
|---|---|---|
| Сервер контракта | `grpc.aio` (генерируемые сервисы из `proto/`, см. §3) — бизнес-контракт Go↔Python целиком на gRPC, не REST | Зафиксировано пользователем. `grpc.aio` — асинхронный сервер, нужен под I/O (эмбеддинги, OCR, внешние STT-API), тот же рантайм, что и у Uvicorn. |
| HTTP рядом с gRPC | тонкий FastAPI/Starlette только под `GET /healthz` (+ `/metrics` для Prometheus, Stage 7+) | gRPC health-checking protocol избыточен для docker-compose/k8s liveness-проб на этом масштабе — проще один HTTP-эндпоинт для оркестратора, бизнес-трафик им не идёт. Общепринятый паттерн (grpc-сервис + маленький debug/health HTTP рядом), не костыль. |
| Схемы | Protobuf-сообщения, сгенерированные `buf` из `proto/` (единственный источник правды, см. §3); Pydantic — только для внутренней валидации/бизнес-логики сервиса, не для wire-контракта | Wire-формат задаёт `.proto`, не Pydantic — на нём нельзя случайно разойтись с Go, потому что оба генерируются из одного файла, а не пишутся вручную по договорённости. |
| RAG | `pgvector` (расширение на том же Postgres, отдельная схема `rag`, отдельная БД-роль — см. §2.2) + эмбеддинги (провайдер уточняется, см. открытые вопросы) | Одна инфраструктура вместо отдельного vector DB на MVP-масштабе (закрывает открытый вопрос backend-roadmap.md §8.6 — рекомендация архитектора, не окончательное решение продукта). |
| Извлечение текста из файлов | `PyMuPDF` (PDF), `python-docx` (DOCX), `pytesseract` + `pdf2image` (OCR-фолбэк для сканов) | Стандартный, хорошо поддерживаемый набор без внешних платных API на старте. |
| Рендер документа | `docxtpl` (DOCX из шаблона), `WeasyPrint` (HTML→PDF) | Не нужен headless-браузер (Puppeteer) ради PDF — WeasyPrint легче в контейнере. |
| STT | `faster-whisper` (self-hosted) по умолчанию, с возможностью переключить на внешний API через интерфейс `SttProvider` | Открытый вопрос v3 §8.3 не закрыт продуктом — архитектура должна допускать оба варианта без переписывания вызывающего кода (Strategy-паттерн на уровне одного интерфейса). |
| Аутентификация внутренних вызовов | shared secret в gRPC-метадате (`x-internal-secret`, серверный interceptor) + сервис недоступен из публичного ingress (docker network / VPC), не только метадатой | v3 §1.3: "без аутентификации пользователя — защищены на уровне сети + shared secret". Метадата — вторая линия обороны, не единственная; тот же принцип, что был бы у HTTP-заголовка, просто в терминах gRPC. |
| Логирование | `structlog`, JSON, та же форма записи, что в Go (`backend-roadmap.md §6.1`) | Одна и та же схема лога в обоих сервисах — иначе агрегатор логов (Loki/ELK) не сможет склеить цепочку по `trace_id`. |
| Тесты | `pytest` + `httpx.AsyncClient` для роутов, отдельные юниты на `extraction_service`/`render_service` на фикстурных файлах | Каждый internal-эндпоинт — минимум один "счастливый путь" + один сценарий отказа, зеркально каталогу ошибок §5.2/§5.3/§5.4 v4. |

### 1.3 Общая инфраструктура

- **Postgres — один инстанс, две схемы, две БД-роли.** `core` (все таблицы v2 §2 — Session/Service/Tariff/UserCredit/Payment/Thread/Message/FileAttachment/AgentPrompt) — владеет и мигрирует **только Go**. `rag` (векторный индекс НПА) — владеет и мигрирует **только Python** (Alembic). Роль `go_core` не имеет прав на схему `rag` и наоборот — предотвращает случайную связность мимо gRPC-контракта, которую потом трудно распутать.
- **`proto/` в корне репозитория** — единственный источник правды для контракта Go↔Python (см. §3), не принадлежит ни `backend/`, ни `helper/` по отдельности.
- **docker-compose.yml в корне репозитория** — `postgres` (образ с `pgvector`, напр. `pgvector/pgvector:pg16`), `minio`, `backend`, `helper`. Один `docker compose up` поднимает весь стек локально — обязательное условие Stage 0.
- **Трассировка `trace_id` — сквозная через весь стек, но двумя разными механизмами на двух хопах.** Фронт → Go: HTTP-заголовок `X-Trace-Id` (уже реализовано в `shared/lib/api.ts`). Go → Python: тот же `trace_id` кладётся в gRPC-метадату (`x-trace-id`) клиентским interceptor'ом и читается серверным interceptor'ом на стороне Python — единственное место, где это делается, не руками в каждом вызове. Go генерирует `trace_id`, если фронт не передал заголовок (защита от старой версии фронта).

## 3. Контракт Go ↔ Python

**Изменение относительно `backend-roadmap.md §1.3`: внутренний контракт — gRPC, не REST/JSON.** Набор операций и их семантика (когда вызывается, что значит ответ) — те же 4, что в таблице roadmap §1.3, но транспорт и формат сообщений — protobuf/gRPC вместо HTTP+JSON (решение пользователя — ускорить внутренний трафик; см. обоснование в §1.1/§1.2). Публичный контракт Go↔Frontend этим не затронут — там как был, так и остаётся REST/JSON (`openapi/openapi.yaml`), фронт на gRPC-web не переводится.

### 3.1 Структура `proto/`

```
proto/
  zan/rpc/v1/
    common.proto      # TraceContext, Money, Lang и т.п. — общие типы для всех сервисов
    rag.proto          # service RagService { rpc Search(SearchRequest) returns (SearchResponse); }
    files.proto         # service FilesService { rpc Extract(ExtractRequest) returns (ExtractResponse); }
    documents.proto      # service DocumentsService { rpc Render(RenderRequest) returns (RenderResponse); }
    stt.proto             # service SttService { rpc Transcribe(TranscribeRequest) returns (TranscribeResponse); }
  buf.yaml
  buf.gen.yaml          # два таргета: Go → backend/internal/genproto, Python → helper/app/genproto
```

- Версионирование пакета — `v1` в пути с первого дня (`zan.rpc.v1`), не потому что уже нужна v2, а чтобы breaking-рестарт контракта в будущем не требовал переименования на живую конвенцию. Пакет назывался `zan.internal.v1` до Stage 4 — переименован (не в `internal`, а в `rpc`) из-за Go-специфичной проблемы с двойным `internal` в пути импорта, см. `BACKEND_LOG.md`, Stage 4.
- Payload остаётся маленьким: файлы/аудио передаются **по ссылке** (`file_url` на MinIO/S3 + `mime_type`), а не байтами в сообщении — тот же принцип, что был в HTTP-варианте контракта. Это осознанное решение, а не временное упрощение: избегает лимита на размер unary-сообщения gRPC (по умолчанию 4 МБ) и необходимости стриминга на MVP-этапе. Стриминг (client-streaming для загрузки, server-streaming для потокового STT) — рассматривается отдельно, только если появится измеримая причина (например, живая транскрипция в реальном времени), не заводится "про запас".
- `documents.proto/Render` **всегда** возвращает `file_url` (Python сам загружает готовый PDF/DOCX в тот же MinIO/S3-бакет, в префикс `generated/`), а не бинарь в ответе — закрывает двусмысленность `файл (бинарь) или {file_url}` из исходного HTTP-варианта контракта (`backend-roadmap.md` §1.3) одним явным вариантом.

### 3.2 Codegen и сборка

- `buf generate` — запускается из корня, гоняется в `make proto` (Makefile корня) и в CI при изменении `proto/**`.
- Сгенерированный код — **коммитится** в `backend/internal/genproto` и `helper/app/genproto` (не генерируется на лету в Dockerfile): CI может проверить `git diff --exit-code` после `buf generate`, чтобы поймать забытый `make proto` до ревью, и разработчику не нужен `buf`/`protoc` локально, чтобы просто собрать проект.
- `buf lint` — обязателен в CI (naming conventions полей/сервисов, единый стиль).
- `buf breaking --against '.git#branch=main'` — обязателен в CI на каждый PR, трогающий `proto/**`: ловит удаление/renumber поля, смену типа — то есть именно то расхождение, из-за которого раньше приходилось бы вручную сверять JSON-фикстуры между двумя репозиториями.

### 3.3 Реализация по сторонам

- `backend/internal/grpcclient` — обёртка над сгенерированным клиентом (4 метода: `SearchRAG`, `ExtractFile`, `RenderDocument`, `TranscribeAudio`), единая точка client-side interceptor'ов: ретраи с backoff, circuit breaker (`sony/gobreaker`), логирование вызова (`§6.2`), проброс `trace_id`/`x-internal-secret` в метадату.
- `helper/app/grpc/servicers/{rag,files,documents,stt}.py` — реализации сгенерированных `*Servicer`-классов, тонкие (валидация + делегирование в `app/services/*`, как и в изначальном REST-варианте, просто без FastAPI-роутера сверху).
- **Маппинг ошибок на статус-коды gRPC** — фиксированная таблица (не придумывается по месту): `codes.DEADLINE_EXCEEDED` (таймаут — Go делает ретраи), `codes.UNAVAILABLE` (Python недодоступен целиком — открывает circuit breaker), `codes.INVALID_ARGUMENT` (невалидный запрос — не ретраится), `codes.INTERNAL` (необработанный сбой — логируется как ERROR). Go на основе этих кодов принимает решение ретраить/не ретраить и как логировать — реализуется один раз в interceptor'е, не в каждом вызывающем месте.
- **Контрактные тесты** (Stage 4/5): т.к. `.proto` уже гарантирует совпадение форм сообщений, дополнительные JSON-фикстуры не нужны — вместо них интеграционный тест поднимает `helper` (testcontainers/docker-compose в CI) и гоняет реальные gRPC-вызовы из Go-тестов, проверяя **поведение** (что RAG вернул ожидаемые совпадения, что `Extract` на битом PDF отдаёт нужный код ошибки), а не только форму сообщения.

## 5. Стадии реализации

Каждая стадия: (а) имеет явный DoD; (б) там, где возможно — тестируется без реального LLM/внешних провайдеров (стабы/моки); (в) не блокирует параллельную работу над `frontend/`, если оговоренный контракт (пути, статусы, поля) не меняется без обновления `instructions.md`.

### Stage 0 — Foundation (оба сервиса, блокирует всё остальное)

- `proto/`: `buf.yaml`/`buf.gen.yaml`, `common.proto` с заглушкой (`TraceContext`), `make proto` генерирует пустые пакеты в `backend/internal/genproto` и `helper/app/genproto` — сам codegen-пайплайн работает раньше, чем появится первый реальный RPC.
- `backend/`: скаффолд Go-модуля (`cmd/api`, `internal/{config,httpserver,platform,grpcclient}`), `gin`-роутер с `GET /healthz`, конфиг из ENV, `log/slog` (JSON-хендлер) с контрактом `§6.1`, `Dockerfile`.
- `helper/`: скаффолд `grpc.aio`-сервера (пустой, без реальных сервисов) + тонкий HTTP c `GET /healthz` рядом, `app/core/{config,logging}.py`, `Dockerfile`.
- `docker-compose.yml` в корне: `postgres` (pgvector), `minio`, `backend`, `helper` (с двумя портами — gRPC и health-HTTP) — с health-check зависимостями (`depends_on: condition: service_healthy`).
- `golang-migrate` подключён, одна пустая миграция накатывается при старте контейнера (Go) или через `make migrate`.
- `Makefile`/`justfile` в корне: `make up` / `make proto` / `make migrate` / `make test` (гоняет тесты в обоих деревьях) / `make lint`.
- CI-скелет (GitHub Actions или аналог): `buf lint`/`buf breaking` на изменения `proto/**`, линт + юнит-тесты на пуш, без деплоя.
- `BACKEND_LOG.md` в корне — живой журнал по образцу фронтового `instructions.md` (см. `BACKEND_CODING_STANDARDS.md` §3, §9), первая запись — эта стадия.

**Готово, когда:** `make verify` зелёный (`lint`+`test`+`smoke` — см. `scripts/smoke-test.sh` и `BACKEND_LOG.md` «Конвенции»): `docker compose up` поднимает весь стек, `curl :8080/healthz` (Go) и `curl :8001/healthz` (Python health-HTTP) отвечают 200, `grpcurl :9090 list` показывает пустой список сервисов helper (сервер жив, контракта ещё нет), `make lint`/`make test` зелёные (даже на пустых пакетах) — одной командой, не набором ручных шагов; то же самое гоняет CI (`.github/workflows/backend-ci.yml`, job `smoke`).

### Stage 1 — Сессии, admin-auth, полная схема БД

- Миграции: все таблицы v2 §2 (адаптированные под `Session`, v3 §3) в схеме `core`.
- `Session`: `POST /sessions`, `GET /sessions/me`, `PATCH /sessions/me`, `POST /sessions/onboarding-seen` — опрятная реализация v3 §2.1-2.2 (opaque HMAC-токен, cookie + bearer, скользящее окно 90 дней).
- Middleware сессии: читает токен из `Authorization: Session <token>` или cookie, инжектит `session_id` в `context`, 401 при подделанной подписи (без автосоздания — v3 §5.5), прозрачное создание новой сессии оставлено на клиента (фронт вызывает `POST /sessions` заново).
- `X-Admin-Token`-middleware на `/admin/*` — реализуем сразу (рекомендация архитектора; открытый вопрос v3 §8.1 не блокирует реализацию, только держим секрет конфигурируемым и легко отзываемым).
- Rate limiting на `POST /sessions` (по IP) — первый барьер против спама, до появления треда/оплаты, которые дороже.

**Готово, когда:** интеграционные тесты (testcontainers) покрывают создание/продление/протухание/подделанную подпись сессии, `X-Admin-Token`-гейт возвращает 401 без токена и 200 с верным.

### Stage 2 — Услуги, тарифы, баланс, оплата (заглушка)

- `GET /services`, `GET /tariffs`, `GET /balance`; `/admin/services`, `/admin/tariffs` (CRUD, `DELETE` = `is_active=false`, история платежей не трогается).
- Формула цены (v2 §2.3) — чистая функция `backend/internal/service/pricing`, **побитово** совпадает с тем, что уже реализовано на фронте (`shared/lib/tariffPricing.ts` — округление до 10 тенге, `Math.round`) — сверка golden-тестами с одинаковыми входами/выходами обеих реализаций (кросс-чек вручную на этапе ревью PR, т.к. фронт и бэк не шарят рантайм).
- `POST /payments/checkout`, `POST /payments/{id}/confirm` (идемпотентно — уникальный индекс/проверка статуса перед начислением), `GET /payments/{id}`.
- Списание/начисление баланса — `SELECT ... FOR UPDATE` (v2 §4.2, гонка описана в v3 §5.5).
- Фоновая задача (goroutine + `time.Ticker`): `pending`-платежи старше 30 минут → `failed`.

**Готово, когда:** покупка пакета/своего набора end-to-end через мок-подтверждение, конкурентный тест на списание последней единицы баланса (два параллельных запроса — ровно один списывает), повторный `confirm` не начисляет дважды.

### Stage 3 — Треды и сообщения (без реального агента)

- `POST /threads`, `GET /threads?status=&search=&page=`, `GET /threads/{id}`, `POST /threads/{id}/messages`, `POST /threads/{id}/cancel`, `DELETE /threads/{id}` (soft delete), `POST /messages/{id}/feedback`.
- Статус-машина (`queued → processing → clarify/done/error/canceled`) как явный тип с проверкой допустимых переходов (не строка, которую можно выставить в любое значение из любого места) — `backend/internal/domain/thread_status.go`.
- `title`/`preview_text`/`message_count` — денормализация по правилам v2 §4.5.
- `free_until`-окно (§4.3 v2) — значение конфигурируемое (ENV, дефолт 72ч, см. открытый вопрос).
- **Агент — заглушка**: синхронно возвращает фиксированный `{answer_text, sources: [], needs_clarification: false}` за интерфейсом `AgentService`, который в Stage 5 заменяется на реальный вызов LLM без изменения HTTP-слоя (Strategy — та же идея, что и `SttProvider` в Python).

**Готово, когда:** полный жизненный цикл треда тестируется без сети наружу (заглушка агента), статусы/`title`/`preview_text`/`message_count` совпадают с ожиданиями фронта (`ThreadStatus` enum — сверить строки буквально с `frontend/src/shared/types/common.ts`, закрывает пункт «Общего словаря FE↔BE»).

### Stage 4 — Python: файлы, голос, рендер документа (базовая реализация)

- `proto/zan/rpc/v1/{files,documents,stt}.proto` — первые реальные RPC: `FilesService/Extract`, `DocumentsService/Render`, `SttService/Transcribe`.
- `helper/`: реализации сервисеров — `Extract` (PDF/DOCX + OCR-фолбэк), `Transcribe` (faster-whisper за интерфейсом `SttProvider`), `Render` (DOCX через `docxtpl`, PDF через `WeasyPrint`, результат — `file_url` в MinIO, см. §3.1).
- `backend/`: `POST /files/upload` (валидация типа/размера, антивирус-хук — интерфейс `AVScanner`, MVP-реализация может быть no-op с явным TODO и логом, не тихой заглушкой), сохранение в MinIO/S3, `GET /files/{id}`; `POST /voice/transcribe` — вызывает `grpcclient.TranscribeAudio`.
- Ошибки §5.3/§5.4 v3 (неподдерживаемый формат, файл слишком большой, антивирус, пустая транскрипция) — реализованы по таблице буквально, включая тексты пользователю; на стороне gRPC — через маппинг ошибок §3.3.

**Готово, когда:** реальный PDF/DOCX → извлечённый текст, короткая аудиозапись → текст, JSON-черновик документа → скачиваемый PDF и DOCX — всё через Go-оркестрацию и gRPC-вызовы, `trace_id` виден в логах обоих сервисов (HTTP-заголовок на входе в Go, gRPC-метадата на хопе Go→Python) на одном запросе.

### Stage 5 — RAG + вызов LLM в Go (ядро v4)

- `proto/zan/rpc/v1/rag.proto` — `RagService/Search`.
- `helper/`: реализация `Search` — поиск по `rag.chunks` (pgvector), плюс отдельный офлайн/админский скрипт индексации корпуса НПА (не RPC — batch job), с хотя бы небольшим сид-корпусом для тестов.
- `backend/internal/agent`: сборка промпта (`AgentPrompt(qa)` + история треда + источники от RAG), HTTP-клиент к LLM-провайдеру (Anthropic API), парсинг структурированного JSON-ответа.
- **Верификация источников** — явно вынесенная функция `verifySources(llmSources, ragMatches) → unverified_sources bool`, юнит-тестируемая отдельно от остального пайплайна (риск прямо назван в `backend-roadmap.md §1.4` — "стоит явно заложить эту проверку в код, а не полагаться только на промпт").
- Полный каталог ошибок §5.2 v4: таймаут/5xx LLM (до 2 ретраев + backoff), невалидный JSON, отказ модерации, `needs_clarification`, RAG недоступен (деградация без блокировки — `sources_degraded=true`), возврат кредита при `error`.
- Логирование — все 14 этапов `backend-roadmap.md §6.2` реализованы как явные вызовы логгера в местах переходов, не восстанавливаются постфактум из общих логов.

**Готово, когда:** живой раунд Q&A с реальным LLM + сид-корпусом RAG отрабатывает end-to-end; тест с намеренно "придуманной" LLM ссылкой на несуществующую статью подтверждённо ставит `unverified_sources=true`; отключение Python (docker stop) не роняет тред, а даёт деградацию `sources_degraded=true`.

### Stage 6 — Агент "Документы" + генерация файла

- `POST /threads/{id}/generate-document`, `GET /threads/{id}/document?format=`.
- Переиспользует LLM-клиент Stage 5 с промптом `AgentPrompt(document)` + рендер-пайплайн Stage 4.
- Изоляция ошибки рендера от уже сохранённого текстового ответа (§5.2 v4, последняя строка таблицы) — `doc`-кредит возвращается отдельно от `qa`/основного треда.

**Готово, когда:** тред `qa` → генерация документа → PDF/DOCX скачивается; принудительный сбой `DocumentsService/Render` не откатывает уже сохранённый текстовый ответ в чате.

### Stage 7 — Админ-аналитика, клиентские логи, борьба со злоупотреблениями

- `GET /admin/analytics/overview` (агрегаты по своей БД — `total_threads`, `avg_processing_time_sec`, `satisfaction_rate`, разбивка по статусам).
- `POST /logs/client` (v3 §6.3) — без авторизации или с сессионной (см. открытый вопрос в `instructions.md` «Деплой» п.5 — закрыть здесь).
- Circuit breaker на клиенте к Python активирован и протестирован (серия отказов → быстрый отказ новых тредов вместо долгого ожидания, §5.6 v3).
- Rate limiting на `POST /threads`, брутфорс-защита `X-Admin-Token` (блокировка IP после N неудач, v3 §5.7).

**Готово, когда:** аналитика отдаёт корректные агрегаты на тестовых данных; принудительное отключение Python triggers circuit breaker в пределах ожидаемого окна (тест с таймером); нагрузочный мини-тест на `/admin/*` подтверждает блокировку после N попыток.

### Stage 8 — Закрытие контракта, hardening, подготовка к деплою

- Закрыть **все** пункты «Общего словаря FE↔BE» из `instructions.md` явным решением (см. §6 ниже) — обновить `openapi/openapi.yaml`, разослать/задокументировать для фронта.
- Security-обход: секреты не в репозитории, сила `admin-secret` и `x-internal-secret`, SSRF-риск на `file_url` в `FilesService/Extract` (Python не должен ходить по произвольному URL без ограничения на собственный storage), лимиты на размер unary-сообщений gRPC.
- `docker compose` → реальная цель деплоя (решение — вне скоупа этого плана, как и у фронта, см. `PLAN.md §9`/`instructions.md` «Деплой»): CI/CD, staging.
- Нагрузочный smoke-тест пути `POST /threads` → LLM → ответ.

## 7. Sequencing / зависимости

```
Stage 0 (Foundation: оба сервиса, docker-compose, CI)
   │
   ▼
Stage 1 (Сессии, admin-auth, полная схема БД)
   │
   ▼
Stage 2 (Услуги/тарифы/баланс/оплата-заглушка) ──┐
   │                                              │ параллельно возможно,
   ▼                                              │ Stage 4 не зависит от Stage 2/3
Stage 3 (Треды/сообщения, агент-заглушка)         │
   │                                              │
   ├──────────────────────────────────────────────┘
   ▼
Stage 4 (Python: файлы/голос/рендер — базовая реализация)
   │
   ▼
Stage 5 (RAG + реальный вызов LLM в Go — ядро v4)
   │
   ▼
Stage 6 (Агент "Документы" + генерация файла)
   │
   ▼
Stage 7 (Админ-аналитика, клиентские логи, anti-abuse)
   │
   ▼
Stage 8 (Закрытие контракта FE↔BE, hardening, деплой)
```

Stage 2 и Stage 4 не зависят друг от друга по коду (разные таблицы/сервисы) и **могут делаться параллельно** двумя людьми сразу после Stage 1, если команда больше одного бэкендера. Stage 5/6 обязательно последовательны — оба используют один и тот же LLM-клиент и полагаются на готовый RAG/рендер из предыдущих стадий.

## 8. Definition of done (общий для каждой стадии)

- Миграции применяются чисто на пустой БД (`make migrate` в CI, не только локально).
- Юнит-тесты на бизнес-логику (не требующую сети/БД) — обязательны; интеграционные — там, где стадия трогает Postgres/S3/внешний HTTP.
- Ни один секрет (admin-token, HMAC-ключ, ключ LLM-провайдера, internal shared secret) не в коде/конфиге репозитория — только ENV, `.env.example` обновлён (как у фронта).
- Изменение путей/схем/enum-значений относительно того, что уже задокументировано в OpenAPI — сначала правка `openapi/openapi.yaml` в этом же PR, потом код (та же дисциплина, что `FRONT_DESIGN_SYSTEM.md` требует от токенов на фронте).
- Обновлён `BACKEND_LOG.md` (корень репозитория, живой журнал по образцу фронтового `instructions.md`, заводится в Stage 0 — покрывает `backend/` и `helper/` вместе, т.к. они связаны общим `proto/`-контрактом) с тем же принципом: не в конце проекта, а после каждой стадии.
