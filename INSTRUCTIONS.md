Этот файл — практическое руководство для разработки: структура репозитория, конвенции,
переменные окружения и то, какие решения нужно принять до начала кодинга. Общий план и

## 0. Быстрый старт

```bash
npm install
cp .env.example .env   # если .env ещё нет — заполнить реальными значениями, см. ниже
```

Обязательные переменные в `.env` (без них backend не стартует, `config.ts` падает с ошибкой):

- `OPENAI_API_KEY` — используют все 4 агента (Агенты 1, 2 и 4 — со встроенным `web_search`, см.
  §9).
- `DATABASE_URL` — Postgres. На проде — Supabase Postgres напрямую (см. §7.1, это НЕ
  docker-compose). **Для внешней БД почти всегда нужен SSL** — добавь `?sslmode=require` в конец
  строки подключения, иначе получишь ошибку соединения (в коде это не настраивается отдельно:
  `pg` сам берёт `sslmode` из строки подключения).
- `SUPABASE_URL`, `SUPABASE_SECRET_KEY` — backend в рантайме ходит в БД только через них
  (`@supabase/server`/PostgREST, см. `backend/src/db/db.module.ts`), не через `DATABASE_URL`
  напрямую (тот нужен только миграциям/ingestion, см. §7.1).
- `REDIS_URL` — оркестратор кладёт задачи обработки запроса в очередь через BullMQ. Локально:
  `docker compose up -d redis`.

`JWT_SECRET`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_JWKS_URL` убраны из `.env.example` — не
использовались нигде в коде (проект работает на анонимных cookie-сессиях, см.
`common/session.ts`, а не на JWT; admin-клиент Supabase создаётся только с `secretKeys`, см.
`backend/src/db/db.module.ts`). Если понадобится проверка JWT пользователей на бэкенде
(`auth: 'user'`) — вернуть их обратно тогда же.

**Никогда не хранить реальные секреты в `.env.example`** — этот файл, в отличие от `.env`,
не в `.gitignore` и коммитится в git; настоящие значения — только в `.env`.

Дальше:

```bash
# Схема БД — requests/request_steps/documents (см. PLAN.md §2). --envPath обязателен:
# node-pg-migrate по умолчанию ищет .env в ingestion/ (там, откуда запущен скрипт), а не в
# корне репозитория.
npm run migrate -w ingestion -- up --envPath ../.env

npm run start:dev -w backend    # API на :3000 (см. PORT в .env)
npm run dev -w frontend         # UI на :3001
```

Никакого наполнения корпуса законодательства не требуется — Агенты 1 и 2 ищут нормы живьём через
`web_search` на каждый запрос (см. §9).

Проверить без фронтенда:

```bash
curl -X POST http://localhost:3000/requests \
  -H "Content-Type: application/json" \
  -d '{"queryText":"Меня уволили без предупреждения, законно ли это?"}'

curl http://localhost:3000/requests/<id из ответа>
```

Подробности по каждому компоненту — `backend/README.md`, `frontend/README.md`.

## 1. Решения по стеку

1. **LLM-провайдер:** OpenAI (ChatGPT / API) — _решено_. Нужен `OPENAI_API_KEY`.
2. **Backend-язык:** Node.js + NestJS + TypeScript — _решено_. Единый язык с фронтендом
   (Next.js), общие типы контрактов между агентами вынесены в `shared/`.
3. **Хостинг:** ещё не выбран (облако vs свой сервер) — не блокирует Этапы 0–1, понадобится к
   Этапу 11 (деплой). БД уже на Supabase независимо от выбора хостинга backend (см. §7.1).
4. **Домен и бренд** сайта — не выбраны, не блокируют разработку.
5. **Бюджет на инфраструктуру** — LLM-вызовы основная статья расходов. Агенты 1 и 2 ищут нормы
   живьём через `web_search` на каждый запрос (см. §9) — офлайн-индекс пробовали как способ
   снизить эту стоимость и латентность, но откатили 2026-08-28 (см. §9.5): ресинк корпуса требовал
   сетевого доступа к adilet.zan.kz, которого не было из части инфраструктуры.

## 2. Структура репозитория

```
zan/
├── INSTRUCTIONS.md          # этот файл
├── docker-compose.yml       # Postgres, Redis — опционально для локальной разработки
├── frontend/                # веб-интерфейс (Next.js) — Этап 7
├── backend/                 # API Gateway + оркестратор + 4 агента (NestJS)
├── ingestion/                # только миграции общей схемы БД (см. §9 — раньше здесь же был
                               # синк корпуса законодательства, убран 2026-08-28)
└── shared/                   # общие типы, логирование, LLM-клиент — DRY между backend и ingestion
```

Детальная структура — в `backend/README.md`, чтобы не дублировать и не рассинхронизироваться с
кодом. Внутри `backend/src/` ключевые директории сверх стандартного NestJS-набора: `agents/`
(4 агента пайплайна, Агенты 1/2 ищут нормы живьём через `web_search`, см. §9), `orchestrator/`
(собирает пайплайн воедино).

Каждый агент backend'а — отдельный файл с одним публичным интерфейсом (`run(input): Promise<Output>`,
см. `backend/src/agents/agent.types.ts`) и DI-токеном, за которым эта реализация подставляется —
это даёт возможность подменять/тестировать агентов независимо (Open/Closed, Dependency Inversion).

## 4. Конвенции разработки

- **Ветки:** `feature/<короткое-описание>`, `fix/<описание>`, `chore/<описание>`.
- **Коммиты:** осмысленные сообщения на английском или русском — главное, последовательно.
- **Один PR — одна логическая задача.** Не смешивать этапы плана в одном PR.
- **Каждый агент и оркестратор покрываются unit-тестами** до того, как считается «готово».
- Перед мержем значимых изменений — прогон `/security-review` (уязвимости — приоритет №1
  для этого проекта, так как обрабатываются юридические запросы пользователей).
- Комментарии в коде — только там, где неочевидна причина решения (WHY), не что делает код.
- **Backend (NestJS) запускается через `tsx` (esbuild), который не поддерживает TypeScript
  `emitDecoratorMetadata`.** Это ломает две вещи, которые в обычных Nest-проектах работают
  "из коробки" — молча, без ошибки при старте:
  1. **Неявный DI по типу конструктора не работает** (`constructor(private readonly x: Foo)`
     резолвится в `undefined`). Правило: **каждый параметр конструктора в каждом
     `@Injectable()`/`@Controller()` — только через явный `@Inject(TOKEN)`**, даже для
     конкретных классов, не только интерфейсов. См. `backend/src/orchestrator/orchestrator.service.ts`.
  2. **Глобальный `ValidationPipe` не может определить DTO-класс параметра** и тихо
     пропускает валидацию. Правило: валидация тела запроса — только явным вызовом
     `validateDto(DtoClass, body)` из `backend/src/common/validate-dto.ts` внутри контроллера,
     `@Body() body: unknown`, без обычного `@Body() dto: SomeDto`.
     Оба правила проверены вручную (см. коммит/PR Этапа 2) — не полагаться на то, что "так
     делают во всех туториалах по Nest", в этом проекте это не работает.

## 5. Логирование — обязательный минимум с первого коммита

Каждый шаг пайплайна должен логироваться структурированно (JSON), со сквозным `request_id`:

```json
{
  "timestamp": "2026-08-19T10:00:00Z",
  "request_id": "uuid",
  "stage": "agent.verification",
  "status": "success | failure | retry",
  "duration_ms": 842,
  "meta": { "law_ref": "ГК РК ст. 123" }
}
```

Правила:

- Персональные данные пользователя в логах — маскировать/не хранить в открытом виде.
- Ошибки логируются с полным контекстом (какой агент, какой вход, какая причина сбоя).
- Логи хранятся централизованно, доступны для аудита конкретного запроса по `request_id`.

## 6. Как добавить нового агента в будущем (Этап 13+)

1. Создать папку в `backend/src/agents/<name>/`.
2. Реализовать единый интерфейс агента (вход/выход, ошибки).
3. Зарегистрировать агента в оркестраторе как новый шаг пайплайна (или ветку пайплайна).
4. Добавить unit-тесты + обновить сквозные интеграционные тесты.
5. Никаких изменений в существующих агентах не требуется — в этом смысл разделения по SOLID.

## 7. Как запускать проект локально

См. [§0 «Быстрый старт»](#0-быстрый-старт) в начале этого файла. Правила `@Inject` и
`validateDto` из раздела 4 — в `backend/README.md`.

### 7.1. Миграции БД — Supabase, не docker-compose

`DATABASE_URL` в `.env` указывает напрямую на прод Supabase Postgres
(`db.<project>.supabase.co`), не на локальный `docker-compose` postgres — им пользуются только
пустой docker-compose `postgres`/`redis` для локальной разработки при желании (см. `README.md`),
основная база проекта — Supabase. Backend в рантайме тоже ходит только в Supabase (через
`@supabase/server`/PostgREST, см. `backend/src/db/db.module.ts`), не подключается к Postgres
напрямую.

**Источник правды для схемы** — версионированные миграции `ingestion/migrations/*.cjs`
(`node-pg-migrate`, коммитятся в git, накатываются `npm run migrate -w ingestion`). Но поскольку
прямое подключение к Supabase Postgres из CLI не всегда удобно/доступно, есть параллельный путь —
`ingestion/supabase-migrations.sql`: копия SQL из тех же миграций одним файлом, чтобы вставить в
Supabase Dashboard → SQL Editor → New query и выполнить руками.

**Правило: при добавлении новой миграции в `ingestion/migrations/` — ОБЯЗАТЕЛЬНО добавь её `up`
SQL новым блоком в конец `ingestion/supabase-migrations.sql`**, с комментарием-заголовком вида:

```sql
-- ============================================================================
-- Версия: <timestamp из имени файла миграции> — <имя файла>.cjs
-- ============================================================================
<сам SQL>
```

`down` в этот файл не переносится (он не нужен для ручного прогона в Dashboard). Не редактируй и
не удаляй уже добавленные блоки — только дописывай снизу.

**SQL в этом файле обязан быть идемпотентным** (у части пользователей уже могут быть некоторые
таблицы созданы руками раньше — файл должен спокойно накатываться поверх этого, без "already
exists"): `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN
IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`; для `CREATE TYPE` (enum, не поддерживает
`IF NOT EXISTS` напрямую) — оборачивать в `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN
NULL; END $$;` (см. примеры в самом файле). Если у функции меняется сигнатура параметров (как в
миграции `law_chunks_fulltext`, добавившей `query_text`) — `CREATE OR REPLACE FUNCTION` не заменит
старую версию с другой сигнатурой, а создаст ВТОРУЮ перегрузку; сначала явный
`DROP FUNCTION IF EXISTS name(старая сигнатура);`. Не копируй `up`-SQL из `.cjs`-миграции сюда
буквально, если он не в такой форме — сначала приведи к идемпотентному виду.

Не смешивай `npm run migrate` и ручную вставку в Supabase SQL Editor на одной и той же базе —
`node-pg-migrate` не знает о миграциях, применённых через SQL Editor (своя служебная таблица
`pgmigrations`), и попытается накатить их заново.

## 8. Границы ответственности сервиса (важно держать в UI и промптах)

- Сервис даёт информационную справку на основе текста закона, а не юридическую консультацию.
- Ответ всегда сопровождается дисклеймером и точной ссылкой на статью/редакцию закона.
- Агент 1 отвечает на основании живого поиска по adilet.zan.kz/zan.gov.kz (`web_search`, см. §9) —
  не по памяти LLM. Агент 2 независимо перепроверяет каждую упомянутую норму собственным живым
  поиском и помечает сомнительные места (`concerns`, см. §9).
- **Полнота ответа не гарантирована математически** — живой поиск не даёт формальной гарантии,
  что учтены вообще ВСЕ применимые нормы (то же верно и для человека-юриста при быстрой
  консультации). Система устроена так, чтобы не выдумывать несуществующие нормы (Агент 1 цитирует
  только то, что реально прочитал через инструмент в этом обращении), но не может доказать
  отсутствие пропущенной нормы вне того, что она сама нашла. Это осознанно принятый компромисс —
  при выводе ответа в UI и в промптах дисклеймер о необходимости консультации с юристом для
  критичных решений должен оставаться видимым пользователю.

## 9. Эволюция архитектуры поиска и верификации (2026-08-27 — 2026-08-28)

Единая хронология пересмотров пайплайна Агент 1 (search) ↔ Агент 2 (verification) — от исходной
проблемы (латентность) через локальный индекс и обратно к живому поиску. Держать в синке с
`README.md` §"Поиск по законодательству" (короче) и `PROMPTS.md` (полные тексты промптов на
каждом этапе).

### 9.0. Исходное состояние — в чём была проблема

Агенты 1 и 2 вызывали LLM с встроенным `web_search` (OpenAI Responses API) **на каждый запрос
пользователя**: модель сама, вживую, читала adilet.zan.kz/zan.gov.kz внутри каждого вызова.
Замер (см. комментарий у `DEFAULT_CHAT_MODEL` в `shared/src/llm/chatClient.ts`): 15-100+ секунд на
один такой вызов. Пайплайн — 2-5 последовательных LLM-вызовов на запрос (search → verification,
до 2 раундов при замечаниях) → итоговая задержка ответа пользователю 60-120 секунд. Неприемлемо
для продукта.

### 9.1. Пересмотр 1 — локальный индекс вместо live-браузинга

**Решение:** офлайн-индексация вместо запросов в интернет на лету.

- Новый пакет-функция `ingestion/src/sync.ts`: скачивает документы из курируемого списка
  (`lawSources.ts`), парсит (`parseDocument.ts` — вырезает ещё не вступившие в силу поправки и
  целиком отменённые документы/статьи на уровне HTML-разметки adilet.zan.kz, не текстом промпта),
  эмбеддит, пишет в `law_chunks` (pgvector, Supabase).
- Новый `backend/src/retrieval/` — векторный поиск по этому корпусу через Supabase RPC
  (`match_law_chunks`), десятки-сотни миллисекунд вместо секунд.
- Агент 1 (`law-search.agent.ts`) больше не получает `web_search` — получает `<law_context>` от
  retrieval и отвечает строго на его основании.
- Агент 2 (`law-verification.agent.ts`) стал детерминированным: сверяет регексом цитаты в ответе
  с тем, что реально было в `<law_context>` — без LLM-вызова вообще.

**Результат:** латентность упала на порядок. **Новая проблема, вскрытая пользователем сразу же:**
курируемый список документов (на тот момент — 4 кодекса) физически не может покрыть всё
законодательство РК — вопрос по непокрытой теме получал "нет данных" вместо ответа.

### 9.2. Пересмотр 2 — расширение корпуса + fallback по пустому результату

**Решение:**

- Расширили `LAW_SOURCES` с 4 до 21 документа (все основные кодексы РК + Конституция) — каждый id
  проверен вживую (`curl` + сверка `<title>`), не угадан.
- Добавили автоматизацию, чтобы клиент никогда не ждал переиндексацию: `backend/src/law-sync/`
  регистрирует в BullMQ ночную (02:00 Алматы) джобу ресинка (см. §7.2).
- Добавили режим `mode: 'live'` в `SearchAgentOutput`/`VerificationAgentInput`: если retrieval
  возвращал **пустой** результат (`citedSources.length === 0`), Агент 1 откатывался на прежний
  live-`web_search`-промпт, Агент 2 — на прежнюю LLM-перепроверку.

**Обнаруженная при этом же разборе проблема (найдена вживую, не гипотетически):** Конституция РК
1995 года (`K950001000_`) формально существует на adilet.zan.kz, но прекратила действие с
01.07.2026 — заменена новой редакцией по референдуму 15.03.2026 (`K2600000000`). Едва не попала в
курируемый список как "действующая". Отсюда — обязательное правило live-проверки статуса
документа перед добавлением id (см. `ingestion/src/lawSources.ts`), не только его существования.

**Результат:** непокрытые темы больше не тупик. **Новая проблема, вскрытая следующим вопросом
пользователя:** триггер "retrieval пуст" не срабатывает, если retrieval находит ЧТО-ТО релевантное
(документ реально в корпусе), но для ПОЛНОГО ответа не хватает ещё одной нормы из документа,
которого в курируемом списке просто нет. Ответ оставался частичным без предупреждения — фейковое
чувство полноты хуже честного "не хватает данных".

### 9.3. Пересмотр 3 — единый промпт, режим решается по факту, не заранее

**Решение (текущее состояние):** отказ от выбора режима ДО вызова LLM. Агент 1 теперь получает
`<law_context>` (может быть пустым) И инструмент `web_search` ОДНОВРЕМЕННО, в одном промпте —
инструкция: использовать контекст как приоритетный источник, обращаться к инструменту, только
если чувствует, что контекста недостаточно для ПОЛНОГО ответа.

Чтобы Агент 2 знал, какую verification применить (детерминированную или LLM), потребовалось узнать
**по факту**, вызвала ли модель инструмент в конкретном обращении — не предсказывать это заранее
по тому, что вернул retrieval. Для этого `ChatClient` (`shared/src/llm/chatClient.ts`) расширен
методом `completeWithMeta()`, возвращающим `{ content, usedWebSearch }` — `usedWebSearch`
вычисляется по наличию элемента `type: 'web_search_call'` в `response.output` OpenAI Responses
API. `mode` в `SearchAgentOutput` теперь = `usedWebSearch ? 'live' : 'grounded'`, определяется
после вызова, а не до.

**Побочно решённая другим способом, отдельная проблема** (найдена в том же разборе, но не про
триггер режима, а про сам поиск): чисто ВЕКТОРНЫЙ поиск внутри уже покрытого документа мог не
найти нужный кусок в top-k, если формулировка вопроса семантически далека от текста статьи
(редкий термин, номер статьи) — документ "в базе", но конкретный кусок мимо. Решение — гибридный
поиск (вектор + Postgres full-text search, `to_tsvector('russian', ...)`), миграция
`law_chunks_fulltext.cjs`, объединение результатов в `match_law_chunks` (60/40 взвешенная сумма
векторного и keyword-скора).

**Дополнительная проактивная защита** (не реактивная, как всё выше): раз в неделю
`ingestion/src/discoverGaps.ts` (LLM + `web_search`, см. §7.2) сверяет текущий `LAW_SOURCES` с
тем, что реально действует, и логирует WARN-находки — важные законы вне списка, документы,
уже заменённые новой редакцией под другим id. Только рекомендация для человека, ничего не меняет
автоматически (LLM-находки не всегда точны — то же правило live-проверки, что и при первом
добавлении id).

### 9.4. Состояние после третьего пересмотра (2026-08-27, отменено 2026-08-28 — см. §9.6)

Retrieval (векторный + full-text, 21 документ, автообновляется ночью) — приоритетный, быстрый
источник. Агент 1 сам решает по каждому запросу, достаточно ли его, или нужно доискать через
`web_search` — решение видно постфактум через `mode`. Verification зеркально ветвится по этому же
`mode`: дёшево и быстро для обычного пути, полноценная LLM-перепроверка для случаев, когда Агент 1
реально ходил в интернет. Курируемый список расширяется вручную (с обязательной live-проверкой
статуса), но пробел в нём не превращается ни в "нет ответа", ни в тихо неполный ответ — превращается
в чуть более медленный, но полный ответ. Еженедельный скан пробелов держит список актуальным
проактивно, а не только реактивно на вопросы клиентов. Известные, осознанно принятые ограничения —
100%-ная полнота не гарантирована математически (см. §8), zan.gov.kz не используется для
ingestion (собственный корневой CA Минюста РК, не входящий в стандартные доверенные — риск
безопасности, не отключаем проверку TLS молча), полный автообход adilet.zan.kz недоступен
(`robots.txt`).

### 9.5. Разбор реальной латентности >3 минут (2026-08-28) и отказ от переспроса

Несмотря на пересмотр §9.1-9.3, на реальном проде запрос всё равно занимал 3+ минуты. Разбор по
факту (не по предположению — см. ниже источники):

- **Корневая причина №1 — корпус на проде оказался пуст.** Проверка через Supabase REST
  (`law_chunks`, `law_documents` — `content-range: */0`) показала 0 строк: `npm run sync -w
ingestion` на проде ни разу не запускался. Следствие: `retrieval.service.ts` всегда возвращал
  `[]`, `<law_context>` у Агента 1 всегда пуст → `mode` был **всегда** `'live'`, не как редкий
  fallback, а как единственный путь — grounded-путь редизайна §9.1-9.3 ни разу не сработал ни на
  одном реальном запросе. Ничего в `startup-checks.ts` это не проверяет — сервисы (Supabase/Redis/
  OpenAI) отвечали здоровьем, деградация была тихой.
- **Корневая причина №2 — цикл переспроса не окупался.** Замер на реальном завершённом запросе
  (`request_steps`, id `e8b702e8...`, суммарно 214с): search round 1 — 44.0с (`mode=live`),
  verification round 1 — 56.1с, 4 замечания; search round 2 (revision) — 36.6с (`mode=live`
  снова), verification round 2 — 48.7с, **те же 4 замечания** — второй раунд не устранил ни
  одного замечания, но добавил ~85с. editor — 22.7с.

**Решение (текущее, 2026-08-28):**

1. Наполнить корпус на проде (`npm run sync -w ingestion`) — операционный, а не архитектурный шаг,
   но без него grounded-путь не включается вообще.
2. **Убран цикл переспроса search↔verification** (`MAX_VERIFICATION_ROUNDS`,
   `orchestrator.service.ts`). Search и verification теперь вызываются ровно по одному разу на
   запрос, независимо от найденных замечаний — данные выше показали, что повторный раунд не
   гарантирует устранения замечаний, но безусловно стоит ещё один полный LLM-вызов (в live-режиме
   до ~85с). Замечания verification не блокируют пайплайн и не переписывают `draftAnswer` через
   повторный запрос Агенту 1 — они остаются в `request_steps` шага verification (видны через
   `GET /requests/:id`) как диагностическая информация для ручной проверки при доработке промптов,
   не как автоматический gate. `SearchAgentInput.revision`, `<verifier_notes>` — удалены как
   код, ставший недостижимым после этого изменения (см. `law-search.agent.ts`,
   `shared/src/security/userContent.ts`).

Отдельно, не устранено в рамках этого разбора: `startup-checks.ts` пока не проверяет, что
`law_chunks` не пуст — это позволило корневой причине №1 остаться незамеченной. Стоит добавить
как последующий шаг (gauge/health-check по размеру корпуса), не сделано здесь, чтобы не смешивать
с решением по латентности. **Далее оказалось не нужным, см. §9.6 — план "наполнить корпус" из
пункта 1 выше физически неисполним, retrieval-слой убран целиком.**

### 9.6. Полный откат retrieval-слоя — возврат к живому поиску (2026-08-28)

План из §9.5 («наполнить корпус на проде») уже на следующем шаге разбился о инфраструктурное
ограничение: `npm run sync -w ingestion` требует прямого сетевого доступа к `adilet.zan.kz` (и к
`db.<project>.supabase.co:5432` напрямую по Postgres-протоколу для миграций/синка — не через
Supabase PostgREST, которым пользуется backend в рантайме). Проверено вживую: `curl`/DNS-résolve
обоих хостов из среды, где ведётся разработка, зависает/не резолвится, при этом `api.openai.com` и
обычные HTTP-хосты доступны нормально — то есть это не временный сбой сети вообще, а ограничение
конкретно этих двух хостов из данной инфраструктуры. Раз корпус нельзя наполнить оттуда, откуда
реально идёт разработка/деплой, вся конструкция §9.1–9.4 (курируемый список, ночной ресинк,
еженедельный скан пробелов, гибридный `mode`) не может работать надёжно — она уже не работала на
проде ни разу (см. §9.5, корневая причина №1) и нет причин ожидать, что заработает после починки
только доступа: сам факт, что синк требует сетевого доступа, которого структурно нет, — не
временная случайность.

**Решение: retrieval-слой убран целиком, не чинится.** Агенты 1 и 2 возвращены к исходному подходу
§9.0 — живой поиск через `web_search` (OpenAI Responses API, домены adilet.zan.kz/zan.gov.kz) на
каждый запрос пользователя, без локального индекса. Латентность решается не индексом, а тем, что
уже сделано в §9.5 — циклом переспроса search↔verification, который убран и не возвращён.

Удалено полностью:

- `ingestion/src/{sync.ts,lawSources.ts,parseDocument.ts,discoverGaps.ts,db.ts,config.ts,chunker.ts,
fetchDocument.ts}` — весь код синка корпуса; `ingestion/` теперь только владелец миграций
  `requests`/`request_steps`/`documents`.
- `backend/src/retrieval/` (retrieval.service.ts и т.д.) и `backend/src/law-sync/` (ночные
  BullMQ-джобы синка/скана пробелов) — целиком, вместе с DI-регистрацией в `agents.module.ts`/
  `app.module.ts`.
- `shared/src/llm/embeddingClient.ts` (`EmbeddingClient`/`OpenAiEmbeddingClient`) — эмбеддинги
  были нужны только для retrieval/sync.
- `ChatClient.completeWithMeta`/`usedWebSearch`/`ChatCompletionResult` (`shared/src/llm/chatClient.ts`)
  — существовали только для того, чтобы Агент 1 узнавал постфактум, использовал ли он `web_search`
  (нужно было для выбора `mode` в гибридной схеме §9.3); при чистом live-поиске это больше не
  нужно, `ChatClient.complete()` снова возвращает просто строку.
- `SearchMode`, `SearchAgentOutput.citedSources`/`.mode`, `VerificationAgentInput.citedSources`/
  `.mode` (`agent.types.ts`) — гибридного режима больше нет; `LawVerificationAgent` — только
  live-путь (бывший `mode==='live'` из §9.2, единственный оставшийся).
- Метрики `zan_search_mode_total`, `zan_retrieval_duration_ms`, `zan_retrieval_result_count`,
  `zan_law_sync_duration_ms`, `zan_law_sync_total` (`metrics.service.ts`) — измеряли то, чего
  больше нет.

Схема БД (`law_documents`/`law_articles`/`law_chunks`, `match_law_chunks`) откатывается штатным
`node-pg-migrate down` — миграции `1787130553000_law_corpus.cjs` и `1787130554000_law_chunks_fulltext.cjs`
уже содержат корректный `down()`. Выполнить (не автоматизировано здесь — тот же сетевой барьер,
что и выше, делает это невозможным из среды разработки; нужен доступ к
`db.<project>.supabase.co:5432` напрямую):

```bash
npm run migrate -w ingestion -- down 2 --envPath ../.env
```

Таблицы на момент отката были пусты (`sync` ни разу успешно не отработал, см. §9.5) — потери
данных нет. Если миграции применялись через Supabase Dashboard → SQL Editor (не через
`node-pg-migrate`, см. §7.1), `down` из `.cjs`-файлов туда не переносится (это осознанное решение
для того файла) — выполнить эквивалентный `DROP FUNCTION`/`DROP TABLE` вручную по образцу `down()`
в указанных миграциях.

**Промпты Агента 1/2 переписаны заново** (не восстановлены дословно из §9.0 — с тех пор прошло
несколько пересмотров, часть формулировок про "систематически рассмотри все реалистичные варианты
ответственности" и т.п. из §9.3 сохранена как ценная, независимо от режима поиска), см. `PROMPTS.md`.

### 9.7. Оптимизация стоимости/качества/latency (2026-08-28)

После отката §9.6 пайплайн снова стал похож на исходный §9.0 (2 живых LLM+web_search вызова
подряд) — вместе с этим вернулись и его старые болячки: пользователь оценил стоимость одного
пайплайна примерно в $1 (это ощущение, не замер по `zan_llm_request_total` — точную цифру
предстоит снять оттуда по факту), ответ воспринимался как "сгенерированный ИИ", и хотелось ещё
снизить latency. Разбор без переизобретения retrieval-слоя (см. §9.6 — сетевой барьер к
adilet.zan.kz никуда не делся):

- **Все 4 агента использовали одну и ту же модель** `gpt-5.6-sol` (`DEFAULT_CHAT_MODEL`,
  `chatClient.ts`) — переключённую туда 2026-08-23 "по прямому указанию", без единого замера
  latency/качества/стоимости. При этом в коде уже лежал реальный замер по `gpt-5.6-luna`: то же
  качество на реальном юридическом кейсе, заметно быстрее и (предположительно) дешевле `terra`.
  **Решение:** `DEFAULT_CHAT_MODEL` возвращён на `gpt-5.6-luna` — единственная модель из трёх с
  подтверждённым, а не предполагаемым, качеством на этой задаче.
- **Агент 3 (editor) — единственный шаг без web_search, то есть самый дешёвый вызов в пайплайне —
  сидел на `reasoningEffort: 'low'`**, как и остальные три (дорогих) агента, хотя именно от него
  зависит, насколько ответ звучит по-человечески (перефразирование, сжатие). **Решение:** поднят
  до `'medium'` — cost-нейтрально относительно live-поиска остальных агентов, при этом прямое
  влияние на воспринимаемое качество текста. Заодно переписан сам промпт
  (`law-editor.agent.ts`): убраны жёсткие markdown-заголовки (гипотеза — сама структура "отчётом"
  читается как шаблонный ИИ-ответ, даже если язык внутри живой), добавлен список запрещённых
  ИИ-штампов и короткий few-shot пример нужного тона/длины прямо в промпте. **Откачено в тот же
  день по фидбэку** — формат без заголовков вышел хуже прежнего, не лучше: промпт вернули к
  версии с заголовками ("## Что говорит закон" и т.д., см. `PROMPTS.md`), `reasoningEffort:
'medium'` оставлен — это независимый от структуры текста рычаг. Урок: гипотеза "заголовки =
  шаблонность" здесь не подтвердилась на практике, при следующей попытке менять
  формат — проверять на реальных ответах, не полагаться на рассуждение заранее.
- **Агент 4 (document) всегда делал свой web_search**, даже для типов документов, где официальной
  формы в законе обычно нет ("заявление", "претензия" — сам промпт это и предполагал как fallback,
  но инструмент всё равно вызывался). **Решение:** веб-инструмент теперь выдаётся УСЛОВНО —
  эвристика по ключевым словам в `documentType` (`иск`/`жалоб`/`апелляц`/`кассац`/`ходатайств`,
  см. `mayHaveOfficialForm()` в `law-document.agent.ts`) — это приблизительный список, не
  юридически выверенный перечень процессуальных документов РК, уточнять по факту (обращения, где
  документ вышел неверной структуры), не расширять заранее вслепую. Для остальных типов документ
  строится сразу по общепринятой деловой структуре, без лишнего живого поиска.

**Осознанно не сделано в рамках этого пересмотра** (обсуждали, отложили): связать Агента 2 с
конкретными URL, которые реально открыл Агент 1 (Responses API возвращает `url_citation` с
реальным адресом страницы в `response.output`, см. типы `openai` SDK) — вместо независимого
поиска с нуля Агент 2 проверял бы именно эти страницы. Даёт и cost, и latency одновременно, но
меняет контракт между агентами (`SearchAgentOutput` пришлось бы снова расширять) и требует
отдельного тщательного теста, прежде чем трогать verification — основной content-quality gate
пайплайна.
