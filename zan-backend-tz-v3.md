# Zan — Техническое задание на бэкенд v3

Обновление v2 → v3. Ключевые изменения:
1. **Авторизация убрана.** Продукт полностью общедоступен, пользователь идентифицируется **сессией**, без регистрации/логина/OTP.
2. **Разделение сервисов**: ядро системы — на **Go**, всё, что связано с LLM/речью/извлечением контента из файлов — на **Python (FastAPI)**. Go оркестрирует и вызывает Python как внутренний сервис.
3. Добавлен полный **каталог ошибок** — что происходит и что видит пользователь в каждом сценарии сбоя.
4. Добавлена схема **логирования** по этапам обработки, включая приём событий с фронта.

---

## 1. Архитектура и разделение задач

### 1.1 Go — ядро системы (весь основной трафик)
Всё, что не требует вызова LLM/ML-моделей напрямую:
- Сессии (создание, продление, идентификация)
- Треды и сообщения — CRUD, статусная модель, история
- Оплата (заглушка), баланс/кредиты по услугам
- Услуги и тарифы (публичные + админ CRUD)
- Промпты агентов — хранение и выдача (сам текст промпта; вызов LLM с этим промптом делает Python)
- Загрузка файлов — приём, валидация (тип/размер/антивирус), сохранение в хранилище, метаданные
- Аналитика (агрегаты по своей же БД)
- Приём логов с фронта
- Оркестрация вызовов к Python-сервису (с таймаутами, ретраями, circuit breaker)

### 1.2 Python (FastAPI) — всё, что связано с AI/ML
Внутренний сервис, недоступный напрямую с фронта — вызывается только из Go по внутренней сети:
- Вызов LLM-агента "Вопрос-ответ" (сборка промпта + история треда → структурированный ответ)
- Вызов LLM-агента "Документы" (анализ загруженного файла / генерация нового документа)
- STT — распознавание голосовых сообщений в текст
- Извлечение текста из файлов (PDF/DOCX/изображения, включая OCR)
- Сборка итогового файла документа (PDF/DOCX) из ответа агента

### 1.3 Контракт Go ↔ Python
Внутренние эндпоинты (пример), без аутентификации пользователя — защищены на уровне сети (внутренний VPC/сервис-мэш) + shared secret между сервисами:

| Метод | Путь | Вызывается при | Тело запроса | Ответ |
|---|---|---|---|---|
| POST | `/internal/agent/qa` | новое сообщение в `qa`-треде | `{prompt_text, history[], attachments_text[]}` | `{answer_text, sources[], needs_clarification}` |
| POST | `/internal/agent/document` | генерация документа | `{prompt_text, history[], attachments_text[]}` | `{answer_text, findings[], document_draft}` |
| POST | `/internal/stt` | голосовое сообщение | multipart audio | `{text}` |
| POST | `/internal/files/extract` | загружен файл на анализ | `{file_url, mime_type}` | `{extracted_text, pages, warnings[]}` |
| POST | `/internal/documents/render` | после генерации документа | `{document_draft, format: pdf\|docx}` | файл (бинарь) или `{file_url}` |

Каждый вызов **обязательно** прокидывает заголовок `X-Trace-Id` (= `thread_id` или `message_id`) — см. §6.

## 2. Сессии (вместо авторизации)

### 2.1 Принцип
- Логина/регистрации нет. При первом обращении клиент создаёт сессию: `POST /sessions` → Go выдаёт подписанный непрозрачный токен (`session_token`, напр. JWT-подобный, но без пользовательских данных внутри — только `session_id` + подпись, чтобы токен нельзя было подделать).
- Токен возвращается и в `Set-Cookie` (httpOnly, Secure, SameSite=Lax) для веба, и в теле ответа — для мобильного клиента, который хранит его сам (Keychain/Secure Storage) и передаёт в `Authorization: Session <token>`.
- Сессия — скользящее окно: `expires_at = last_seen_at + 90 дней`, продлевается при каждом запросе.
- Баланс, история, промпты/тарифы (админ-часть) — привязаны к `session_id`, а не к "аккаунту". Это значит: **баланс и история живут в браузере/устройстве**, смена устройства или очистка кук = потеря доступа к прошлым тредам и балансу. Это осознанный компромисс на данном этапе — см. риск в §2.3.

### 2.2 Session (сущность, заменяет User)
| Поле | Тип | Описание |
|---|---|---|
| id | UUID | = `session_id` |
| language | enum: `ru`, `kz` | |
| theme | enum: `light`, `dark`, nullable | |
| onboarding_seen | bool | |
| created_at, last_seen_at, expires_at | timestamp | |

Все сущности, ранее ссылавшиеся на `user_id` (`UserCredit`, `Payment`, `Thread`), теперь ссылаются на `session_id`.

### 2.3 ⚠️ Риск, который нужно явно решить с продуктом
Без авторизации и без ролей `/admin/*` (промпты, услуги, тарифы) **физически ничем не защищены** — любой человек с URL может их открыть и изменить. Раньше это был осознанный временный компромисс ("открыто пока для всех, потом скрою"), но теперь, когда убрана авторизация целиком, скрыть эти роуты позже будет не так тривиально, если сразу не заложить механизм. Рекомендация: даже без полноценной авторизации пользователей — завести отдельный **admin-secret** (статичный токен/пароль в заголовке `X-Admin-Token`) уже сейчас для `/admin/*`, не завязанный на сессии пользователей. Это не блокирует разработку, но защищает продукт с первого дня. Прошу подтвердить — закладываем?

## 3. Данные (изменения относительно v2)

Все таблицы из v2 сохраняются, кроме:
- ~~`User`~~ → заменена на `Session` (см. §2.2), без `phone`/`email`/`role`.
- `UserCredit.user_id` → `UserCredit.session_id`
- `Payment.user_id` → `Payment.session_id`
- `Thread.user_id` → `Thread.session_id`

Остальные сущности (`Service`, `Tariff`, `Thread`, `Message`, `FileAttachment`, `AgentPrompt`) — без изменений, см. v2 §2.2–2.3, §2.6–2.9.

## 4. API (актуализация)

`/auth/*` **удаляется полностью**. Вместо него:

| Метод | Путь | Сервис | Описание |
|---|---|---|---|
| POST | `/sessions` | Go | создать новую сессию → `{session_token, session_id}` |
| GET | `/sessions/me` | Go | текущая сессия (язык, тема, `onboarding_seen`) |
| POST | `/sessions/onboarding-seen` | Go | пометить онбординг просмотренным |
| PATCH | `/sessions/me` | Go | обновить `language`/`theme` |

Остальной API — как в v2 (§3.2–3.8), с пометкой, какой сервис реально исполняет логику:

| Группа | Роуты | Кто исполняет |
|---|---|---|
| Треды/сообщения (CRUD, статусы, баланс) | `/threads*` | Go (оркестрирует, вызывает Python для генерации ответа) |
| Голос | `/voice/transcribe` | Go принимает файл → проксирует в Python `/internal/stt` |
| Файлы | `/files/upload`, `/files/{id}` | Go принимает/хранит → вызывает Python `/internal/files/extract` для текста |
| Услуги/тарифы/баланс | `/services`, `/tariffs`, `/balance` | Go |
| Оплата | `/payments/*` | Go |
| Обратная связь | `/messages/{id}/feedback` | Go |
| Админ: промпты/услуги/тарифы | `/admin/*` | Go (+ `X-Admin-Token`, см. §2.3) |
| Аналитика | `/admin/analytics/overview` | Go |
| Логи с фронта | `/logs/client` | Go — см. §6.3 |

## 5. Каталог ошибок и поведение системы

Общий принцип: пользователь никогда не видит "сырую" ошибку интеграции (текст исключения, стектрейс, ответ LLM как есть) — только понятное сообщение на его языке. Все ошибки логируются с полным техническим контекстом (см. §6).

### 5.1 Оплата

| Сценарий | Что делает бэкенд | Что видит пользователь |
|---|---|---|
| `checkout` с несуществующим `tariff_id` или пустыми `items` | 400, не создаёт `Payment` | "Не удалось сформировать оплату, попробуйте ещё раз" |
| `confirm` вызван повторно для уже подтверждённого платежа | идемпотентно возвращает прежний успешный результат, баланс не начисляется повторно | ничего не меняется, тред/баланс как после первого успеха |
| Платёж оформлен (`pending`), но `confirm` так и не вызван | фоновая задача каждые N минут помечает `pending`-платежи старше 30 минут как `failed`, связанный тред остаётся `queued`/неоплаченным | если пользователь вернулся позже — видит тред в статусе "ожидает оплаты", может оплатить заново |
| Мок-платёж "не прошёл" (симулированный отказ) | `status=failed`, баланс не меняется, тред остаётся неоплаченным | "Оплата не прошла. Попробовать снова" + кнопка повтора |
| (На будущее, для реальной интеграции) отказ карты / недостаточно средств / 3DS не пройден / вебхук от провайдера не пришёл вовремя | архитектура уже это допускает через `status=failed` + `provider` — детали реализовать при подключении реального шлюза | аналогичный "Оплата не прошла" + причина от провайдера, если он её даёт |

### 5.2 Обработка запроса агентом

| Сценарий | Что делает бэкенд | Что видит пользователь |
|---|---|---|
| Python-сервис не отвечает (таймаут/5xx) | Go делает до 2 повторов с backoff; если не помогло — `thread.status = error`, кредит услуги возвращается на баланс (§4.2 из v2) | "Не удалось обработать запрос, попробуйте ещё раз. Оплата возвращена на баланс" |
| Агент вернул невалидный/неразбираемый JSON | то же самое (`status=error`, возврат кредита), сырой ответ агента пишется в лог для разбора | тот же текст, что выше |
| Модель отказалась отвечать / контент заблокирован модерацией провайдера | `status=error`, возврат кредита. Пользователю не показывается формулировка отказа модели | "Не удалось обработать запрос, попробуйте переформулировать" |
| Агент запросил уточнение (`needs_clarification: true`) | это не ошибка: `status = clarify`, кредит не возвращается (обращение продолжается) | ассистент задаёт уточняющий вопрос в чате |
| Генерация документа упала после успешного ответа в чате | ошибка изолирована **только** к `doc`-кредиту и статусу конкретной операции генерации — сам тред/ответ в чате не откатывается | "Ответ готов, но не удалось подготовить файл документа. Попробовать ещё раз" + кредит `doc` возвращается |

### 5.3 Файлы

| Сценарий | Что делает бэкенд | Что видит пользователь |
|---|---|---|
| Неподдерживаемый тип файла | отклоняется на `POST /files/upload`, `413`/`415`, баланс не трогается (до оплаты дело не доходит) | "Этот формат файла не поддерживается" |
| Файл превышает лимит размера | `413` | "Файл слишком большой (макс. N МБ)" |
| Антивирус пометил файл как опасный | файл не сохраняется, событие логируется как security-инцидент | "Не удалось загрузить файл" (без деталей） |
| `/internal/files/extract` не смог прочитать файл (плохой скан, повреждён) | файл помечается `processing_status=error`, сообщение всё равно уходит агенту с пометкой "файл не удалось прочитать" | агент в ответе сам просит переслать файл читаемым — это заводится как обычный `needs_clarification`, не ошибка треда |

### 5.4 Голос

| Сценарий | Что делает бэкенд | Что видит пользователь |
|---|---|---|
| Нет доступа к микрофону | не доходит до бэкенда — обрабатывается на фронте, событие пишется через `/logs/client` | "Разрешите доступ к микрофону в настройках браузера" |
| STT вернул ошибку/таймаут | Go не отправляет пустой текст в тред, возвращает ошибку клиенту без создания сообщения | "Не удалось распознать голос, попробуйте текстом" |
| STT вернул пустой текст (тишина) | то же, без создания сообщения | "Не расслышал, повторите ещё раз" |

### 5.5 Баланс и сессии

| Сценарий | Что делает бэкенд | Что видит пользователь |
|---|---|---|
| Гонка: два запроса одновременно пытаются списать последнюю единицу баланса | списание баланса — атомарная операция с блокировкой строки (`SELECT ... FOR UPDATE` / аналог в используемой БД), второй запрос увидит баланс = 0 после первого | второй пользователь получает штатный сценарий "баланс закончился, нужна оплата" |
| Сессия истекла (`expires_at` в прошлом) | `401`, но т.к. авторизации нет — Go просто создаёт новую сессию прозрачно на следующий `POST /sessions` | пользователь не видит ошибку, но теряет доступ к старой истории/балансу (см. риск §2.3) |
| Токен сессии подделан/невалидная подпись | `401`, сессия не создаётся автоматически — требуется новый `POST /sessions` | как при первом заходе — чистое состояние |

### 5.6 Инфраструктурные

| Сценарий | Что делает бэкенд | Что видит пользователь |
|---|---|---|
| Python-сервис полностью недоступен (не только таймаут одного запроса) | circuit breaker в Go отключает попытки на N секунд после серии отказов, все новые треды сразу уходят в `error` без долгого ожидания | "Сервис временно недоступен, попробуйте позже" |
| БД недоступна | `503` на уровне Go | общий экран "Сервис временно недоступен" |
| Хранилище файлов недоступно | загрузка файла возвращает `503`, сообщение без файла отправить нельзя | "Не удалось загрузить файл, попробуйте позже" |

### 5.7 Злоупотребления (важно из-за отсутствия авторизации)

| Сценарий | Что делает бэкенд | Комментарий |
|---|---|---|
| Массовое создание сессий/тредов с одного IP (спам, нагрузочная атака) | rate limiting на `POST /sessions` и `POST /threads` по IP + по `session_id` | обязательно на первом этапе, раз нет логина — единственный барьер |
| Подбор/перебор `admin-secret` | rate limiting + блокировка IP после N неудачных попыток на `/admin/*` | см. §2.3 |

## 6. Логирование

### 6.1 Формат
Структурированные JSON-логи (не текстовые строки) во всех сервисах (Go и Python), вывод в stdout → собираются агрегатором (Loki/ELK/аналог — конкретный выбор вне скоупа этого ТЗ). Обязательные поля в каждой записи:
```json
{
  "timestamp": "...",
  "level": "INFO|WARN|ERROR|CRITICAL|DEBUG",
  "service": "go-core | python-agent",
  "trace_id": "...",      // = thread_id, сквозной по всей цепочке
  "session_id": "...",
  "stage": "...",         // см. §6.2
  "message": "...",
  "context": { ... }      // произвольные доп. поля под конкретный stage
}
```

### 6.2 Этапы обработки одного запроса (пример для нового сообщения в треде)

| # | Этап (`stage`) | Сервис | Уровень | Что логируем |
|---|---|---|---|---|
| 1 | `request_received` | Go | INFO | session_id, thread_id (или "new"), input_type |
| 2 | `balance_checked` | Go | INFO | service_id, credit_before, credit_after |
| 3 | `payment_required` / `payment_confirmed` | Go | INFO | payment_id, amount |
| 4 | `thread_status_changed` | Go | INFO | from_status → to_status |
| 5 | `file_extract_started` / `file_extract_completed` | Python | INFO/WARN | file_id, extracted_chars, warnings |
| 6 | `stt_started` / `stt_completed` | Python | INFO/WARN | audio_duration_ms, latency_ms |
| 7 | `agent_call_started` | Go→Python | INFO | agent_type, prompt_version (можно хэш промпта, чтобы видеть, какой именно текст использовался) |
| 8 | `agent_call_completed` | Python | INFO/ERROR | latency_ms, success/fail, needs_clarification |
| 9 | `message_saved` | Go | INFO | message_id |
| 10 | `thread_status_changed` (финал) | Go | INFO | → `done`/`clarify`/`error` |
| 11 | `credit_refunded` | Go | WARN | только если `error` — service_id, session_id |
| 12 | `response_sent` | Go | INFO | итоговый статус, длительность всей цепочки |

Каждая запись со `stage` из списка выше обязана нести один и тот же `trace_id`, чтобы всю цепочку одного запроса можно было поднять одним фильтром в логах.

### 6.3 Логи с фронтенда
`POST /logs/client` (Go, без rate-лимита ниже разумного, но с базовой защитой от спама):
```json
{
  "session_id": "...",
  "trace_id": "...",        // если событие привязано к конкретному треду/запросу
  "level": "INFO|WARN|ERROR",
  "event": "mic_permission_denied | api_call_failed | render_error | ...",
  "message": "...",
  "context": { "url": "...", "user_agent": "...", "screen": "chat|history|tariffs|settings" }
}
```
Это позволяет соединить клиентские события (отказ в доступе к микрофону, неудавшийся вызов API с фронта, необработанное исключение в интерфейсе) с серверной цепочкой по `trace_id`/`session_id` в общей системе логов.

### 6.4 Уровни логирования — общее правило
- `DEBUG` — только в dev-окружении, детали промптов/сырых ответов LLM
- `INFO` — штатные переходы этапов (§6.2)
- `WARN` — восстановимые сбои (сработал ретрай, файл не распознан, но обработка продолжилась)
- `ERROR` — операция завершилась отказом, пользователю показана ошибка, баланс/данные скорректированы (возврат кредита и т.п.)
- `CRITICAL` — инфраструктурный сбой уровня всего сервиса (Python недоступен целиком, БД недоступна)

## 7. Вне скоупа текущего этапа (без изменений/дополнено)

- Реальная интеграция платёжного шлюза
- Полноценная авторизация/аккаунты (сознательно убрано в v3 — сессии вместо неё)
- Перенос баланса/истории между устройствами (следствие отказа от аккаунтов — см. риск §2.3)
- Инлайн-редактирование сгенерированного документа
- Централизованная система сбора логов (Loki/ELK/аналог) — предполагается, но конкретный инструмент выбирается отдельно
